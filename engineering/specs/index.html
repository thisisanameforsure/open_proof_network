Open Proof Network — spec site

The build plan for the Open Proof Network — a distributed crowdsourced Lean 4 proof network for open mathematical problems. Every session starts with the constitution; features follow the conventions. The design input is the architecture decisions document (docs/architecture_decisions_v_3_12.html), whose D-numbers are frozen citable identifiers. That document is what is built; everything under engineering/ is how. Specs cite decisions, never restate or override them. This repo is network — gate, API/MCP, website (D-35); the graph repo is the sibling ../open_proof_network_graph, and nothing on this site lands there.

Features — dependency order

Two features are built but not tagged. F03 and F05 each have one acceptance criterion that needs a graph with an unproved node — a real merge (F03-AC13) and a claim round trip against the deployed service (F05-AC19). The live graph holds one node and it is proved, so both wait on F11's intake rather than on any code; adding a node purely to satisfy them would put content in the mathematical record for a test's sake (F05-Q6, decided 2026-09-09).

F06 is done. The GitHub App permission landed on 2026-09-10, main was pushed, and the graph was re-pinned to it — in two commits, because a precheck job pins frontier.json's rendered_from and reads the network pin from that commit (F06-Q10), so the pin had to land before the products were rendered from it. D-19's account-free loop then ran end to end on the live service: an anonymous precheck of the tutorial node, a signed attestation from a hosted runner, a nonce exchanged for a write token, and that token authenticating a write route.

F07 and F08 interleave, by design. F07-T4 needs F08's admission check for a partial's holes (F07 §8), and F08 needs the rest of F07 for everything else — so F08-T1 was built inside F07's slice on 2026-09-10, and F07-T4 landed the same day on top of it. T5 and T6 followed. The one piece of F07 still outstanding is the graph's gate.yml (T1's last line), now unblocked by the re-pin. F08-T2 followed on 2026-09-10: the proposal and curator modes, the graph's curators.json, and a gate.yml that admits a proposal inside the sandbox and regenerates the products for every merged mode — committed to the graph in a form the old pin ignores (F08-Q8), so it switches on with T6's re-pin. Driving admission through the real container for the first time found the relation check reading the root's statement from outside the sandbox's mounts (F08-Q13). T6 met AC21 against the live service on 2026-09-10, and it found three defects no fake could: a DynamoDB Decimal reaching the JSON encoder (MemoryStore round-trips exactly); the contributor being recorded as committer as well as author, because the Git Data API copies an absent committer from the author — so omitting the field, which the earlier test asserted, was the defect rather than the enforcement; and the smoke resubmitting the committed Proof.lean byte for byte, which made the pull request empty and the gate green over nothing.

What is left of F07, and why it needs a decision. T1's gate.yml line landed on the graph as 1ac359d: the mode is now decided by the pinned commit rather than by a sed script in the graph, proved on a live submission. Three things remain, and all three are the same shape of problem — an act that needs write permission on a pull-request trigger, which C8 forbids and D-4 forbids the App doing. Merging append and explainer mode on green (R9, R10, F07-Q16); recording a racing proof as an alternate and closing its pull request unmerged (R7, F07-Q17); and the post-merge effects having no caller at all (R6, R12, F07-Q17). Decided 2026-09-10 not to build the privileged actor yet: there are no contributors, so it would buy a risk early for a convenience nothing uses, and the first real submissions are worth watching land by hand. The five affected requirements are badged in the F07 table so the gap is visible where the requirement is, not only in the questions.

The graph's merge gate was broken and is fixed (2026-09-10). Its main ruleset required a status check named gate (steps 1, 2, 4, 5 in the sandbox) while the workflow's job reports gate (steps 1, 2 and 4-8 in the sandbox) — the name drifted when the gate grew from four sandboxed steps to six. GitHub matches by exact name, so the required check never reported and no pull request could ever merge. Corrected in the ruleset, that field alone, and verified live: a submission went from blocked to mergeable_state: clean. The same check confirmed two design properties hold — GitHub's own required_approving_review_count is 0, so step 9 stays a property of the statement (D-4 v3.11) rather than a blanket rule, and a pseudonymous submission is not caught by require_extra_approval_for_unattributed_changes, because the App is the committer (F07-R2).

The push and the re-pin happened on 2026-09-10. main is on GitHub at af2f4e7, the api is deployed from it, and each gate-spec.json pins it — so the authoritative gate now runs F07's classifier and artifact checks and F08's admission, and the post-merge products are graph/v2 and targets-index/v2. What that unblocked: F06-AC15 (met), F07-T1's gate.yml line and the two live smokes (F07-T6, F08-T6).
