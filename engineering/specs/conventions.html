Conventions

How we build: architecture, testing, verification, security, git protocol, spec format. Stable rules of the road; feature specs assume these and only state deviations. Stack locked 2026-09-07 (§1); the decisions behind it are recorded in §1 and §2 so a later session can overturn one with evidence rather than re-derive it.

1. Architecture

  • Two repositories (D-35). This repo is network: it has no authority of its own and is rebuildable from the graph. The graph repo is ../open_proof_network_graph, a sibling directory whose history is mathematics only; build work touches it solely for the files D-35 places there (.github/workflows/gate.yml, schemas/, seeded targets and nodes), named in a task's Files column with the ../open_proof_network_graph/ prefix. A gate change reaches a graph only as a diff to its gate-spec.json (D-35).
  • Repo layout (decided by D-35): gate/ — the checks, hazard checkers, pregate.sh, reproduce.sh, devcontainer, olean-cache pipeline · api/ — HTTP endpoints, precheck runner, MCP adapter (D-28) · site/ — static generator (D-36) · AGENTS.md — the one context file for agents building all three. Module owners within each are named on stack lock.
  • Stack (locked 2026-09-07). One language across all three components: Python 3.13, pinned in .python-version, managed by uv with a committed uv.lock; one pyproject.toml at the root. Lint and format: ruff. Types: mypy --strict. Tests: pytest (§2). Runtime dependency: jsonschema, because the protocol's schemas are JSON Schema 2020-12 files that other tools must read (D-34) and a hand-written validator is a bug farm. These four packages are the only ones justified here; any other needs its own C5 justification in a feature spec. Lean side: the toolchain is pinned per graph in gate-spec.json (D-4 step 1, D-7); this repo carries a lean-toolchain for its own Lake package of hazard checkers under gate/lean/, installed via elan. The step-3 sandbox is a container image built from gate/Dockerfile with a digest-pinned base; the same image serves the authoritative gate, precheck and reproduce.sh (D-4: three invocations, one codebase). Why one language: split stacks double the audit surface C5 exists to shrink; Python has an official MCP SDK; it is what the founder reads. Why Python 3.13: current stable at lock time.
  • Python packages live inside the D-35 directories as gate/opn_gate/, api/opn_api/, site/opn_site/. The prefix exists because a top-level package named site would shadow Python's own site module. Tests sit beside their package: gate/tests/, api/tests/, site/tests/. Fixture graphs under gate/tests/fixtures/graphs/<name>/.
  • Where things run (decided 2026-09-07; "boxless" at Stage 0).
    • The authoritative gate runs on GitHub-hosted runners from the graph repo's gate.yml (D-35). Never on a self-hosted runner: GitHub's own guidance forbids self-hosted runners for public repositories because any pull request can execute code on them, and D-24 names that liability. Step 3's isolation is a container the workflow starts with no network, no secrets, non-root, and the cpu/memory/wall-clock caps the graph's gate-spec.json declares (C6).
    • The api and MCP adapter run as an AWS Lambda function behind API Gateway; tokens, claims, precheck jobs and rate-limit counters live in DynamoDB. All of it is operational state (D-35, C9). The MCP server holds no state (D-28), so a stateless function is the honest shape for it.
    • Precheck (POST /precheck, D-28) runs as a GitHub Actions job in a scratch repo (open_proof_network_precheck) dispatched by the api through a GitHub App: the same gate.yml steps minus step 9, on GitHub's throwaway VM, which is the sandbox. The graph repo's history stays mathematics only. Verdicts take minutes, not seconds; that is the accepted Stage 0 cost. Precheck sits behind one seam so it can move to a warm-cache machine with evidence from the invited run, without the api changing.
    • The site (D-36) is rendered by the graph repo's post-merge workflow into an S3 bucket served by CloudFront on a custom domain; CDN logs are the analytics (C9). No server-side code, no database, ever (D-36).
    • Deploys of the api and site happen from CI via OIDC role assumption; no long-lived cloud key exists anywhere (C8).
    • Both repos, and the precheck scratch repo, live under the founder's GitHub account at Stage 0.
  • Module owners. Every module is owned by the founder until Stage 1 roles exist (D-22); the founder is the gate's named owner (D-4) and the MCP server's (D-28).
  • The one config module is opn_gate.config for the gate and opn_api.config for the api; each reads environment and secrets (C8) in one place with documented defaults (C6). Nothing else reads os.environ.
  • Source of truth is the spec site under engineering/specs/; runtime code implements it. Keep responsibilities in named modules so each spec can point at the files it touches.
  • One seam per external boundary. Every call out to an external service goes through a single module so it can be faked in tests and swapped without touching callers. The seams, by name: Toolchain (elan, lake, lean4checker), GitHost (GitHub API: PRs, dispatch, checks), Store (DynamoDB), ObjectStore (S3), Signer (ssh-keygen sign/verify), Clock.

2. Testing

  • Test runner: pytest. Two tiers, both mandatory:
    • make verify — fast, deterministic, offline: ruff check, ruff format --check, mypy --strict, and pytest -m "not lean and not docker and not network". This is the pre-commit hook (§6), so it must stay under a minute on a laptop with no toolchain installed.
    • make verify-lean — the same gate code against the real pinned Lean toolchain and the real step-3 container on the fixture graphs (pytest -m "lean or docker"). It is the named verification command for every task that touches a Lean-facing step, it runs in this repo's CI on every push, and a Lean-facing task is not done until both tiers pass (C1).
    Why two tiers rather than one: a hook that takes minutes gets bypassed, and a suite that needs elan fails on any machine without it; production fidelity comes from the second tier and from evidence, not from the hook.
  • No network in unit tests. Every external service sits behind a seam (§1) with a fake; unit tests use the fake. The fake Toolchain returns structured step results; it never imitates Lean's stdout, because a fake that mimics Lean drifts silently and the real tier is what catches drift.
  • Every gate rejection is a named test. Each step of D-4 that a feature implements ships with an adversarial fixture diff expected to fail at exactly that step (touches Statement.lean, touches another node, touches defs/, edits META.yaml, contains sorry, adds an axiom, uses native_decide, ships a divergent lake-manifest.json, compiles but fails kernel replay, …) and a test that the JSON verdict names that step first with a structured diagnostic (D-34).
  • Markers: lean (needs the toolchain), docker (needs the sandbox image), network (hits a real service). Unmarked tests are the fast tier.
  • Gate and site tests run against fixture graphs kept in this repo — small directories in the D-35 graph/ layout — never against the live graph repo.
  • Every acceptance criterion in a spec names its test case. A criterion without a test is a bug in the spec.
  • Integration tests that hit real services are marked/isolated and run as part of feature verification, not in the default fast run.

3. Verification

  • Each task in a feature's task list names one verification command. The task is done when the command's captured output (saved to engineering/evidence/FXX/task-n.txt) shows pass — C1.
  • Visual work additionally requires a screenshot/recording in engineering/evidence/FXX/.
  • A feature is done when all task verifications pass and the full suite passes.

4. Security

  • No secrets in code, config, or logs. The inventory and its three doors — the git-ignored .env locally, AWS Systems Manager Parameter Store for the api, GitHub Actions secrets for the two signing keys alone — are C8; code reads them through the one config module named in §1 only.
  • External input is untrusted. Contributor submissions, informal annexes, and data from any external service are validated at the boundary before use; they are never interpolated into a query, command, or template unsanitized.
  • New dependencies require a named justification in the spec, a pinned version, and a locked install.

5. Errors, logging, and degradation

  • Exceptions are caught at boundaries, logged with enough context to diagnose, and degrade per C7 (fail safe) — never a silent swallow, never a crash that loses work.
  • Logs carry no secrets and no sensitive data above DEBUG. Records the protocol intentionally keeps — attestations, ledger entries, attempt records — are stores in their own right (C9), distinct from application logs.

6. Git & session protocol

  • Commit per verified task, message = F01-T2: short description; the evidence file is committed with it. Trunk-based on main.
  • Task ledger: each spec's Status block carries a Tasks: line (e.g. T1 ✓ 2026-09-07 · T2–T5 todo) — the single explicit record of task state, updated in the same commit as the task. Any commit that changes task state also updates the feature's Status cell in index.html.
  • This protocol governs the network repo. Specs, evidence and the task ledger live here only. When a task also commits to the graph repo, that commit carries the same FXX-Tn: message so the two histories cross-reference, and its evidence is captured here. How contributors submit to the graph is the protocol's business (D-3, D-4, D-35), not this section's.
  • Verification entrypoint: make verify runs the full suite — the regression gate behind each task's own named command. It also runs as the pre-commit hook (.githooks/pre-commit; enable once per clone with git config core.hooksPath .githooks).
  • Session start: read the constitution, the current feature spec, and the task ledger; state what this session will do. Session end: verifications captured, work committed, spec status updated — the docs stay current or the session isn't done. /session-start runs the start ritual.
  • Feature complete: tag the commit FXX-done, update the Status column in index.html, prune the ## Log in engineering/CLAUDE.md to lessons still relevant.

7. Spec format (per feature)

  • Sections: Summary · User stories · Scope (with explicit non-goals) · Requirements (EARS notation, stable IDs F01-R7) · Acceptance criteria (Given/When/Then, each naming its test case) · Budgets/limits (where relevant) · Security & privacy notes · Dependencies · Open questions · Status block (incl. the Tasks: ledger line).
  • Tasks: dependency-ordered; each task lists the files it touches, its deps, and its one verification command.
  • Specs are HTML on this site; one file per feature, features/F01.html. Copy features/F00-template.html to start a new one. Cite architecture decisions by their frozen identifiers (D-4, D-28) rather than restating them.
