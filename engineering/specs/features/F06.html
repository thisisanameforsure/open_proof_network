F06 — Precheck service

POST /precheck and GET /precheck/<id> (D-28, D-35): the gate's mechanical steps run on a submitted bundle as a GitHub Actions job in a scratch repository, returning structured diagnostics and a service-signed attestation. Also the account-free identity proof of D-19.

1. Summary

Precheck is the write tool D-28 says ships first: it is how an agent learns of a failure before CI does, and the signed attestation it returns is what the authoritative gate requires attached. F06 runs it without a machine of its own: the api pushes the bundle to a branch of a scratch repo, dispatches a workflow that runs the same gate code in the same container image (D-4: three invocations, one codebase), and serves the result when asked. Because the tutorial node is the D-19 identity proof, a precheck of it may be requested without a token, and a passing one can be exchanged for a write token under a pseudonym. Cites: D-4, D-19, D-24, D-27, D-28, D-34, D-35.

2. User stories

  • As an agent, I want to submit my proof and get the first failing step with a diagnostic in minutes, so I can fix it without a human reading CI logs.
  • As a person with no GitHub account, I want my agent to prove the tutorial node and receive a write token, so I can contribute anonymously (D-19).
  • As the founder, I want strangers' Lean to run only on GitHub's throwaway VMs, so nothing I administer executes their code (D-24).

3. Scope

In: bundle validation; job records; the scratch repo with its workflow and signing key; dispatch, polling and artifact retrieval through the GitHost seam; both endpoints; the anonymous tutorial flow and tutorial-proof tokens; rate limits; result retention and branch cleanup; deployment and a real end-to-end run as evidence.

Non-goals:

  • Opening the submission PR — F07 (POST /submissions consumes a precheck result).
  • Warm-cache precheck on dedicated infrastructure — a Stage 0 measurement (Stages, v3.9) decides whether it is ever needed.
  • --record precheck records into attempts/precheck/ (D-34) — F07, since it is a graph write.

F06-R3When a job is accepted, the system shall create a job record {id, node, statement hash, graph commit at main, bundle hash, identity or nonce, state queued, created}, push a branch job/<id> to the scratch repo containing job.json and the bundle files, and dispatch the scratch repo's precheck workflow with the job id, all through the GitHost seam using the GitHub App installation token.
F06-R4The scratch workflow shall check out the graph at the recorded commit and this repo at the commit the graph's gate-spec.json pins, apply the bundle, run gate steps 1–2 and 4–8 inside the step-3 image with the graph's caps, sign the resulting attestation with the precheck key (C8 item 2) as kind service, and upload result.json {verdict, steps, diagnostics, attestation} as a workflow artifact; the job shall hold no secret other than that key and no write permission.
F06-R5When GET /precheck/<id> is called, the system shall return the job record; while not terminal it shall look up the workflow run by job id and, if complete, download the artifact, verify the attestation's signature against the committed precheck public key, store the result, and mark the job done; if the run failed or produced no artifact, mark it error with the run URL; results shall be served for 30 days, then expired.
F06-R6The returned attestation shall validate against attestation/v1 (or the current version), carry runner: hosted, signature.kind: service, the graph commit and the bundle hash, and shall be the document a submission attaches (F00-Q1).
F06-R7When POST /tokens receives proof kind tutorial {job_id, nonce} with a pseudonym and DCO acceptance, the system shall verify the job is done with verdict pass, was created without a token, its nonce matches and is unconsumed, then issue a token as in F05-R4 with proof kind tutorial and consume the nonce; every other condition responds 400 without leaking which one.
F06-R8The system shall limit authenticated prechecks per identity (invited-run default 40 per hour) and publish the limit in rate_limit_policy.
F06-R9A scheduled workflow in the scratch repo shall delete job branches older than 7 days; the scratch repo's contents are disposable and never read by the gate (D-35: operational, never evidentiary).
F06-R10If dispatch fails, the system shall mark the job error with the cause and respond 502 to the submitter; a bundle shall never be silently dropped (C7).

6. Budgets / limits

  • Tutorial node precheck under 5 min end to end on a cold hosted runner; Mathlib-pinned graphs under 10 min with the cache download. Both measured and recorded in evidence as the Stage 0 latency series.
  • Bundle 512 KiB; result 1 MiB; diagnostics truncated with a marker.

7. Security & privacy notes

  • Contributor Lean runs only on the hosted runner inside the step-3 image (C9, D-4 v3.9). The scratch repo's workflow has permissions: {} plus the artifact upload, and the precheck key is its only secret (C8 item 2).
  • The scratch repo is public (hosted runners are free for public repos) so bundles are public the moment they are pushed; D-26 makes public attempts the default, and the api says so in its response.
  • Job branches carry contributor code; the 7-day cleanup bounds retention. Results in the store hold diagnostics, which may quote contributor text: served as data (D-28).
  • Anonymous precheck is the one unauthenticated write-shaped route; it is bounded by address rate limits and by being restricted to the tutorial node.

8. Dependencies

  • F05 (required): api foundation, tokens, rate limits. F00: pipeline, image, attestation, signer. F02 (soft): waiver path rule.
  • Packages: cryptography (pinned 50.0.1), approved by the founder 2026-09-09 — Q5. Two uses, both of them "do not roll your own": RS256 for the GitHub App JWT (R3), and Ed25519 for verifying a downloaded precheck attestation (R5) without the ssh-keygen binary the Lambda image does not carry. Nothing else in the repo may reach for it: the gate keeps signing through opn_gate.signer (C8).
  • Scratch repo open_proof_network_precheck under the founder's account, public, with the GitHub App installed and the precheck key as its Actions secret.

9. Open questions / judgment calls

IDCall made — for review
F06-Q1A third repository — decided in D-35 (v3.11): the scratch repo holds nothing but disposable job branches and one workflow, has no authority, and the gate never reads it. No deviation.
F06-Q2Anonymous precheck is the single carve-out from "writes are token-authenticated" (D-28). Without it the D-19 v3.9 account-free proof is circular. Scoped to the tutorial node, address-limited, and returns nothing a token would not.
F06-Q3Polling instead of webhooks. A GitHub webhook would need an inbound secret and endpoint; polling on read keeps the service stateless and the secret list at C8's five items.
F06-Q4The nonce is not inside the signed attestation. The service verifies tutorial proofs against its own job record, so the attestation shape stays the gate's, with no identity field for the gate to ignore.
F06-Q5T3 needs RSA and the standard library has none. Authenticating as the GitHub App (R3) means an RS256 JWT signed with the App's private key. The options are a new dependency (cryptography, what PyJWT uses) or hand-written PKCS#1 v1.5 signing. C5 dislikes the first; "never roll your own crypto" forbids the second more strongly, so the proposal was cryptography, pinned and locked. Decided by the founder 2026-09-09: approved, pinned at 50.0.1 (§8). The packaging note is discharged in engineering/evidence/F06/task-3.txt — the aarch64 wheel resolves with its compiled extensions, 23 MiB unzipped against a 250 MiB limit, and the deploy workflow needs no change.
F06-Q6The api verifies signatures without ssh-keygen. The gate signs by shelling out to OpenSSH, which is always present where the gate runs; the Lambda image has no such binary, so R5's verification would have failed only in production. api/opn_api/sshsig.py parses the SSHSIG wire format and hands the bytes to cryptography's Ed25519 verify — format parsing here, no primitive. Its tests check it against real ssh-keygen output, never against a fixture this repo generated, so the two halves of the one seam cannot drift apart.
F06-Q7The workflow is dispatched at the job branch, not at main. The branch is main's tree plus job.json and bundle/, so the workflow that runs is the scratch repository's own — the api pushes no runnable code — and the run is then findable by ?branch=job/<id>. Dispatching at main would have needed a run-name convention to tell one job's run from another's, which is a second thing to keep in step.
F06-Q8The tutorial exchange advances the job itself. R7 requires the job to be done, and only GET /precheck/<id> moves it there (Q3). Rather than make an agent remember to poll before spending its nonce, POST /tokens calls the same precheck.advance. No new exposure — the GET is itself unauthenticated (R5) — and one fewer step to get wrong.
F06-Q9The tutorial exchange is address-limited by the token-start counter. POST /tokens has no identity to limit by, and the tutorial branch is reachable without one. It shares OPN_API_TOKEN_STARTS_PER_DAY (default 10) with GET /auth/github/start because both answer the same question: how many identities may one address try to mint in a day. The honest flow costs one.
F06-Q10A job pins frontier.json's rendered_from, not the graph's current main. R3 says "the graph commit at main"; the two differ whenever main has moved without the products being re-rendered, which is the live graph's state today. rendered_from is the stronger choice: the whole of the service's view of the graph — which nodes exist, their statement hashes, whether one is the tutorial node — comes from the rendered products, so pinning the commit those were rendered from keeps the job consistent with the facts it was validated against. Reading main's head would pin a commit the service cannot see the contents of. Staleness is bounded where D-34 already bounds it, by precheck_max_age_s.
F06-Q11A precheck that cannot pass is refused before it costs anything. The Euclid tester prechecked the blocked root twice, and each hosted run ended at step 4 dep-unproved. node_facts now reads the graph first and carries status, cause and dependencies, and check_open refuses only blocked: a refuted or superseded node stays precheckable because a proof there fails on its own terms, and a proved node stays precheckable for the tutorial path (D-19). The refusal comes before authentication, so a caller with no token learns why rather than getting a 401. Still open: the same call at the top of POST /submissions, so a job minted before a node turned blocked cannot open a pull request the gate will fail; api/opn_api/submissions.py is held by another session's uncommitted work. Decided 2026-09-14 in T6.
F06-Q12A job is pinned to the commit its node was found at (T7, 2026-09-20). Q10 pins a job to frontier.json's rendered_from. In the 2026-09-19 primes run a precheck for a freshly merged variant was accepted, ran at the commit before the merge, and failed step 2 layout-missing, "missing required file META.yaml, Statement.lean", naming the contributor's bundle as the thing at fault. Cause: F05-T10's freshness generation marks every cached product stale when info.json moves, but info.json is itself revalidated once per window, and a product this process has never read has no cache entry to be stale: a new target's graph.json is fetched new while frontier.json is still inside its window, so the node is found in the new products and the job pinned to the old commit. The post-merge job writes every product in one commit and each carries the commit it was rendered from (checked on the live graph: every graph.json and the frontier name the same one), so the job is pinned to the rendered_from of the target's own graph.json, the document the node was found in, and to the frontier's only when that names none or the node was served from its frontier entry alone. graph-unrendered is still the answer when neither names a commit (C7). Q10's reason stands: the network pin is read from the pinned commit, and any rendered commit carries one. Reversal: the argument to rendered_from.
F06-Q13A precheck that cannot pass yet is refused at once, and says what it waits for (T8, 2026-09-21). A job runs at the commit the products were rendered from (Q10, Q12), not at main, and the three calibration testers paid for the gap twice. A partial citing an annex whose pull request was still open was accepted and failed annex-uncited minutes later; after the annex merged a second job, pinned to the render from before the merge, failed the same way. And for three minutes after a witness merged, every precheck on the hole said node-blocked and told the contributor to submit the witness they had just merged. Both are now answered before any job exists: 409 annex-pending naming the pull request, 409 products-pending with Retry-After for an annex or a witness that is on main and not yet rendered, 400 annex-unknown for a hash nobody submitted. The claim route gives the witness case the same answer. Judgment: both checks read the tree at the two commits rather than the submission store: a merged annex is on main whoever opened it, and a finished record leaves the open list, so the store could not have said "merged, not rendered". The store is asked one thing, whether an annex pull request is open on this node. A malformed citation is left to the gate, which names the line; an unreadable host refuses nothing (C7). Reversal: check_cited_annex and witness_awaits_render, one call each.
