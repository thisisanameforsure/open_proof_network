F17 — Prover adapters: sorry in, proof out

A single-file, standard-library client, opn-prove, that turns a node into the one self-contained Lean file an automated prover expects, turns the prover's answer back into a submission the gate will accept, and turns a failure into a postmortem. It has a generic backend for any command and presets for hosted and self-run provers. Its test oracle is the gate itself.

1. Summary

Most proving systems do not browse a frontier or read a guide. They take a Lean file with sorry and return a filled one (the research doc, part 2). The network has no path from a node to such a file and back. The self-contained file already exists inside the service, where POST /check inlines a node's Defs and own Context before forwarding it to AXLE (F13-T11, T12), but only as a step on the way to a check. Nothing a contributor holds produces it. On the way back, a prover's answer typically:

  • adds import Mathlib;
  • adds set_option lines;
  • adds helper lemmas before the theorem;
  • arrives wrapped in a Markdown fence.

Each of these fails step 2's proof-is-statement rule (F00-R19), because a proof cannot add an import.

This feature ships opn-prove, one Python file with no dependencies beyond the standard library, delivered from the site because contributors clone only the graph (AGENTS.md). It has five subcommands:

  • export writes the self-contained problem file from a graph clone.
  • run hands the file to a backend.
  • import normalises the answer into Proof.lean or a partial, in the shape step 2 admits, or refuses with the gate's own diagnostic.
  • check and submit call the existing /check, /precheck and /submissions routes.
  • postmortem writes a D-13 record when the prover fails.

A backend is a command that reads a file path and writes a file. Named presets are only defaults for such a command (D-1: no prover is blessed).

It closes the gap F15's hold names. The steward policy switch waits "until a prover harness exists and outside provers can be invited" (F15 status, 2026-09-17).

Not here: coding-agent connectors (F16); orchestrating harnesses and blueprint import or export (the research doc, part 3, waits for a user who asks); running any prover on the network's infrastructure. The contributor runs the prover. The network runs only its gate (C9).

2. User stories

  • As someone with Aristotle access or a local open-weight prover, I want one command that gives my prover a node and gives the network its answer, so that I can point my compute at the frontier without learning the graph's layout.
  • As that person, when my prover fails, I want the failure recorded as a postmortem with the budget I spent, so that the next prover does not repeat it (D-13).
  • As the owner, I want to know from a test, not from a live refusal, that what import writes passes step 2, and that what export writes elaborates at the pin.

3. Scope

In:

  • The single-file client: export, run, import, check, submit and postmortem.
  • The generic command backend, and presets for the provers the research doc names (Q2).
  • A corpus of realistic prover answers used as fixtures.
  • Delivery through the site with a sha256 manifest.
  • The guide section, run by the walkthrough runner.
  • One recorded live run per preset.

Non-goals:

  • Hosting or paying for a prover. The network runs none (C9).
  • Changing step 2's rule to accept helper lemmas or extra imports. If the corpus shows that provers need it, it is a D-4 question for the owner (Q4).
  • Choosing nodes for the user. export takes a node id. Frontier filters stay the agent's or the person's (D-25).
  • New routes or tools (D-28, D-35).

F17-R1opn-prove shall be one file, api/clients/prove/opn_prove.py, importing only the Python standard library, and shall run on the oldest Python the research finds hobbyist provers ship with (Q3).
F17-R2When given export --graph <clone> --node <id>, it shall write problem.lean: the node's statement with its Defs and own Context inlined in dependency order. The file shall be byte-identical to what POST /check forwards for the same statement text (the F10-Q7 precedent: two builders of one document produce the same bytes). A comment header shall name the node, the pinned Lean toolchain and the Mathlib commit. With --project, it shall instead write a minimal Lake project: lean-toolchain and a lakefile pinning the graph's Mathlib commit, plus the same file. Aristotle takes a project directory, not a file, and never uploads Mathlib (research, part 2).
F17-R3When given run --backend command -- <argv>, it shall run the argv with the problem path and an output path substituted. It shall enforce a wall-clock cap from its own config (C6), and shall record the backend name, the argv's first word, the exit status and the elapsed time for tooling and for any postmortem.
F17-R4When given import --node <id> <answer>, it shall:
  1. extract the theorem's body from the answer, whether it is a whole file, a file in a Markdown fence, or a bare tactic block;
  2. drop the header lines the statement already has;
  3. write Proof.lean as the statement's prefix plus that body.
If the answer changes the signature, adds an import the statement lacks, or still contains sorry, it shall write nothing and exit non-zero, naming the diagnostic paths.check_proof_is_statement would give.
F17-R5If the answer's residual sorrys sit only in have … := sorry positions, import shall offer the partial path (D-12, F07) instead of refusing: attempts/<ts>-<pseudonym>-partial.lean in the shape the guide gives.
F17-R6If the answer defines helper lemmas, import shall place them in the body where Lean allows (have, or where clauses). If it cannot, it shall refuse and name the lemma, never silently drop it (C7; Q4).
F17-R7check, submit and postmortem shall call only existing routes (/check, /precheck, /submissions, /postmortems), with the token from OPN_TOKEN. submit shall fill tooling with harness: "opn-prove/<backend>" and the model the user names. The gate never reads either (F16-R12).
F17-R8When the backend exits without a usable answer, postmortem shall draft a D-13 record: failure_class from the import diagnostic or the backend's status, the budget from R3, and the prover's last message capped and demarcated as untrusted (D-28). The draft shall validate against the postmortem schema and shall not be sent without --send.
F17-R9The site shall serve the file at a stable path with its sha256 in the static manifest (the KaTeX precedent, F04-R10), and the guide shall show the download and the checksum check. The walkthrough runner shall execute the guide's commands against the fixture clone and the fake service with the stub backend.
F17-R11Where a preset's service publishes the toolchain it runs (Aristotle's GET /version), run shall read it before submitting and record it with the result. Where a service reports "complete with errors" (Aristotle's COMPLETE_WITH_ERRORS), import shall treat the answer as a candidate partial (R5), not as a failure.
F17-R10Before running a preset, run shall compare the problem's pinned Lean version with the version the preset declares it targets. On a mismatch it shall warn, naming both versions, and shall not refuse, because version drift is the prover's risk and not a gate rule.

5a. Why the corpus is the centre

Every refusal this client can meet lives in import, and every one of them has already been met live: a proof that adds an import (the 2026-09-12 log entry), a header that is not the statement's (2026-09-13), and a hole's printed type (2026-09-17). The corpus holds each prover's real answer shapes as captured files, dated and labelled by prover, and the gate's own function judges them. When a new prover or a new version produces a shape import does not handle, the captured answer becomes a corpus case first, red, and the fix follows. The live runs (AC10) exist to capture those answers.

6. Budgets / limits

  • Fast tier: under one second in total for the corpus and parity tests.
  • run's default cap is 30 minutes (config). A hosted prover's own queue time is outside it and recorded separately where the preset can see it.
  • Postmortem prover text is capped at the schema's detail length.

7. Security & privacy notes

  • The client runs on the contributor's machine and runs whatever backend they name. The network runs no prover and no contributor Lean outside the gate (C9).
  • OPN_TOKEN is read from the environment, never from a flag (shell history) and never written to a file. A prover's API key is the prover's concern, and the client never reads it.
  • Exporting a node sends nothing anywhere. What the backend sends to a hosted prover is between the contributor and that service. The guide says so plainly, because a statement is public anyway, but a partial proof in progress may not be.
  • The served file is checksummed in the manifest, and the guide shows the check, so a tampered bucket is detectable.

8. Dependencies

  • F13 (required): inline_defs and forwarded_text, the parity reference, and /check.
  • F00 (required): paths.check_proof_is_statement, the oracle.
  • F07 (required): the partial path for R5.
  • F04 (required): the static manifest and the Docs page.
  • F16 (soft): the harness marker and the runner's three states, reused for AC10.
  • Packages: none, in the client or in uv.lock.

9. Open questions / judgment calls

IDCall made — for review
F17-Q1export composes the file client-side from the clone, rather than asking /check to echo what it forwards. Everything the client needs is plain files in the clone, which is the bijection rule's spirit (D-28). The cost is a second builder, held to the first by AC2.
F17-Q2Two presets, from the research doc's part 2:
  • aristotle: the only hosted prover an outsider can call today, through the aristotle submit … --project-dir … --wait CLI of aristotlelib 2.1.0. The contributor installs it; we never import it.
  • whole-file: the one prompt DeepSeek-Prover-V2, Goedel-Prover-V2 and Pythagoras-Prover share, sent to any OpenAI-compatible endpoint the contributor runs (vLLM, for example) through urllib.
Not presets:
  • step-level provers (BFS-Prover-V2), which need a search driver;
  • Seed-Prover and AlphaProof, which have no public access;
  • Leanstral's hosted API, which Mistral says retires on 2026-09-30 (unverified).
A preset is argv defaults plus a declared Lean version, never code specific to one prover. That keeps D-1 intact: the generic backend is the real interface. The whole-file preset ships only if AC12 shows its models' output survives the Lean 4.9 to 4.33.1 gap often enough to be worth a contributor's GPU.
F17-Q3The oldest supported Python is set from the research (what the prover repositories pin). A CI job runs the client's tests under it with uv run --python <that>. That fetches an interpreter, so it is a network-marked job, not part of make verify.
F17-Q4For the owner, if the corpus shows it. If captured answers routinely need top-level helper lemmas that cannot be moved into the body, the honest fix is a D-4 amendment letting Proof.lean carry declarations between the header and the theorem. Not built here. The corpus supplies the evidence.
F17-Q6For the owner. A submission certifies the DCO (D-19). Whether Aristotle's terms let a user submit its output under that certification could not be read: the site was unreachable from the research sandbox. The aristotle preset waits for the owner to read the terms. The generic backend does not, because what a contributor runs is their own certification.
F17-Q7The fast inner loop is /check, which forwards to AXLE's hosted lean-4.33.1. The alternative is a local checker, and the research found that none pins cleanly to the graph today: the community REPL has tags v4.33.0 and v4.34.0 and no v4.33.1, Kimina Lean Server's version defaults need an override, and LeanInteract stops at 4.32. AXLE's Mathlib revision can differ from the graph's pin. F13 already publishes whether the mapping is exact, and check prints that line.
F17-Q5Delivery is a file on the site, not a PyPI package. A package would be a publishing credential, and so a new C8 door, for a file of a few hundred lines. Revisit if people ask for pipx install.
