F13 — Fast check

A second-scale, non-authoritative Lean check for contributors and their harnesses: the network forwards Lean text to a named hosted checker matched to the target's pinned Mathlib, adds the warnings where the gate would disagree, logs every call, and publishes which checker serves which pin.

1. Summary

AI provers iterate on compiler feedback: tens of checks per attempt, each expected in about a second, with errors and goal states (surveyed 2026-09-13: Goedel-Prover-V2 and Seed-Prover 1.5 gain most of their accuracy from error-message rounds, and AXLE's own measurements put a warm Mathlib check near one second). The network's only check today is the signed precheck, minutes per job and rate-limited, which is right for its purpose (D-4's attached attestation) and wrong for an inner loop. F13 adds POST /check and its MCP tool check_lean: the service resolves the target's Mathlib pin to a hosted environment on AXLE (Axiom Math's public Lean engine), lints the text for the three ways a checker pass still fails the gate, forwards it, and returns the checker's answer verbatim beside the lint and an explicit authoritative: false. Every call is logged by its metadata and content hash. The pin policy that keeps targets on hosted environments is written down (a Mathlib release tag, matching the Formal Conjectures registry at intake), and the mapping from pin to environment is network configuration served as GET /hosted-checkers.json and shown on the target page and, once the endpoint is live, in the guide. This required decisions v3.14 (D-4, D-28, D-35) and constitution v2 (C9), because the network had promised that no contributor Lean is ever elaborated outside the gate's sandbox. Cites: D-1, D-4, D-7, D-19, D-28, D-35, D-36.

2. User stories

  • As an agent working an Erdős node, I want a check that answers in about a second with line and column errors and the goal at each failure, so I can iterate before spending a precheck.
  • As an agent, I want to be told when the checker's pass would still fail the gate (a helper lemma above the theorem, a changed import, a leftover sorry), so a green fast check does not become a red precheck.
  • As a curator importing a new wave of registry statements, I want the pin policy and the checker mapping to say, before I pin, whether contributors will have a hosted checker.
  • As the gate owner, I want every call logged, so abuse, load and harness behaviour are visible without keeping anyone's unmerged work.

3. Scope

In: the pin-tag rule on gate/mathlib-pins.txt; the gate/hosted-checkers.yaml mapping; the AXLE client seam and its fake; POST /check with lint, limits and a concurrency cap; the call log and GET /checks/<id>; GET /hosted-checkers.json (Q12); the target page line; the guide section; the MCP tool check_lean; a network-tier smoke.

Non-goals:

  • A checker the network runs itself on the gate image, for pins no hosted service carries (F-later; D-35's rule on administered machines would bind it).
  • Keeping the checked Lean text. Decided 2026-09-14: the log keeps metadata and a hash only (Q3).
  • Relaxing F00-R19 so helper lemmas above the theorem are accepted; F13 only warns.
  • Watching the registry's Mathlib bumps; F12's drift watcher already flags an edited statement.
  • Any change to the gate. opn_gate helpers are imported for the lint; no step reads anything F13 writes (D-1).

4. Requirements

EARS notation, stable IDs.

IDRequirement (EARS)
F13-R1The system shall pin each new Mathlib-based graph to a Mathlib release tag, chosen at intake to match the tag the Formal Conjectures registry builds against, and each line of gate/mathlib-pins.txt shall name that tag in a trailing comment (D-7 unchanged: a graph keeps its pin for life).
F13-R2The system shall keep gate/hosted-checkers.yaml (hosted-checkers/v1) with exactly one entry per pinned sha: the tag, the hosted environment or null, whether it is exact, and a note saying what differs when it is not.
F13-R3When POST /check receives {target_id, node_id?, content, mode ∈ {check, verify}}, the system shall resolve the target's mathlib_sha from its gate-spec, map it to an environment, and forward the content to AXLE's check, or in verify mode to verify_proof with the node's Statement.lean as the formal statement.
F13-R4Before forwarding, the system shall lint the content with the gate's own parsers and return named warnings, never refusals: imports-differ when the header is not the statement's, helper-declarations when anything but the statement's theorem is declared, sorry-present when a sorry token remains.
F13-R5When the node's statement imports Defs.* modules, the system shall inline those definitions' sources ahead of the content before forwarding, because the hosted checker imports only Mathlib, and shall say so in the response.
F13-R6The system shall answer {authoritative: false, service, environment, exact, lint, inlined_defs, result: the checker's body verbatim, log_id}, and shall never accept a check answer where a precheck attestation is required (D-4 v3.14).
F13-R7If the pin maps to no environment, the content exceeds the size limit, or the checker is unreachable, then the system shall refuse with no-hosted-environment, content-too-large or upstream-unavailable and log the refusal.
F13-R8The system shall rate-limit checks at the identity layer (D-19, D-28): per identity per hour when a token is presented, per source address per day otherwise, and shall cap in-flight calls to the hosted service per process at a configured concurrency, refusing checker-busy when no slot frees within the call budget (Q8).
F13-R9The system shall log every call that passes the body's shape and the caller's limit (Q11) as a check-log record in the operational store: id, time, caller (identity id, or a keyed hash of the source address), target, node, environment, mode, content SHA-256 and size, outcome, error count, lint codes, the checker's request id, upstream status and latency; it shall never store the content (C9 v2, Q3).
F13-R10When GET /checks/<id> is called by the identity that made the call, the system shall return that record; any other caller shall get not-found.
F13-R11amended 2026-09-14, Q12 The system shall publish the mapping at GET /hosted-checkers.json — every pin's environment and exactness and every listed target's pin — show the environment and its exactness on each target page, and, once POST /check is deployed, document the endpoint in the graph's AGENTS.md, naming AXLE as a third party, the precheck as the only verdict, and the lint's three gaps (T8).
F13-R12The system shall expose check_lean on the MCP server as the one tool over POST /check (D-28, D-35 v3.14), with the same arguments, limits and log.

6. Budgets / limits

  • Measured 2026-09-14, keyless, from the laptop: about 0.8 s per call round trip, 57–81 ms of execution on AXLE; Mathlib is preloaded there, so the budget is the network hop.
  • Defaults (config, C6): OPN_API_CHECKS_PER_HOUR 600 per identity, OPN_API_ANONYMOUS_CHECKS_PER_DAY 200 per address, OPN_API_CHECK_MAX_BYTES 200 000, OPN_API_CHECK_CONCURRENCY 8 (AXLE allows 10 concurrent keyless requests), OPN_API_CHECK_TIMEOUT_S 60. Provisional until the smoke and the first week's log say otherwise.
  • Lambda's own timeout bounds a call; a verify of a large proof may approach it (Q6).

7. Security & privacy notes

  • Contributor Lean leaves the network for a third party's sandbox. The network elaborates none of it (C9 v2, D-4 v3.14) and states in the guide that check text is sent to AXLE.
  • The answer is untrusted data from a third party; it is returned, never parsed into any record, and never reaches a page.
  • The log keeps no text. The caller is an identity id or a keyed hash of the source address, keyed with the api's existing token-signing secret, so no new secret is added (Q4).
  • No AXLE key at Stage 0 (keyless limits suffice). A key, when needed, is a Parameter Store SecureString read at startup, and C8's inventory gains the line in the same commit (Q5).
  • The lint imports opn_gate.layout and opn_gate.steps.artifact, which shell out to nothing (2026-09-10 log: ask what binary a gate helper assumes).

IDCall made — for review
F13-Q1DECIDED 2026-09-14 (Mike): delegate, and amend the decisions. D-4 said a contributor's Lean is never elaborated outside the gate's sandbox and D-35 that strangers' Lean runs only where nobody administers the machine; a wrapper forwarding to AXLE breaks both as written. The alternatives were a client-side wrapper that posts its own log (no amendment, but only cooperating clients are logged) and shipping only the mapping. Decisions v3.14 amended D-4 and D-35 and added the D-28 and D-35 rows for check_lean; constitution v2 amended C9. PROTOCOL_VERSION and the file name stay, as for v3.13.
F13-Q2DECIDED 2026-09-14 (Mike): anonymous calls under an address limit, a token raises it. Mirrors precheck, and lets a first-time agent iterate before it can mint a token (the MCP bootstrap gap, F09-T6).
F13-Q3DECIDED 2026-09-14 (Mike): no text in the log. Mike first chose to keep the Lean text; that contradicts D-36's opt-in rule for precheck records ("the value is theirs to donate … without turning the gate into a telemetry sink") and D-13's no-transcript stance, and when shown the conflict he dropped it, with the retention question it raised. Metadata records carry no expiry.
F13-Q4The anonymous caller is hashed with the token-signing secret rather than a new salt, so C8 gains no door; rotating that secret re-keys the hashes, which only splits an address's history.
F13-Q5AXLE is named, not abstracted: service: axle is the only value the mapping accepts. A second service is a schema version, not a flag, because the lint and the response shape are AXLE's.
F13-Q6Mathlib v4.33.1 maps to lean-4.33.0 with exact: false: the two Mathlib tags differ by one commit, a toolchain bump. A proof that uses something only the patch changed would pass the checker and fail the gate; the lint cannot see that, and the precheck remains the verdict.
F13-Q7R1 turns D-7's "new graphs pin latest" into "the latest release tag the registry builds against". This reads D-7 rather than overturning it: the registry has bumped on release tags only (v4.28.1 … v4.33.1, 2026-08-23), and a master-head pin would never match a hosted environment.
F13-Q8The in-flight cap is a per-process semaphore (T3). On Lambda each container serves one request at a time, so there the real cap on calls to AXLE is the function's own concurrency; the semaphore bounds the local runner and any threaded host. A global cap would need a lease in the store or reserved concurrency on the function; neither is built until T7's smoke or the first week's log shows AXLE refusing us (429s appear in the log as upstream-unavailable with their status).
F13-Q9A Mathlib-free graph is refused no-hosted-environment, as R7 reads. This includes the tutorial node, the first node an agent meets. Every hosted environment imports all of Mathlib, and a core-only statement is not guaranteed to mean the same under it (names can collide), so forwarding it would answer a different question. The alternative, an entry keyed by toolchain for core-only graphs, is one mapping line if Mike wants the tutorial fast-checkable.
F13-Q10POST /check refuses an unknown top-level key (unknown-field) from its first commit, which finding 5 asks of every write route. It first did so in its own parser, with the finding's strict expected failure marked per route so its pass was not an XPASS; F05-T8 landed the same day with identity.body_fields(request, accepted) refusing for every route, so on the merge the route passes its four keys there, its own check went, and /check is one plain row in the finding's table.
F13-Q11What is logged (T4): every call that passes the body's shape and the caller's limit, answered or refused, including target-unknown, no-hosted-environment, checker-busy and upstream-unavailable. A malformed body, a bad token or a spent limit is left to the access log line, which every request already writes: logging those would let anyone fill the store with records at no cost, and none of them reached the checker. A record is written once, carries no expiry (Q3), and a store failure is logged and never fails the check (C7), so its log_id is then null. GET /checks/<id> needs a token and answers the owner alone; an anonymous call's record is readable by no one through the service, only by the gate owner in the table.
F13-Q12R11 first put the mapping into info.json and server_info. Priced at T5, that was wrong twice: info/v1 is additionalProperties: false and hash-pinned (D-34), so a field meant info/v2, a regenerated golden in every product test and a graph re-pin; and info.json is the graph's product, while the mapping is network configuration that D-35 keeps out of the graph. So the service serves it at GET /hosted-checkers.json, an open read with no D-35 row (like /dco.json), check_lean's own answer already names the environment, and the site reads the same file at build time. One loader, opn_gate.hosted, serves the api and the site; no gate step imports it (D-1). The guide section moved to T8, because the graph's copy of AGENTS.md must equal the tested one byte for byte and a section describing an endpoint that is not yet deployed would send agents to a 404.
