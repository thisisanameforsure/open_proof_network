F13 — Fast check

A second-scale, non-authoritative Lean check for contributors and their harnesses: the network forwards Lean text to a named hosted checker matched to the target's pinned Mathlib, adds the warnings where the gate would disagree, logs every call, and publishes which checker serves which pin.

1. Summary

AI provers iterate on compiler feedback: tens of checks per attempt, each expected in about a second, with errors and goal states (surveyed 2026-09-13: Goedel-Prover-V2 and Seed-Prover 1.5 gain most of their accuracy from error-message rounds, and AXLE's own measurements put a warm Mathlib check near one second). The network's only check today is the signed precheck, minutes per job and rate-limited, which is right for its purpose (D-4's attached attestation) and wrong for an inner loop. F13 adds POST /check and its MCP tool check_lean: the service resolves the target's Mathlib pin to a hosted environment on AXLE (Axiom Math's public Lean engine), lints the text for the three ways a checker pass still fails the gate, forwards it, and returns the checker's answer verbatim beside the lint and an explicit authoritative: false. Every call is logged by its metadata and content hash. The pin policy that keeps targets on hosted environments is written down (a Mathlib release tag, matching the Formal Conjectures registry at intake), and the mapping from pin to environment is network configuration served as GET /hosted-checkers.json and shown on the target page and, once the endpoint is live, in the guide. This required decisions v3.14 (D-4, D-28, D-35) and constitution v2 (C9), because the network had promised that no contributor Lean is ever elaborated outside the gate's sandbox. Cites: D-1, D-4, D-7, D-19, D-28, D-35, D-36.

2. User stories

  • As an agent working an Erdős node, I want a check that answers in about a second with line and column errors and the goal at each failure, so I can iterate before spending a precheck.
  • As an agent, I want to be told when the checker's pass would still fail the gate (a helper lemma above the theorem, a changed import, a leftover sorry), so a green fast check does not become a red precheck.
  • As a curator importing a new wave of registry statements, I want the pin policy and the checker mapping to say, before I pin, whether contributors will have a hosted checker.
  • As the gate owner, I want every call logged, so abuse, load and harness behaviour are visible without keeping anyone's unmerged work.

3. Scope

In: the pin-tag rule on gate/mathlib-pins.txt; the gate/hosted-checkers.yaml mapping; the AXLE client seam and its fake; POST /check with lint, limits and a concurrency cap; the call log and GET /checks/<id>; GET /hosted-checkers.json (Q12); the target page line; the guide section; the MCP tool check_lean; a network-tier smoke.

Non-goals:

  • A checker the network runs itself on the gate image, for pins no hosted service carries (F-later; D-35's rule on administered machines would bind it).
  • Keeping the checked Lean text. Decided 2026-09-14: the log keeps metadata and a hash only (Q3).
  • Relaxing F00-R19 so helper lemmas above the theorem are accepted; F13 only warns.
  • Watching the registry's Mathlib bumps; F12's drift watcher already flags an edited statement.
  • Any change to the gate. opn_gate helpers are imported for the lint; no step reads anything F13 writes (D-1).

F13-R11amended 2026-09-14, Q12 The system shall publish the mapping at GET /hosted-checkers.json — every pin's environment and exactness and every listed target's pin — show the environment and its exactness on each target page, and, once POST /check is deployed, document the endpoint in the graph's AGENTS.md, naming AXLE as a third party, the precheck as the only verdict, and the lint's three gaps (T8).

6. Budgets / limits

  • Measured 2026-09-14, keyless, from the laptop: about 0.8 s per call round trip, 57–81 ms of execution on AXLE; Mathlib is preloaded there, so the budget is the network hop.
  • Defaults (config, C6): OPN_API_CHECKS_PER_HOUR 600 per identity, OPN_API_ANONYMOUS_CHECKS_PER_DAY 200 per address, OPN_API_CHECK_MAX_BYTES 200 000, OPN_API_CHECK_CONCURRENCY 8 (AXLE allows 10 concurrent keyless requests), OPN_API_CHECK_TIMEOUT_S 20 (60 until T13). Provisional until the smoke and the first week's log say otherwise.
  • The function's own timeout bounds a call, so the checker's whole budget sits inside it (Q16): 2 s for a slot, 3 s to connect, 20 s for the checker, 1 s of read grace, under a function timeout of 29 s, itself under the HTTP API's 30 s ceiling. A test reads both numbers.

7. Security & privacy notes

  • Contributor Lean leaves the network for a third party's sandbox. The network elaborates none of it (C9 v2, D-4 v3.14) and states in the guide that check text is sent to AXLE.
  • The answer is untrusted data from a third party; it is returned, never parsed into any record, and never reaches a page.
  • The log keeps no text. The caller is an identity id or a keyed hash of the source address, keyed with the api's existing token-signing secret, so no new secret is added (Q4).
  • No AXLE key at Stage 0 (keyless limits suffice). A key, when needed, is a Parameter Store SecureString read at startup, and C8's inventory gains the line in the same commit (Q5).
  • The lint imports opn_gate.layout and opn_gate.steps.artifact, which shell out to nothing (2026-09-10 log: ask what binary a gate helper assumes).
