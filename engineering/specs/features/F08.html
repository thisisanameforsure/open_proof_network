F08 — Proposals and admission

The graph grows from contributions (D-29): speculative crux nodes (D-14), labeled variants (D-30), witness completion for compiler-derived holes, revision requests (D-8), defect claims (D-16), and the thin curator operations — all admitted by the gate's statement-side checks, never by a person approving structure.

1. Summary

F08 adds the one gate mode that creates nodes — proposal — and the admission check behind it: layout, statement typechecks with body sorry, witness (F01), hazards (F02), context matches deps (F01), acyclicity (F03), and for variants the kernel-checked relation proof (D-30). It exposes POST /proposals/speculative and POST /proposals/variant (D-28's propose_speculative_node and propose_variant), the append-shaped POST /revision-requests and POST /defect-claims with D-16's pre-triage bounce, and the curator-only curator PR mode with three commands: revise (D-8), consolidate (D-29), and status records (abandon, dormancy; D-14, D-33). Statement authorship enters the ledger for admitted variants and speculative cruxes (D-19). Cites: D-3, D-8, D-9, D-13, D-14, D-16, D-18, D-19, D-21, D-28, D-29, D-30, D-33, D-35.

2. User stories

  • As a prover mid-attempt, I want to enter the crux my route hinges on as a speculative node, so an unfalsifiable idea becomes a typechecked object others can refute or prove (D-14).
  • As a prover who can only prove something weaker, I want to propose a labeled variant with its relation proof, so weakening is legal and visible (D-30).
  • As a contributor who thinks a statement is defective, I want to file evidence and have a curator version it, without anyone editing the statement (D-8).
  • As the curator, I want revision, consolidation and abandonment to be commands that open signed PRs, so my authority is thin, mechanical and on the record (D-29).

3. Scope

In: the admission check as a command and as gate mode proposal; node-directory scaffolding from a statement and witness; variant layout with Relation.lean; witness completion for compiler-derived holes; the four proposal/request endpoints; defect-claim pre-triage as a CI check; curators.json and the curator mode; curator commands revise, consolidate, status; missing-library aggregation report; ledger statement line; schemas revision-request/v1, defect-claim/v1, node-status/v1 (F03) usage.

Non-goals:

  • Adjudication of defect claims and revision requests (D-17), the rolling rejected-claim budget (D-16), canaries (D-11), reviewer assignment (D-15) — Stage 1.
  • Automatic prerequisite-node creation from missing-library postmortems — a report for the curator only (Q3).
  • Mechanical re-run of stale dependents after a revision (D-18) — Stage 1; F08 marks them stale.
  • Intake of targets (D-6) — F11.

F08-R5When POST /proposals/witness {node_id, witness} is received for a compiler-derived node with cause witness-missing, the system shall open a proposal PR adding only Witness.lean; admission shall run on the completed node and on pass the node becomes ready (F07-Q3); Witness.lean creation on such nodes is the one permitted addition to an existing node directory in proposal mode.
F08-R6When POST /revision-requests {node_id, evidence} is received, the system shall validate against revision-request/v1 {schema, node, contributor, defect_class, evidence: {text ≤ 2,000 chars, exhibit?: Lean file}}, write nodes/<id>/revisions/<ts>-<pseudonym>.yaml and open an append PR (F07-R9); an exhibit, if given, shall elaborate in the append gate or the PR fails.
F08-R7When POST /defect-claims {stmt_ref, class, line, exhibit} is received, the system shall bounce (400) unless class is in the defect taxonomy {missing-hypothesis, junk-value, vacuity, quantifier-scope, wrong-domain, definition-mismatch, strength-drift, other-with-exhibit}, line is an existing line of the referenced Statement.lean or defs/ file, and exhibit is a Lean file; the append gate shall repeat the same check as CI (D-16, D-35) and elaborate the exhibit; the record goes to nodes/<id>/defects/ or defs/defects/.
F08-R8partly built The graph repo shall carry curators.json {identities: [{pseudonym, github_login}]} owned by the founder; the gate shall classify a PR authored by a listed login that adds status records, a versioned node, or a consolidation record as mode curator, run admission on any new node directory, and merge on green plus one approving review by a different listed identity — waived while only one curator exists (D-22's founding-team waiver), recorded in the attestation. Built except the merge (F07-Q16) and the attestation record of the waiver, which is in the classification output instead (F08-Q9); a versioned node is classified but cannot yet validate (F08-Q10).
F08-R9The system shall provide opn-gate revise <node-id> --statement <file> --request <revision-file> that scaffolds <node-id>@v2 (next free version) with supersedes, copies witness and deps for the curator to adjust, writes a node-status/v1 record marking the old node superseded and each dependent stale with cause naming the revision, and opens a curator PR (D-8, D-18).
F08-R10The system shall provide opn-gate consolidate <keep> <drop> that refuses unless the two statements have equal statement hashes or elaborate to definitionally equal types, and otherwise writes a status record marking drop superseded by keep and opens a curator PR (D-29).
F08-R11The system shall provide opn-gate status <node-or-target> <abandoned|dormant|active> --cause <text> writing the corresponding record; a dormancy record shall name the D-25 starvation series values and the K and N in force, and shall fail if the target has had a merge within N days (D-33 condition a).
F08-R12The system shall provide opn-gate missing-library <target> that aggregates missing-library postmortems by normalized missing_lemmas string and lists those at or above the configured threshold (default 3) for the curator, without creating nodes (D-13).
F08-R13When a proposal PR merges, the post-merge job shall append a statement ledger entry for the proposer on variants and speculative cruxes only (D-19; never for holes, D-31), and shall regenerate products so the node appears in the frontier.

6. Budgets / limits

  • Admission under 5 min on a hosted runner for Mathlib-free nodes; proposals per identity per day: 40 (invited-run config default, published).
  • Node ids: <target>/<slug>, slug ≤ 64 chars; versions @v<n>.

7. Security & privacy notes

  • Admission elaborates contributor Lean: sandbox only (C9). Exhibits in defect claims and revision requests are Lean files and are elaborated under the same rules.
  • curators.json is the only role file at Stage 0 and is founder-owned; a change to it is a visible commit (D-22).
  • Proposal spam is bounded by identity-layer limits (D-19, D-29), never by review.

8. Dependencies

  • F07 (required, except T1 which F07-T4 needs): PR creation, modes, ledger. F02, F01, F03: the checks admission composes.
  • Packages: none new.

F08-Q1Relation.lean — in the D-3 layout since v3.11, variant nodes only, gate-checked at admission and immutable after. No deviation.
F08-Q2Speculative nodes are origin: authored with a speculative flag, since D-14 describes them as authored crux statements and F03's status model already publishes speculative. Reworded 2026-09-10 (F07-Q13): this call originally rested on D-3's origin set having no fourth value. It has one as of v3.12, but it is skeleton-hole, so the conclusion is unchanged and only the reason was stale.
F08-Q3Missing-library prerequisites are not auto-created — decided in D-13 (v3.11): above the threshold (config default 3) the aggregated lemma is surfaced to the curator, who proposes the node like anyone else. No deviation.
F08-Q4Defect taxonomy — enumerated in D-16 since v3.11: the eight classes R7 lists. No deviation.
F08-Q5Curator PRs need a second curator's approval per D-21's separation, waived while the founder is the only curator (D-22), with the waiver recorded per PR so the ledger shows it. Confirmed by Mike 2026-09-07.
F08-Q6A variant's label lives in Relation.lean, so a claim without a proof is not a node anyone can build. F03 already reads the label from the -- relation: line in that file, and F03's frontier publishes it from there. Keeping one home for it means labeled partial with no Relation.lean (AC5's first half) describes something that cannot exist: the label would have nowhere to live. The impossibility is enforced in the two places it can be — the scaffold refuses to build such a proposal, and admission refuses a Relation.lean that carries no label (relation-unlabelled) — and AC5 is met there. Decided 2026-09-10 in T1.
F08-Q7Admission's verdict is keyed by check name, not by D-4 step number. R1 asks for "a verdict in the F00 shape with the first failing check", and its eight checks are not D-4 steps: two of them (context, graph) are halves of steps, and one (relation) has no step at all. The document therefore carries checks: [{check, result, diagnostic}] and first_failing_check, mirroring the gate verdict field for field. Nothing consumes both, and forcing admission into 1–9 would have invented step numbers the protocol does not have. Decided 2026-09-10 in T1.
F08-Q8The pull request's author reaches the classifier as OPN_PR_AUTHOR, and the graph's gate.yml lands before the re-pin. R8 needs the host's one fact — who opened the pull request — and the natural shape is a classify --author flag, which exists. But a workflow may only use a flag the pinned commit understands (log, 2026-09-09), and the pin is af2f4e7, which predates T2: a flag would have failed every classification and so blocked every merge until the re-pin. The workflow therefore sets the environment variable, which the old pin ignores and the config module of the new one reads (C8's one door; the OPN_RUNNER precedent), reads every new classification field with a default, and runs the admission and curator steps only on values the old pin never emits. So the file is inert on the old pin and switches on at T6's re-pin, and it can be committed to the graph now rather than sitting uncommitted until then. Decided 2026-09-10 in T2.
F08-Q9The single-curator waiver is recorded in the classification output, not yet in an attestation. R8 says "recorded in the attestation", but a curator pull request that adds a status record builds no proof, and the post-merge job attests only the modes that do (Q11) — the same gap F07-Q17 names for appends. The classifier's output carries reviewers (the other listed identities, who alone may satisfy step 9 for a curator record) and review_waived: single-curator when there are none (D-22), and the workflow logs it on every run. Putting the waiver into a committed record needs the post-merge job to attest non-building merges, which is a schema question; it goes with R13's ledger line in T5. Raised 2026-09-10 in T2.
F08-Q10A versioned node is classified but cannot yet exist. R8's "versioned node" and R9's <node-id>@v2 follow D-8 and §6, so the path grammar accepts <slug>@v<n> and routes a directory so named to curator mode with admission. But meta/v2's id pattern, graph/v2's and frontier/v1's node ids all forbid @, so such a node fails admission at the layout check today. R9 therefore needs a schema version that admits the spelling, or a spelling the schemas admit — T5's call to price, not T2's to pre-empt (D-34: versioned, never edited; adding a schema regenerates every product golden). Raised 2026-09-10 in T2. Closed by Q16 the same day: the spelling is -v<n>.
F08-Q11The post-merge job classifies the merged diff and attests only the modes that build. Before T2 it ran the proof pipeline on whatever node the merge touched, which for a merged proposal — a node with no Proof.lean — fails, so the products would never regenerate and R13's "the node appears in the frontier" could not happen. It now asks the pinned classifier what merged: proof and partial re-derive and sign as before; every other mode goes straight to the products and the bot commit, whose verdict is pass because the merged diff passed the classifier's own checks. The same change stops an append on an unproved node from failing the job, which F07-R9 needed too. Decided 2026-09-10 in T2.
F08-Q12Three rules the requirements imply but do not state. (i) A proposal's own status record may only say speculative (Q2), since every other status is a curator's judgment; the check is proposal-status. (ii) Whether a hole's slot is still unfilled (R5) is a fact about the base commit, so the classifier reads the base's Witness.lean through git rather than trusting the head; with no base it refuses rather than guesses (witness-completion-unverified), and a witness that was already real is never replaced (witness-filled). (iii) A curator pull request may touch several nodes, because D-8's revision marks the old node superseded and each dependent stale in one change; the one-target rule still holds, and a plain new node in a curator pull request is a proposal in the wrong pull request (mode-mixed). Decided 2026-09-10 in T2.
F08-Q13The sandbox found a bug the real toolchain could not. R2's "inside the step-3 sandbox" was first exercised in T2 (admit --sandbox, test_admit_docker.py), and the relation check failed there while passing AC18 locally: it handed the metaprogram the root's Statement.lean from the graph tree, and the container holds only the node under admission and the work directory (F00-R12). Both statements are now read from their staged copies. Logged rather than hidden because it is the second time a check that passes every laptop tier fails in production (log, 2026-09-10, F06-Q6). Found 2026-09-10 in T2.
F08-Q14Four small calls in the proposal endpoints. (i) R3's id <target>/spec-<hash8> is the node's path; node ids are target-scoped slugs everywhere else (F00, F03), so the response carries node_id: spec-<hash8> and target_id separately, and a variant is variant-<hash8> by the same rule. (ii) AC8's "META has speculative: true" is read as Q2 decided: the flag is a status record inside the new directory, which F03 derives from, and the test asserts that. (iii) The service never elaborates (C9): a statement is checked for shape by the scaffold's parser and everything else is admission's; Lean files are capped at 64 KiB and deps at 20, F07 §6's numbers reused. (iv) The label of a variant's relation proof is written into Relation.lean by the scaffold (-- relation:, F03's line) so the service and a hand-written directory produce the same file; a proof that already names a different label is refused, and a related variant with a proof is refused because it would claim nothing the proof could prove (Q6). Decided 2026-09-10 in T3.
F08-Q15An exhibit is the append mode's one build, and it elaborates against the node it is about. R6 and R7 want an exhibit to "elaborate in the append gate", and F07-R9 gives appends no sandbox. Contributor Lean runs only in the sandbox (C9), so the classifier now reports needs_exhibits and the workflow runs one more command, opn-gate exhibits --sandbox, for that alone — nothing else about an append changes, and step 9 is still skipped. An exhibit about a node is elaborated as Nodes.«id».Exhibit<n> with the node's Statement.lean and Context.lean staged first, so it may import either (Q13's lesson applied in advance); an exhibit about a defs/ file is elaborated as a bare module against library imports alone, because compiling a target's defs/ tier is F11's, and the tutorial graph has none. Elaborating is all the gate asks: whether the exhibit shows what the record says is D-17's question. Two record details: a revision request's body carries defect_class beside evidence, since the schema requires the class and R6's {node_id, evidence} named no home for it; and a defect claim's stmt_ref is a bare node id or <target>/defs/<file>.lean on the wire, recorded as the node id or defs/<file>.lean under the target the record sits in, which is how the gate re-derives the referenced file from where the record is rather than from what it says. Decided 2026-09-10 in T4.
F08-Q16A revision is <id>-v<n>, and the fact that makes it one is supersedes in META. D-8 and D-19 write <node-id>@v2, and Q10 priced what that spelling costs: @ is outside the node-id alphabet of six hash-pinned schemas (meta, graph, frontier, targets-index, ledger, attestation), each of which would need a new version before a revision could be admitted, rendered, proved or credited. Read instead as the document's notation for "version 2 of the node" — the reading F03 already gave D-13's d13/v1 when it named the schema postmortem/v1 — the version rides inside the existing alphabet as -v<n>, the suffix is reserved (a proposal may not end in one, and only a curator adds a directory that does), and the only schema change is meta/v4's optional supersedes, which is the fact the products and the ledger read. Two consequences: graph.find_root sets aside superseded nodes and revisions of interior nodes before it requires the sink to be unique, so a revised interior node does not make the root ambiguous and a revised root becomes the root; and D-19's "a revision never re-mints paid credit" is a one-line check on supersedes. Proposed as a notation amendment to D-8 and D-19 rather than an overturn; reversible by one regex and the scaffold's slug check if the founder wants the @. Decided 2026-09-10 in T5.
F08-Q17The curator's commands write files and, with --branch, a commit; the pull request is the curator's own git act. R9–R11 say each command "opens a curator PR". The service opens pull requests as the App with the App's credentials (F07-R2); a command on the curator's machine has only the curator's, and the gate never holds them (C8). So each command writes the node directory or the status records, and --branch puts them on a branch in one commit and prints the git push and gh pr create that finish the job — which is also what makes the pull request the curator's, so R8's author check can see who filed it. Two smaller calls: consolidation's "elaborate to definitionally equal types" is asked of Lean without a new metaprogram, by elaborating the dropped statement with its sorry replaced by the kept theorem (the elaborator's isDefEq is the check), under a fresh declaration name because duplicates share one — the real toolchain found that, the fake could not; and dormancy's "last progress artifact" is the last commit on main touching the target's nodes, which is a merge or the bot's products commit, with the D-25 series (ready nodes, attempts per ready node, zero-attempt fraction) computed from the tree and written into the cause with the K and N in force, since gate-spec/v1 has no field for them and a new gate-spec version for two integers was not worth its churn. Decided 2026-09-10 in T5.
