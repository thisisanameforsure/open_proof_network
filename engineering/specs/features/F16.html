F16 — Harness connectors: coding agents

A tested connector for each coding agent a hobbyist is likely to use: its config snippet and pointer to the guide, proved by tests at four levels: the snippet parses, the tool surface passes the harness's known limits, the real harness binary connects, and a fresh agent in that harness completes a contribution. Built so that "harness-agnostic" (D-1) is a measured result.

1. Summary

D-1 says the gate cannot tell harnesses apart, and D-28 ships an MCP server "so any MCP-speaking agent (Claude Code, Codex, Gemini CLI, Cursor, custom harnesses) can participate in one tool call". The only harness the network has ever been exercised through is Claude, and most of that through hand-written JSON-RPC rather than a harness's own MCP configuration (session notes 2026-09-12 to 2026-09-23). The guide's only setup line is claude mcp add. D-1's claim has never been tested.

This feature adds a connector registry under the api (api/clients/): one entry per coding-agent harness, holding:

  • its config template
  • how it carries the bearer token
  • how it finds the contributor guide
  • its headless command
  • the known limits of its MCP client
  • the version last verified, with that version's evidence

The site's Docs page and a generated guide section render from it with the configured service URL. Most of the feature is its tests (§5a), which prove each connector at four levels, from a parse check that costs nothing to a fresh agent completing a contribution inside the real harness. A scheduled job repeats the cheap real-harness check against each harness's latest release, because these clients change month to month.

A connector is a client of the plain protocol and nothing else. It adds no route, no tool and no capability (D-28's bijection rule), sits outside the trust base with the MCP server, and is invisible to the gate. The harness a contributor names in tooling.harness stays declared and never verified (D-23), and no gate code may read it (R12).

Not here: adapters for automated provers that take a sorry and return a proof (Aristotle and self-run open-weight models), which are F17; import and export for orchestrating research harnesses, which waits for a user who asks (the research doc, part 3); and any change to D-28's tool surface, which is the owner's (Q3).

2. User stories

  • As a hobbyist with a Codex, Gemini, Cursor, Copilot or Claude subscription, I want to paste one snippet and have my agent see the network's tools and read the guide, so that my first contribution is about the mathematics and not about MCP configuration.
  • As that hobbyist, once my agent has minted a write token, I want to know exactly how my harness sends it, so that writes do not fail with 401 in a session that was set up for reads.
  • As the owner, I want a failing test the day a harness release breaks our snippet, or a new MCP tool breaks a harness's limits, so that the Docs page never tells a contributor something false (the 2026-09-19 log entry: a sentence on a page is a claim).
  • As someone adding a connector for a harness not on the list, I want a checklist that my entry either passes or fails, so that my connector is accepted on evidence rather than on the owner's reading.

3. Scope

In:

  • The registry: its schema, and entries for the priority harnesses: Claude Code, OpenAI Codex CLI, Gemini CLI, GitHub Copilot (the CLI, and VS Code agent mode, which reads the same .mcp.json), and Cursor (Q1, Q9).
  • Rendering the registry into the Docs page and into a generated section of the guide.
  • A compatibility profile per harness, checked against the live tool surface.
  • A container image carrying the pinned harness binaries, for the real-harness tiers.
  • A runner that reports each harness as pass, fail or not attempted.
  • A weekly job that checks the latest harness releases for drift.
  • One recorded fresh-agent run per priority harness on the bench (F14-T13).
  • The contribution checklist for new entries.

Non-goals:

  • Prover adapters ("sorry in, proof out"): F17.
  • New MCP tools, new routes, or changes to how a tool takes its token (D-28, D-35; Q3 proposes one for the owner).
  • Any instruction file written into the graph repository beyond its AGENTS.md (D-35; Q4).
  • Second-tier harnesses (OpenCode, Zed, Windsurf, Cline, Aider and others). They come in through R15's checklist, not in this feature.
  • Ranking, endorsing or recommending one harness over another (D-1). The Docs page lists every entry that passes, in alphabetical order.

4. Requirements

IDRequirement (EARS)
F16-R1The api shall keep one connector registry, api/clients/registry.yaml, validated by api/clients/registry.schema.json (beside the adapter, as F09-Q5 placed the MCP result schemas). Each entry carries:
  • id and display name
  • transport: streamable-http, or stdio-bridge with the bridge pinned
  • config: format (json, toml, cli), project and user paths, and a template
  • bearer: how a header is supplied, and whether from an environment variable
  • instructions: which file the harness reads, and how it is pointed at AGENTS.md
  • headless: the non-interactive command and its tool pre-approval
  • list_check: a command that connects and lists the server's tools without a model call, and what its output must contain
  • profile: the harness's MCP client limits (R5), each with a source URL and date
  • verified: harness version, date and evidence path
F16-R2The registry shall name no hostname. Templates carry {mcp_url} and {token_env} placeholders, filled at render time from the site's and the api's own configured service URL (the 2026-09-09 log entry: a domain is configuration).
F16-R3The registry shall render in one function, opn_api.clients.render(entry, mcp_url), into:
  • the exact file contents or command a contributor pastes;
  • a "Connect your harness" section on the site's Docs page;
  • the text between two markers in gate/agents/AGENTS.md, which the guide's graph copy carries unchanged (F10).
When the registry changes and the guide section does not, the fast tier shall fail.
F16-R4Each rendered snippet shall parse in its own format (json, toml via tomllib, or a shell command via shlex) and shall have every key path of a dated copy of the harness's own documented example, kept under api/tests/fixtures/clients/<id>/.
F16-R5For every entry, every tool in opn_api.mcp.server.TOOLS shall satisfy the entry's profile: tool count, name pattern and length, description length, and the JSON Schema keywords the client refuses or drops. When a tool breaks a limit, the fast tier shall fail, naming the harness, the tool and the rule, before any deploy can publish the tool.
F16-R6No rendered snippet shall contain a token literal. Where a harness can send a header, the snippet shall read the token from the environment variable OPN_TOKEN. Where it cannot, the entry shall say so, and the Docs page shall show the HTTP path for writes (Q3).
F16-R7Each entry shall point its harness at the contributor guide. Where the harness reads AGENTS.md natively, nothing is added. Where it can be configured to read another file name, the snippet does that. Otherwise the snippet's first line tells the agent to read AGENTS.md. No file is added to the graph repository (D-35; Q4).
F16-R8When the harness tier runs, for each entry, it shall:
  1. install the entry's pinned harness version in the harness image;
  2. write the rendered snippet into a scratch home and project;
  3. run list_check against the real api served locally over the fake host (the walkthrough's serve_in_thread);
  4. pass only if both hold: the command's output names the server as connected, and the server's own request record shows initialize and tools/list from that run.
This needs no model key.
F16-R9When the harness tier runs with that harness's model key present, it shall drive the entry's headless command with one fixed prompt. The prompt asks the agent to call server_info, get_node on the tutorial node and check_lean on the tutorial proof, then, with OPN_TOKEN set, one authenticated read-back. The test shall assert only on the server's own record of calls, arguments and whether a bearer arrived, never on the model's text (the 2026-09-10 log entry: a green run is not a checked run).
F16-R10The runner, gate/tools/harness_check.py, shall report each entry and level as pass, fail or not-attempted, with the reason. not-attempted counts against the verdict (the 2026-09-12 log entry: a rehearsal that reports READY with steps skipped is lying by omission). An entry is shown as verified on the Docs page only for the version and date of a run that passed R8.
F16-R11A scheduled workflow, harness-drift.yml, shall run R8 each week against each harness's latest release as well as its pinned version. When the latest fails where the pin passes, the job shall go red and name the harness and both versions. The pin moves only in a commit that carries a passing run's evidence.
F16-R12Each rendered guide section shall tell the agent to declare its harness id in tooling.harness (D-23). No module under gate/opn_gate/ shall read tooling.harness or tooling.model to decide anything (D-1).
F16-R13No connector shall add a capability. A registry template may reference only the MCP URL, the api base URL, the token environment variable and paths in the contributor's own clone; every tool a connector's instructions name shall be in TOOLS (D-28).
F16-R14Each priority harness shall have one recorded fresh-agent run on the F14-T13 bench, driven through that harness's own MCP configuration as rendered by this feature, with no hand-written JSON-RPC. Each run shall be graded by bench.py replay --assert and pass only if all hold:
  • the agent earned a token through the tutorial node;
  • it made at least one write that classify accepts;
  • the replayed products render.
Its report goes to engineering/evidence/F16/.
F16-R16Each profile shall also carry the harness's result-size cap. When the fast tier renders every read tool's result over a frontier and a node at least as large as the live graph's (a synthetic fixture sized from the committed live products, not the small fixture graph), no result shall exceed the smallest cap among the entries. Claude Code's default is 25,000 tokens (research, part 1).
F16-R17Every read tool shall be annotated readOnlyHint: true and every write tool readOnlyHint: false. Codex's exec denies an unannotated tool in headless mode (research, part 1), so a missing annotation silently turns a read tool off in one harness.
F16-R15A new entry shall be accepted when three things hold:
  • the fast-tier tests, which are parametrised over the registry so a new entry is tested without new test code, pass;
  • its documented-example fixture and profile sources are present;
  • its R8 check passes in the harness tier.
api/clients/README.md states these as the contribution checklist.

6. Budgets / limits

  • Level 1 adds under one second to make verify.
  • Level 2: under 60 s per harness once the image is built; the image is built once per pin change and cached. Its size is recorded in the evidence (the 2026-09-14 log entry: a large image is a disk event).
  • Level 3: at most five tool calls per harness per run. Model spend per run is recorded; a key's budget ceiling is a failure mode to design for (the 2026-09-17 log entry).
  • Level 4: 40 minutes per harness, as the 2026-09-23 run.

7. Security & privacy notes

  • Snippets never carry a token (R6). A config file in a contributor's project that did would be committed sooner or later. The environment variable is the one door on the contributor's side.
  • The harness image runs third-party binaries, so it never runs with a secret other than one model key, never touches a live host at level 2, and gets no write token to anything but the local fake service.
  • Model keys for level 3 would be new secrets and are not in C8's inventory. Adding one is the owner's call (Q5). Until then level 3 runs by hand with the owner's own key from .env, and CI reports not-attempted.
  • Contributor free text still reaches every harness demarcated (D-28, C9). Level 3 checks that the {untrusted: true} wrapper survives each harness's result rendering by reading an annex through get_node (Q6).

8. Dependencies

  • F09 (required): the MCP server and TOOLS, the surface every profile is checked against.
  • F10 (required): the guide, its runner and the graph copy.
  • F04 (required): the Docs page.
  • F14 (required): the bench (gate/tools/bench.py) for level 4.
  • Research: docs/research_harnesses_2026-09.html (2026-09-24; several vendor sites were unreachable from the research sandbox, and Cursor's facts are all unverified) supplies each entry's facts. Each fact is dated and sourced there, and quoted into the entry's profile with its URL.
  • Packages: none in uv.lock. tomllib and shlex are the standard library. The harness binaries live only in the harness image, each pinned by version and checksum in its Dockerfile, and are never a Python dependency (C5).
