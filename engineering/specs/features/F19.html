F19 — Proof outlines and the reading view

Give every merged proof an outline the pinned gate extracts from the Lean (its named steps, each with the claim it establishes, the goal it leaves and whether automation closed it) and give each way a target is proved a page a mathematician can read top-down, every line one click from the Lean that proves it.

1. Summary

The owner asked, on 2026-10-03, that a reader who does not know Lean be able to read the network's proofs, with two hard requirements: the mathematics must link back to the Lean, and a mathematician of the subfield must be able to follow it. The research (docs/reports/Lean proofs for mathematicians.md, notes beside it) found that no system turns arbitrary agent-written Lean into followable mathematics. Linking back is a solved engineering problem. Followability comes from a person writing the account. The owner adopted its three-stage plan and its ten proposed requirements (A to J) on 2026-10-04. This feature is stages one and two, the part that needs no model.

Today a node page prints the attested Proof.lean verbatim in a <pre> (D-36), and F18 already says which nodes each proof rests on (target_proofs, closures by use). F19 adds two things. The first is the outline: a product per merged proof, computed by the pinned gate in its sandbox from the proof term's elaboration and committed to the graph like every product (D-35). It holds the have-tree with each step's claim printed so that it reads back as the same Lean, the goal after the step, the constants it uses with Mathlib's own docstring, and whether automation closed it. The second is the reading view: for each entry of target_proofs, one page in dependency order. It leads with the statement and its fidelity state, gives each node its informal account slot, its Lean statement and its outline, and carries a correspondence table from every node to its declaration, lines and attestation. Explainer and annex prose gains math rendering. F19 writes no prose: the drafted explainer, its versions and the steward's editing are F20.

F19 changes no verdict and no status. The outline asserts nothing the kernel did not check, and it is derived from the tree and the pinned gate, so it is rebuildable (D-35). Placing it on the graph is the owner's decision (a) of 2026-10-04 and needs the decisions note drafted in Q1.

2. User stories

  • As a mathematician reading a resolved target, I want the proof laid out as lemmas then theorem, each lemma as a short list of named claims, so that I can read the argument as I would a paper and open the Lean only where I want to check a step.
  • As the same reader, I want the steps closed by automation marked as routine and folded away, so that the page shows me where the difficulty is rather than hiding it under bookkeeping.
  • As a steward about to write or correct an explainer (F20), I want stable step ids with their claims and goals, so that each paragraph I write can say which steps it describes.
  • As a sceptical reader, I want every block on the page to say in words what it is (checked by the kernel, a statement a person audited, or unverified prose), so that I never mistake commentary for proof.
  • As a reader on a phone or with a screen reader, I want the outline to expand with native controls and the mathematics to be readable as MathML.

3. Scope

In: the Lean outline program and its Python wrapper; the outline/v1 schema and product at targets/<id>/outlines/<artifact-hash>.json; the round-trip check of every printed claim and goal; Mathlib docstrings and Stacks/Kerodon tags of used constants; the extraction's placement (Q2) and its backfill workflow; the reading view, the correspondence table and provenance labels; the outline rendering on node pages; math rendering of explainer and annex prose; the guide and the Docs page; the re-pin, backfill and re-render on the live graph.

Non-goals:

  • Any machine-written prose, and any change to explainers: drafts, versions, anchors, the steward's edit path and the drafter are F20. The reading view shows F15's explainers as they are today, in the slot F20 fills.
  • A readability, faithfulness or difficulty score of any kind (requirement H; D-25 forbids ranking; the project's own research refuted readability metrics, research_math_and_ai_2026-09 §8).
  • Translating Lean into English mechanically (the Massot–Miller line). Its display model is emulated (an expandable tree of claims and goals); its code is unpublished and is not a dependency (Q7).
  • Outlines of annexes, which are prose already. (Partial assemblies are in scope since the owner's ruling that all the Lean in the system is translated, Q9.)
  • The MCP tool surface: agents read outlines through F20's route and tools, where they need them to anchor explainers.
  • A leanblueprint or Verso Blueprint export: cheap later, not needed by either requirement.

4. Requirements

EARS notation, stable IDs. Letters A–J name the report's proposed requirements the owner adopted.

IDRequirement (EARS)
F19-R1The system shall publish, for each merged proof artifact of a node (its Proof.lean, each alternate, and each merged partial assembly), an outline/v1 document at targets/<id>/outlines/<artifact-hash>.json naming the node, the artifact's path and hash and the gate commit that extracted it, and its steps: each with an id, a kind (have, obtain, suffices, show, calc step, case branch, or term for a term-mode proof), the name it binds if any, the claim it establishes, the goal it leaves, its line span in the artifact, the constants it uses (graph nodes and definition modules apart from Mathlib), how it is closed (automation with the tactic names, steps, term, or hole for a partial's sorry step, naming the child node F18's decompositions give it) and its child steps.
F19-R2A step's id shall be a function of the artifact's bytes alone: the name it binds where that name is unique among its siblings, else s<n> by source order, dotted for children; the same artifact shall always yield the same ids.
F19-R3The system shall print every claim and goal with the options the hole writer uses (pp.coercions.types, pp.numericTypes, pp.funBinderTypes) and read each one back (parse, elaborate, definitional equality). If one does not read back, then its step shall carry printed: unreliable and the page shall show that step as its Lean lines only (requirement I).
F19-R4For each Mathlib constant a step uses, the outline shall record the first sentence of its docstring and any @[stacks] or @[kerodon] tag, read from the pinned Mathlib; it shall record no name from any other source (requirement E).
F19-R5If extraction fails, exceeds its budget (§6) or meets text longer than its cap, then the system shall write no outline (or mark the truncated field truncated), name the proof and the reason in the job's report, and render every other product (C7; the 2026-09-17 lesson that one node's defect never decides whether the graph has products).
F19-R6The extraction shall run only in the pinned gate image's sandbox, with no secret, at the place T1's measurement decides (Q2); a merge shall gain its outline without a person acting.
F19-R7The system shall provide a dispatched workflow that extracts the outlines of merges made before outline/v1, in the pinned image, for a curator to commit, as F18-T7 did for footprints; run on the live graph, it shall cover every merged proof artifact (67 proofs, 7 alternates and 20 partial assemblies at 2026-10-04), and any it cannot outline shall be named with its reason and retried after the cause is fixed (Q9).
F19-R8For each target_proofs entry (F18-R1) the site shall render a reading view that leads with the root's informal statement, its Lean statement and its fidelity and QA state (requirement A), then lists the nodes of the proof's closure with dependencies before dependents, ties in record order. Each node shall show its Lean statement with its gloss beside it (F20, or the cue), its informal account slot (its explainer, or the recruiting cue D-36 asks for), its outline folded to top-level steps, and a link to its proof's lines at the merged commit.
F19-R9The site shall render an outline as a tree of native <details> elements: each step shows its claim and the goal it leaves, each used Mathlib constant carries its docstring sentence as a tooltip and its tag as text, and expanding a step reaches its Lean lines. A step closed by automation shall be labelled “routine: <tactic names>” and folded by default (requirements D, F).
F19-R10The reading view shall carry a correspondence table: one row per node of the closure, naming the node, its declaration, its artifact path and lines, its attestation, and the state of its explainer.
F19-R11Every block on a node page and the reading view shall carry a provenance label in text: checked by the kernel (with the attestation's commit), statement audited (with the QA state and its signers), informal account, unverified (with author, drafting model and signer, D-3), or untrusted contributor text (annexes, D-31). No label shall be conveyed by colour alone (requirement B).
F19-R12The site shall render TeX in explainer and annex prose with the vendored KaTeX, through an escaped path in prose.render that recognises $…$ and $$…$$ outside code spans and fences only, with trust off; Lean source and file names shall never be scanned (F04-R10, F04-Q14).
F19-R13Every page F19 adds or changes shall render within 390 px without horizontal page scroll, keep keyboard access to every expandable element, and emit MathML alongside the rendered mathematics (requirement J).

6. Budgets / limits

  • The extraction runs inside the sandbox's caps (2 CPU, 4 GiB, no network) and adds no more than T1 measures and Q2 records; its own wall-clock cap is config (OPN_OUTLINE_TIMEOUT_S, C6), and an exceeded cap is R5's report, never a failed gate.
  • Per-step text caps are config: claim and goal (default 2,000 characters each), docstring sentence (300). Goals store the target and the hypotheses the step introduces, never the whole context (Q4).
  • No outline changes a verdict, a status, the frontier or the queue; a merge never waits for an outline (the F07-T55–T57 rule that nothing waits for a post-merge job).
  • The site stays within 390 px without horizontal page scroll; SVG and outline labels are measured, not eyeballed (2026-09-19 lesson).

7. Security & privacy notes

  • Elaboration executes code: the outline program runs merged contributor Lean only inside the pinned image's sandbox, granted no secret (C9, D-4 step 3). The backfill workflow is the same and the curator commits its output by hand, as F18-T7.
  • The outline carries printed types and Mathlib's docstrings, never contributor comments or docstrings; contributor text on the page stays under the untrusted-data demarcation (C9, D-28, D-31).
  • KaTeX runs with trust: false on marked elements only; prose is escaped before any math pass (F04-R10's CSP is unchanged).
  • Stacks and Kerodon tags are shown as text: an off-site link would need F04-R13's allowlist widened, which is not done here (Q6).

8. Dependencies

  • F18 (required): target_proofs, closures by use, decompositions (the reading view's order and its hole links).
  • F02, F07, F08 (required): the step-4 build and sandbox, the post-merge job, the hole writer's print options and round-trip check (F07-T18, F07-T19).
  • F03, F04, F15: the products, the site and its vendored KaTeX, the explainer slot and its signatures.
  • Packages: none planned. SubVerso is evaluated in T1 against the gate's own Frontend.lean; adopting it is a C5 decision recorded in Q3 and pinned in the lake manifest. Screenshots use Playwright through uv run --with, an evidence tool.

(3) A sorry step is kind hole, closed by hole. (4) Each calc step is a step; the calc block is not. (7) A step's uses are the identifiers written in its source that resolve to constants, given to the innermost step; a case alternative's tag counts as using its constructor. (8) A by proof with no step tactics (by omega) has an empty step list, not one step; such a proof's explainer has one unanchored section. (9) Tags are read through Mathlib's own getSortedCrossRefs (checked at mathlib 0df444a3); if it exists and fails, no outline is written. (10) Failure reasons are strings in outline.py, not codes.py rows. (11) Unlike the programs that read compiled modules, opn-outline elaborates the artifact, because the info trees exist only during elaboration: it runs contributor code and belongs only in the sandbox (R6). (12) --printer plain exists for AC3 alone; the gate never passes it. Also: Tagged.lean imports Lean.Environment, since import Lean ran past the 300 s cap under load.
F19-Q12Judgment calls in T4, T5 (2026-10-04; the building agent's, reviewed by the lead). (1) The outline job checks out main as it is when it starts, not the commit the post-merge job pushed: an artifact is outlined once its attestation is on main, a newer main is a superset, and filling every missing outline recovers what a lost run left behind. (2) It runs only when the merge built and passed (the cache job's condition), so a gloss or explainer append never starts one, and its own push starts nothing. (3) Its commit touches only new targets/<T>/outlines/ files, refusing anything else; on a refused push it re-reads main, stops if the target was re-pinned, drops outlines main already has or whose artifact's bytes changed, and retries six times.
