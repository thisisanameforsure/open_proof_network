F04 — Site

The D-36 website: a static rendering of the graph regenerated on every merge, served from S3 through CloudFront, read-only forever, every page naming the commit it renders.

1. Summary

F04 builds site/: a generator that takes a graph checkout at a commit plus F03's products and emits static HTML; the AWS resources that serve it; and the deploy path that runs after every merge. It is the human view of exactly what an agent sees through the read tools (D-28), so it invents nothing: every page renders a file and links to it at the rendered commit. Contributor prose — explainers, annexes, postmortem detail — is escaped and shown under a fixed "unverified" or "untrusted" label with the kernel-checked object one click above it. There is no server-side code, no database, no form, no account (D-36). Cites: D-3, D-5, D-13, D-14, D-18, D-19, D-23, D-25, D-27, D-28, D-33, D-35, D-36.

2. User stories

  • As a bystander, I want to see which targets exist, what has been proved, and the frontier, without cloning anything.
  • As a mathematician deciding whether to review, I want the root statement in Lean beside the informal one and the fidelity grade, on one page.
  • As a prover, I want a node page that links the merged Proof.lean and its attestation at the exact commit.
  • As the founder, I want visitor counts from CDN logs without a tracking script.

3. Scope

In: opn_site generator with the seven D-36 pages; escaped rendering of Lean and prose; a minimal safe prose renderer (paragraphs and code fences only); client-side frontier filtering in plain JavaScript; a link checker; CloudFormation for bucket, distribution, logging with 90-day retention, OIDC deploy role; the deploy workflow in this repo, triggered by the graph repo's post-merge job; first deploy with screenshots.

Non-goals:

  • A custom domain (none exists as of 2026-09-07); the distribution's issued hostname is the address.
  • Search, accounts, comments, RSS, or any input (D-36: never).
  • Markdown rendering beyond paragraphs and code fences; a fuller renderer is a later, justified dependency.
  • Contributors page content beyond what ledger files exist (F07 creates them).

4. Requirements

IDRequirement (EARS)
F04-R1The system shall render, from a graph checkout at commit C and its products: Home, Targets, Target (one per target), Node (one per node), Frontier, Contributors, Docs, with the contents D-36's table lists for each.
F04-R2Every page shall show commit C and, for each file it renders, a link to that file at C in the graph repository.
F04-R3The system shall HTML-escape all content from the graph before insertion; no string from a graph file shall reach the output unescaped.
F04-R4When rendering an explainer, annex, postmortem detail, approach record, or acknowledgment justification, the system shall place it inside a block carrying the label "unverified" (explainers) or "untrusted" (the rest), with author and drafting model where the record has them, below the link to the kernel-checked object.
F04-R5The Node page shall show the rendered Statement.lean, the proof link at the merged commit if proved, the attestation's verdict, Mathlib SHA, toolchain hash, per-step results, reviewer id, trust_base when compiler, attempt count and route-class histogram, the explainer or an explicit "no explainer yet" line.
F04-R6The Target page shall draw the DAG as inline SVG with nodes colored by status, generated server-side with a layered layout; approach records; the D-32 note when present.
F04-R7The Frontier page shall render frontier.json as a table with every D-25 field and shall filter client-side on every field with plain JavaScript; with JavaScript disabled the full table remains readable.
F04-R8The Contributors page shall list every ledger identity with each entry linked to its artifact, showing revoked entries as revoked; when no ledger files exist it shall say so.
F04-R9The Docs page shall include the architecture decisions document, the graph's AGENTS.md, the human-funnel documentation (D-27, when present), the license and DCO text.
F04-R10The output shall reference no external resource: one inline or same-origin stylesheet, one same-origin script, no fonts, images or scripts from elsewhere; pages shall be served with a Content-Security-Policy that enforces this.
F04-R11The system shall provision, via a CloudFormation template in site/infra/: a private S3 bucket with origin access control, a CloudFront distribution with standard logging to a second bucket whose lifecycle deletes objects after 90 days, and an IAM role assumable only by this repo's deploy workflow through GitHub OIDC (C8 item 4).
F04-R12When the graph repo's post-merge job completes, it shall dispatch this repo's site-deploy workflow with the graph commit; that workflow shall render, sync to the bucket with deletion of stale objects, and invalidate the distribution; a failed deploy leaves the previous site intact (C7).
F04-R13The generator shall fail, writing no output, if any product fails schema validation or any internal link would not resolve.

6. Budgets / limits

  • Full render under 30 s for 1,000 nodes; each page under 200 KiB; frontier page paginates client-side beyond 500 rows.
  • Deploy under 5 min end to end after merge.

7. Security & privacy notes

  • All graph content is untrusted for rendering purposes (C9); escaping is the rule, allow-listing is the exception (code fences).
  • CSP: default-src 'none'; style-src 'self'; script-src 'self'; img-src 'self', set as a CloudFront response-headers policy.
  • CDN access logs hold IP addresses: 90-day lifecycle, aggregate use only (C9). No cookies, no beacons.
  • The deploy role can write the site bucket and create invalidations, nothing else.

8. Dependencies

  • F03 (required): products. F00: attestations.
  • Packages: none new. Templates use string.Template; prose renderer and SVG layout are hand-written.
  • AWS: account with the OIDC provider; the founder bootstraps the CloudFormation stack once from the local .env credentials (C8 item 5).

9. Open questions / judgment calls

IDCall made — for review
F04-Q1Deploy runs in this repo, dispatched by the graph's merge job. D-36 says the generator runs "in the same merge hook that regenerates frontier.json". Running it in the graph repo would require the graph workflow to carry site tooling and AWS credentials; dispatching this repo's workflow keeps the graph workflow secretless beyond the gate key and keeps site changes out of graph history (D-35). Same trigger, different repo; proposed clarification to D-36.
F04-Q2Prose renderer is deliberately tiny. Paragraphs and fenced code only; everything else is literal text. Correct and safe beats pretty at Stage 0.
F04-Q3DAG layout is longest-path layering with nodes ordered lexically within a layer; no crossing minimization. Good enough for 20–100 nodes; revisit at Stage 2 scale.
F04-Q4Docs page ships this repo's decisions doc copied at the site build's network commit, so the site can lag the doc by at most one merge.
