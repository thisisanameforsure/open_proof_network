F10 — Agent funnel

D-27's two funnels: the graph repo as the agent interface — AGENTS.md, per-node context bundles, a pinned devcontainer with a warm olean cache — and the documentation track for the human judgment roles.

1. Summary

By F09 every capability exists; F10 makes them findable and cheap to start. It writes the graph's AGENTS.md as a tested walkthrough of both paths, generates a machine-shaped context bundle per node so get_node and a raw clone serve the same object, pins a devcontainer per graph to the gate's own image, and builds the olean cache pipeline D-27 names as required infrastructure — the difference between minutes and hours for a cold agent, and the thing F11's first Mathlib-pinned graph cannot ship without. The human funnel gets its first documents: review checklists from the defect taxonomy, and walkthroughs for revision requests and defect claims. Cites: D-3, D-4, D-7, D-9, D-11, D-13, D-15, D-25, D-27, D-28, D-31, D-35, D-36.

2. User stories

  • As an operator pointing a fresh agent at the repo tonight, I want one file that tells it how to claim, precheck, submit and record a failure, with commands that actually work.
  • As an agent, I want a node's context as one JSON document with no transcripts, so I spend tokens on mathematics.
  • As anyone starting a devcontainer, I want a warm cache so the first build is minutes, not hours (D-27).
  • As a new statement reviewer, I want a checklist derived from the defect classes, so I look for what actually goes wrong (D-15).

3. Scope

In: the graph's AGENTS.md with an executable walkthrough test; nodes/<id>/CONTEXT.json (schema context/v1) regenerated on merge; get_node served from it; devcontainer.json per graph pinned by image digest; the gate image published to GHCR and referenced by digest in gate-spec.json; the olean cache pipeline (build on merge, upload, fetch in pregate.sh, devcontainer and CI); human-funnel documents on the site's Docs page.

Non-goals:

  • Mathlib itself: its cache comes from lake exe cache get; F10's pipeline covers the graph's own oleans (defs/, nodes). F11 exercises both.
  • Canary-based reviewer training (D-11, D-27) — Stage 1.
  • Skeletonization examples beyond the fixture — F11 provides a real one.

F10-R8The cache pipeline shall verify integrity: every uploaded archive carries a SHA-256 manifest; a fetch whose manifest does not verify shall be discarded and rebuilt, never trusted.
F10-R9The site's Docs page shall carry the human-funnel documents: a statement-review checklist per defect class (F08-Q4 taxonomy) with a worked example each, a revision-request walkthrough, a defect-claim walkthrough, and the curator intake checklist (D-6), each naming the decision it implements.
F10-R10The system shall record, in evidence, cold and warm timings for: devcontainer start to first pregate.sh pass, CI gate on the tutorial node, and precheck end to end — the Stage 0 latency series.

6. Budgets / limits

  • Tutorial graph: devcontainer start to first pass under 3 min cold; CI gate under 5 min; cache archive under 50 MiB.
  • CONTEXT.json under 256 KiB; attempt records capped at the newest 50.

7. Security & privacy notes

  • Cache archives are built only by the post-merge job from merged content and verified by manifest; a poisoned cache cannot change a verdict because the authoritative gate replays from the pinned toolchain (D-4 step 1, D-5), but it could waste time, hence R8.
  • The image is pulled by digest everywhere; a tag is never trusted (D-35 pinning discipline).
  • Cache bucket writes use the same OIDC role pattern as the site (C8 item 4).

8. Dependencies

  • F09 (required): get_node. F04: Docs page. F07, F08: the flows the walkthrough documents.
  • Packages: none new.
  • Infra: GHCR on the founder's account; a cache bucket added to the site's CloudFormation stack.

9. Open questions / judgment calls

IDCall made — for review
F10-Q1The devcontainer image is the gate image. D-27 asks for a pinned devcontainer per graph; using the step-3 image means what a contributor builds in is what the gate builds in, which is D-4's one-codebase rule extended to the environment.
F10-Q2CONTEXT.json is a bot-owned file inside the node directory, excluded from the submission path check like META.yaml. It duplicates nothing evidentiary; it is a rendering, deleted and regenerated on every merge.
F10-Q3Docs are tests. An AGENTS.md whose commands rot is worse than none; the walkthrough runner is how the doc stays true (C1 applied to prose).
F10-Q4The tested AGENTS.md lives in this repo and the graph carries a copy (T1, 2026-09-11). D-27 puts the file at the graph root, but this repo's CI has no sibling checkout, so the test reads gate/agents/AGENTS.md and, when the sibling is present, checks the graph's copy is byte-identical — the same shape as schemas/, which the graph also carries as a copy of this repo's registry (D-35). The copy lands with the same F10-Tn: commit message.
F10-Q5Two tags let a command block escape execution, and both are counted. sh lean marks the one block that needs the pinned toolchain (pregate.sh); the fast tier skips it and a lean-tier twin of AC1's test runs it, so make verify stays under a minute (conventions §2) while the git path is still executed on every make verify-lean. sh manual marks the push to a remote and the MCP registration, which no fixture can absorb; the test freezes that set at those two, so no other command can hide behind the tag. Everything else — 27 blocks — runs against the fixture clone and the fake service on a real port, with the documented output lines matched in order (R2's “drifts from the documented output”).
