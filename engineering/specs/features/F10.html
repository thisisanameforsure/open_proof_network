F10 — Agent funnel

D-27's two funnels: the graph repo as the agent interface — AGENTS.md, per-node context bundles, a pinned devcontainer with a warm olean cache — and the documentation track for the human judgment roles.

1. Summary

By F09 every capability exists; F10 makes them findable and cheap to start. It writes the graph's AGENTS.md as a tested walkthrough of both paths, generates a machine-shaped context bundle per node so get_node and a raw clone serve the same object, pins a devcontainer per graph to the gate's own image, and builds the olean cache pipeline D-27 names as required infrastructure — the difference between minutes and hours for a cold agent, and the thing F11's first Mathlib-pinned graph cannot ship without. The human funnel gets its first documents: review checklists from the defect taxonomy, and walkthroughs for revision requests and defect claims. Cites: D-3, D-4, D-7, D-9, D-11, D-13, D-15, D-25, D-27, D-28, D-31, D-35, D-36.

2. User stories

  • As an operator pointing a fresh agent at the repo tonight, I want one file that tells it how to claim, precheck, submit and record a failure, with commands that actually work.
  • As an agent, I want a node's context as one JSON document with no transcripts, so I spend tokens on mathematics.
  • As anyone starting a devcontainer, I want a warm cache so the first build is minutes, not hours (D-27).
  • As a new statement reviewer, I want a checklist derived from the defect classes, so I look for what actually goes wrong (D-15).

3. Scope

In: the graph's AGENTS.md with an executable walkthrough test; nodes/<id>/CONTEXT.json (schema context/v1) regenerated on merge; get_node served from it; devcontainer.json per graph pinned by image digest; the gate image published to GHCR and referenced by digest in gate-spec.json; the olean cache pipeline (build on merge, upload, fetch in pregate.sh, devcontainer and CI); human-funnel documents on the site's Docs page.

Non-goals:

  • Mathlib itself: its cache comes from lake exe cache get; F10's pipeline covers the graph's own oleans (defs/, nodes). F11 exercises both.
  • Canary-based reviewer training (D-11, D-27) — Stage 1.
  • Skeletonization examples beyond the fixture — F11 provides a real one.

6. Budgets / limits

  • Tutorial graph: devcontainer start to first pass under 3 min cold; CI gate under 5 min; cache archive under 50 MiB.
  • CONTEXT.json under 256 KiB; attempt records capped at the newest 50.

7. Security & privacy notes

  • Cache archives are built only by the post-merge job from merged content and verified by manifest; a poisoned cache cannot change a verdict because the authoritative gate replays from the pinned toolchain (D-4 step 1, D-5), but it could waste time, hence R8.
  • The image is pulled by digest everywhere; a tag is never trusted (D-35 pinning discipline).
  • Cache bucket writes use the same OIDC role pattern as the site (C8 item 4).

8. Dependencies

  • F09 (required): get_node. F04: Docs page. F07, F08: the flows the walkthrough documents.
  • Packages: none new.
  • Infra: GHCR on the founder's account; a cache bucket added to the site's CloudFormation stack.

F10-Q1The devcontainer image is the gate image. D-27 asks for a pinned devcontainer per graph; using the step-3 image means what a contributor builds in is what the gate builds in, which is D-4's one-codebase rule extended to the environment.

F10-Q5Two tags let a command block escape execution, and both are counted. sh lean marks the one block that needs the pinned toolchain (pregate.sh); the fast tier skips it and a lean-tier twin of AC1's test runs it, so make verify stays under a minute (conventions §2) while the git path is still executed on every make verify-lean. sh manual marks the push to a remote and the MCP registration, which no fixture can absorb; the test freezes that set at those two, so no other command can hide behind the tag. F10-Q6The demarcation rule moved into the gate package (T2). F09 put FREE_TEXT and the wrapper in api/opn_api/mcp/demarcate.py; R3 has the post-merge job apply the same rule to CONTEXT.json, and the gate cannot import the api. One table, one wrapper: opn_gate.demarcate is the rule and the api module re-exports it, so every existing import keeps working and the two callers cannot drift.
F10-Q7get_node derives the bundle when the graph has none committed. Until the graph is re-pinned and its products regenerated, no CONTEXT.json exists at main; failing the tool for that window would take the deployed get_node dark across the very push that ships this task (the deploy's read-only smoke calls it). The generator therefore reads through a Reader seam — a checkout for the post-merge job, the host at main for the api — and the tool answers the same document either way, saying which in context_source (file or derived). AC4's test proves the two are equal, which is also the strongest form of R4's “same document”.
F10-Q8get_node's result shape changed in place (T2). The bundle is now {context, context_source, files, claims, annexes, explainers}: the assembled meta/attempts fields of F09 were re-derivations of what CONTEXT.json holds, and serving both would double the tokens an agent spends on one node. The raw META.yaml text is not served, because its hazard justifications are free text; the bundle's meta block carries its facts with that field wrapped. mcp/get_node/v1 was edited rather than versioned: the adapter's result schemas are not protocol records (F09-Q5) and nothing pins them. files gained Proof.lean.
F10-Q9The human-funnel documents are this repository's, under site/docs/, rendered as pages (T5). They are documentation of the protocol, not mathematics, so D-35 keeps them out of the graph; the site renders each as docs/<name>.html and links it from the Docs page, while a graph's own docs/ files stay linked as files, as F04 had them. The site's prose renderer gained a document mode (headings, lists, inline code and strong) for these pages only; contributor prose still goes through the deliberately tiny renderer of F04-Q2, and both escape everything.
F10-Q10One digest by construction: every consumer reads the image from the spec (T3). R5 asks that gate.yml, the precheck job, reproduce.sh and the devcontainer all use the pinned digest. Rather than write it into four files and test that they agree, ensure_image — the one place a sandboxed run chooses its image — pulls devcontainer_ref by digest when the spec names one and builds from gate/Dockerfile when it does not, so the three workflow and script files carry no image of their own (AC5's test checks exactly that) and pin_image.py writes the two files that do name it, gate-spec.json and .devcontainer/devcontainer.json, together. The old pin ignores the field, so the graph's workflow needed no change and the F08-Q8 rule holds.
F10-Q11The devcontainer image is the gate image, grown (T3, Q1 made concrete). The image now also carries uv, the Python .python-version names, this repository's gate/ with its locked environment synced, and a home for uid 1000, so pregate.sh runs inside it offline with no build (R6; AC10 measured 58.8 s from container start to the tutorial's pass, cold). The build context moved to the repository root with a root .dockerignore. The sandbox still runs only elan and lean in it. Published for linux/amd64 only: the hosted runners are amd64 and an arm64 laptop runs it under emulation; a native arm64 build waits for someone to need it. The first digest is Mike's act: the publish workflow runs on a tag push, and the graph's pin (devcontainer_ref, .devcontainer/devcontainer.json) is written by pin_image.py from the digest that run prints — the two-commit shape the log records for every re-pin. Until then devcontainer_ref stays null and every run builds the image locally, as before.
F10-Q12The cache is layered on the gate's own build layout and can never change a verdict (T4). What is cached is what step 4 compiles before the node under check: each proved node's generated Context and merged Proof modules, keyed by the staged source's hash and the toolchain. The node under check is always compiled, and leanchecker --fresh re-checks every import, so a poisoned olean fails step 4 (D-4, D-5). The attestation records nothing about the cache — hits go to the printed summary and cache.json — because D-5 requires two runs anywhere to agree byte for byte and whether a dependency was fetched or compiled is not a fact about the tree (the lean-tier test asserts the two attestations are identical). reproduce.sh and the post-merge re-derivation do not consult the cache at all. Layout in the bucket: <prefix>/<target>/<commit>/{manifest.json,oleans.tar.gz} plus <target>/index.json, served at https://openproofnetwork.org/cache/ through the site's distribution; the index is read-modify-write in the post-merge job, which runs once per push. defs/ oleans enter the cache when F11 gives a graph any (the fixture and the tutorial graph have none).
F10-Q13Ancestry decides “at or before” (T4, R7). The newest cache at or before a commit is the candidate on that commit's own history with the fewest commits between (git merge-base --is-ancestor, rev-list --count); a cache from a side branch is never used, and without git only the exact commit matches. A dirty working tree keys on HEAD, since the cache covers dependencies the tree still shares with it.
F10-Q14A prose finding is fixed by the guide's own edit, and a test's parser moves only when it cannot read the fix. The two live testers of 2026-09-13 met the skeleton's citation refused, holes nobody told them were theirs, bare attestation ids that missed the padded files, their own pull requests invisible, a bare “not claimable”, and MCP argument names that differed from the body fields. The skeleton test's parser only looked above theorem, so no guide in the fixed shape could pass it; it now lays the block over a real statement, and a mutant restoring the old shape fails with the original proof-not-statement. The graph's copy and README are pushed by the lead and held by two strict xfails until then, because the copy test reads the graph's working tree, which every session's hook shares.
