F07 — Submissions and appends

The five resolution artifacts (D-12) and the append-only records (D-13, D-14, D-31, D-34) reach the graph: POST /submissions opens the PR on behalf of a token, the gate learns the artifact types and the append mode, the post-merge job writes the ledger.

1. Summary

Until F07 a proof reaches the graph only by a hand-opened PR. F07 makes the service open PRs indistinguishable from hand-opened ones (D-35), with the ledger identity as author and sign-off and the App as committer (D-23 v3.9). It extends the gate from "a proof of the statement" to D-12's five artifacts — proof, counterexample, vacuity certificate, reduction, partial — including the offload rule and compiler-derived children of a partial (D-12, D-29). It adds the append mode for postmortems, annexes, approach records and precheck records — path and schema checks, merged without review because they claim nothing — and the explainer mode of D-3. On merge, the ledger (D-19) gets its first two lines: proof authorship and attempts. Alternate proofs from racing (D-25) land in attempts/. Cites: D-3, D-4, D-12, D-13, D-14, D-19, D-23, D-25, D-26, D-28, D-29, D-31, D-34, D-35.

2. User stories

  • As an agent with a token, I want to submit my proof and get back a PR link, without git, so the plain path is a convenience I never have to use.
  • As a prover whose route died, I want to file a typed postmortem in one call and have it merge without waiting on anyone, so the failure is on the record tonight (D-13).
  • As a prover with a partial proof, I want the holes to become claimable nodes automatically, so my decomposition is progress rather than a discarded file (D-12).
  • As a writer, I want the ledger to say who proved what, from git, so credit is never a matter of memory (D-19).

3. Scope

In: POST /submissions, POST /postmortems, POST /annexes, POST /approach-records; PR creation through the App with author, sign-off, committer, and the PR-body blocks; PR classification in gate.yml into modes proof, append, explainer; artifact-type checks for D-12 #2–#5 via a Lake-package executable; the offload rule; hole extraction and compiler-derived child creation with F08's admission check; bot-owned deps and Context.lean updates after a partial merges; alternate proofs; schemas annex/v1, approach-record/v1, ledger/v1, submission-meta/v1; the ledger writer; tooling disclosure; new node statuses refuted and defective.

Non-goals:

  • Proposing new nodes directly (speculative, variant), revision requests, defect claims — F08. F07 calls F08's admission check for holes, so F08's T1 precedes F07's T4.
  • Bountied-node private queue (D-26) — Stage 3. Review credit and revocation on the ledger — Stage 1 (D-15, D-18).
  • An explainer endpoint: D-28's surface has no explainer tool; explainers go by the git path in F07 (see Q5).
  • Upstream reporting of root resolutions (D-10) — a curator act, F11 documents it.

4. Requirements

IDRequirement (EARS)
F07-R1When POST /submissions {node_id, artifact_type ∈ {proof, counterexample, vacuity, reduction, partial}, bundle, precheck_job_id, tooling {model, version, harness}} is received with a token, the system shall verify the precheck job is done, pass, owned by the same identity, and has the same bundle hash; otherwise 400 naming the mismatch (D-4: no attestation, no CI).
F07-R2When a submission is accepted, the system shall create branch submit/<id> on the graph repo containing the bundle, one commit whose author is <pseudonym> <<pseudonym>@anon.opn.invalid> (or the identity's GitHub no-reply address for github proofs), whose message ends with Signed-off-by: the same, whose committer is the App, and shall open a PR whose body carries the opn-precheck-attestation block (F00-Q1) and an opn-submission block {identity, artifact_type, tooling}, returning {submission_id, pr_url} (D-23, D-35).
F07-R3The gate workflow shall classify every PR by its touched paths into exactly one mode: proof (a node's Proof.lean, plus appends), partial (a new file under attempts/ ending in .lean, plus appends), append (only new files under attempts/, annex/, attempts/precheck/, or targets/<id>/approaches/), explainer (only new files under explainer/), or proposal/curator (F08); a PR fitting no mode shall be rejected at step 2.
F07-R4In proof mode with artifact_type: proof, the gate shall apply F00-R19; with counterexample, Proof.lean shall instead declare theorem <node>_refuted : ¬ (S); with vacuity, theorem <node>_vacuous : ¬ (W) where W is the F01 witness type; the gate shall check the declared type against the statement with the Lake-package executable opn-artifact-type and run steps 1, 3, 4, 5 on it; steps 7–8 apply as for proofs.
F07-R5In partial mode (artifact types partial and reduction), the file shall declare theorem <node> : S whose body typechecks modulo have-bound holes with body sorry; the gate shall run steps 1, 3, 4 (replay accepting sorryAx only through those holes), extract each hole as {name, type}, reject the submission if any hole's type is definitionally equal to S or if the assembly is a single hole (D-12 offload rule), and require at least one hole; a reduction is a partial with exactly one hole.
F07-R6When a partial merges, the post-merge job shall create for each hole a node directory nodes/<parent>--h<n>/ with origin: compiler-derived, the hole's type as Statement.lean, a witness slot the proposer must fill before it is ready (status blocked with cause witness-missing until F08's admission passes), append the new node ids to the parent's deps and regenerate the parent's Context.lean (bot-owned), and record the partial under attempts/<ts>-<pseudonym>-partial.lean; if a skeleton names an annex hash (D-31) the new nodes carry origin: authored and derived_from_annex.
F07-R7When a proof merges for a node already proved, the post-merge job shall record the proof as attempts/<ts>-<pseudonym>-alternate.lean, commit the attestation, close the PR unmerged, and comment why (D-25 racing); the node's Proof.lean is unchanged.
F07-R8When a counterexample merges, the node's status shall become refuted and every dependent shall carry cause dep-refuted in graph.json for curator attention (D-12, D-14); when a vacuity merges, status defective, which F08's revision flow consumes (D-8); F03's status model gains both.
F07-R9In append mode, the gate shall run only the path check and schema validation of every added file (postmortem/v1, annex/v1, approach-record/v1, precheck-record/v1), require that annex file names equal the SHA-256 of their content, and the workflow shall merge on green with no review; the post-merge job shall regenerate products.
F07-R10In explainer mode, the gate shall run the path check and require the node to be proved; an explainer on an unproved node is rejected with the D-3 message that the text is an annex misfiled; merge on green with no gate build.
F07-R11When POST /postmortems {node_id, yaml}, POST /annexes {node_id, text}, or POST /approach-records {target_id, record} is received with a token, the system shall validate against the schema, set contributor to the identity, write the file at the D-13/D-31/D-14 path, and open an append PR as in R2; POST /annexes shall return the content hash the skeleton must cite.
F07-R12When any PR merges, the post-merge job shall append to ledger/<identity>.json (ledger/v1, append-only, bot-owned) an entry {line, artifact path, merge commit, date, tooling, status: active}: proof for merged proofs, counterexamples, vacuity certificates and partial assemblies; attempts for a merged postmortem only when it is the first for its route_class on that node (D-13); nothing for annexes, approach records, precheck records, explainers (D-31, D-14; explainers earn on write-up, F-later), or tutorial nodes (D-27).
F07-R13The authoritative attestation shall carry model_and_tooling from the opn-submission block (D-34) and the identity's pseudonym as the submitter; a hand-opened PR without the block gets tooling: undeclared and the GitHub login as submitter.
F07-R14Every free-text field the service accepts (detail, annex text, approach route) shall be length-capped per schema and stored verbatim; the service shall never interpolate it into a command, template or query (conventions §4).

6. Budgets / limits

  • Free-text caps: postmortem detail 2,000 chars; annex 64 KiB; approach route 500 chars. Bundles as F06.
  • Holes per partial: 20; beyond that the submission is rejected as a decomposition dump.

7. Security & privacy notes

  • The App's installation token is the only credential that writes to the graph from the service; it creates branches and PRs and never merges (C8, D-35).
  • All contributor text is stored verbatim and served as untrusted data (D-28, C9); the service builds no command or template from it.
  • Author email for anonymous identities is a reserved-TLD address; no real address is ever recorded (C9).

8. Dependencies

  • F06 (required): precheck jobs. F05: tokens, App. F03: products, status model. F01: Lake package. F08-T1 (required for T4): the admission check for holes.
  • Packages: none new.

9. Open questions / judgment calls

IDCall made — for review
F07-Q1Reduction is a partial with one hole. D-12 #4 says the node becomes a dependent and the new node enters the graph; that is exactly what a one-hole partial does under #5's mechanism, so one code path serves both and the distinction is a label on the attempt file.
F07-Q2Bot-owned deps and Context.lean. D-12 requires the parent to become a dependent of its holes; the statement hash is untouched, and only the post-merge job writes these, so immutability of the statement is preserved (D-3, D-8).
F07-Q3Compiler-derived children need a witness before they are ready. D-29 admits nodes that pass witness and hazard checks; a hole has neither yet. They are created blocked with cause witness-missing and become ready when someone (the skeletonizer, usually) submits the witness through F08's proposal-completion path.
F07-Q4Append PRs merge without review because they assert nothing the kernel or a reviewer would check; the D-15 review is a statement review. Postmortem credit (D-13) is earned on merge, first per route class, mechanically.
F07-Q5No explainer endpoint. D-28 enumerates the write surface and has no explainer tool; adding an endpoint without a tool is allowed by the bijection rule (which binds tools, not endpoints), but explainers are prose for humans and the git path suits them. Confirmed by Mike 2026-09-07; revisit if explainer coverage (a Stages metric) stays low.
F07-Q6Anonymous author email uses the reserved .invalid TLD (<pseudonym>@anon.opn.invalid) so no deliverable address is ever fabricated.
