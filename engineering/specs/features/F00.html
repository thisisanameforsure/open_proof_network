F00 — Gate walking skeleton

The thinnest thread through the trust base: one Mathlib-free tutorial node, the gate's mechanical steps 1, 2, 4 and 5 running identically on a laptop (pregate.sh), in CI (gate.yml) and in replay (reproduce.sh), ending in a D-5 identical attestation across two machines.

1. Summary

F00 builds the gate as a pipeline of steps over a node directory (D-3) and proves the one thing everything else depends on: that a verdict is a reproducible artifact (D-5). It implements D-4 steps 1 (dependencies from the pinned toolchain only), 2 (permitted paths and statement hash), 4 (kernel replay from clean, lean4checker --fresh) and 5 (axiom allowlist), the step-3 sandbox the authoritative run adds, the attestation record (D-34 minimum plus the fields in §9), and the three invocations of one codebase D-4 names: pregate.sh locally, the authoritative gate.yml on GitHub-hosted runners, and reproduce.sh. It seeds the graph repo (D-35) with schemas/, one graph's gate-spec.json, the workflow, and the permanently open tutorial node (D-27). It ends with a rehearsal of the invited-run thread for a proof: prove the tutorial node, open the PR, merge on kernel green plus a recorded review, reproduce the attestation byte for byte.

F00 does not implement steps 6, 7, 8 or 9's tooling beyond a reviewer field, the frontier, the site, any HTTP endpoint, MCP, claims, identity, or Mathlib-dependent graphs. Those are F01–F10 (index). Cites: D-3, D-4, D-5, D-7, D-27, D-34, D-35.

2. User stories

  • As a prover (human or agent-operated), I want to run the gate locally on my proof and get a structured verdict naming the first failing step, so I can self-correct before spending anyone's CI minutes.
  • As the gate owner, I want every merge to carry a signed attestation that anyone can regenerate from a clean machine, so a verdict never rests on trusting me or my infrastructure.
  • As a bystander, I want to check that a merged proof rests only on the three allowed axioms, from the attestation alone.
  • As a build session, I want the pipeline testable without Lean installed, and a second tier that runs the real toolchain, so the fast suite stays fast and the real one stays honest.

3. Scope

In: D-3 layout validation and the step-2 path check with statement hash; step 1 toolchain resolution ignoring submitted manifests; step 4 kernel replay; step 5 axiom allowlist with native_decide rejected outright; the pipeline runner with first-failure JSON verdicts (D-34); schemas/ v1 for gate-spec, attestation and META; the Toolchain seam and its fake; the step-3 container image with caps from gate-spec.json; pregate.sh (unsigned or SSH-signed attestation); reproduce.sh; gate.yml with a secretless gate job and a post-merge signing job that commits the attestation; the precheck-attestation bounce rule; the fixture graph; seeding the graph repo; the rehearsal.

Non-goals:

  • Steps 7 and 8 (witness, declared dependencies) — F01.
  • Step 6 hazard checkers and the native_decide waiver path — F02.
  • frontier.json, info.json, claim overlay — F03.
  • The site — F04. Any HTTP or MCP surface, tokens, claims — F05–F08.
  • Olean cache, devcontainer, per-node context bundles — F09. Mathlib-pinned graphs — F10.
  • Reviewer assignment, canaries, anonymity on bountied nodes (D-11, D-15) — Stage 1.

4. Requirements

EARS notation, stable IDs. Step numbers are D-4's.

IDRequirement (EARS)
F00-R1The system shall validate a node directory against the D-3 layout and report every missing, extra, or misnamed entry as a structured diagnostic.
F00-R2When a submission diff is presented, the system shall reject, before any build, any change to a path other than the claimed node's Proof.lean or an append under its attempts/ or annex/, naming every offending path (D-3, step 2).
F00-R3When a submission diff is presented, the system shall recompute the content hash of Statement.lean and reject if it differs from META.yaml's statement-hash (step 2).
F00-R4The system shall resolve the Lean toolchain and every dependency from the graph's gate-spec.json alone, and shall ignore any lake-manifest.json or lean-toolchain present in the submission (step 1).
F00-R5The system shall replay every declaration of the node through the kernel from a clean environment via lean4checker --fresh and fail the step on any error (step 4).
F00-R6The system shall fail step 5 if the set of axioms the proof depends on is not a subset of the allowlist in gate-spec.json, and shall fail it if the proof uses native_decide.
F00-R7The system shall execute the implemented steps in D-4 order, stop at the first failure, and emit a JSON verdict naming that step and a structured diagnostic; on success the verdict shall carry every step's result (D-34).
F00-R8The system shall emit an attestation validating against schemas/attestation/v1.json, carrying the D-34 minimum fields plus graph_id, gate_spec_hash, network_commit, runner, precheck_attestation_hash, merge_commit, and a signature block (§9).
F00-R9The system shall validate every META.yaml, gate-spec.json and attestation it reads or writes against the schema named in its schema field, and shall refuse a document whose schema is unknown.
F00-R10Every schema shall live at schemas/<name>/v<n>.json, and the system shall fail its own test suite if the content hash of a published schema changes (D-34: versioned, never edited).
F00-R11pregate.sh shall run steps 1, 2, 4 and 5 on a node with the pinned toolchain in an ordinary local build, write the verdict and an attestation with runner: local, and when invoked with --sign shall sign it with the caller's SSH key.
F00-R12When the authoritative gate runs, the system shall execute steps 1, 4 and 5 inside a container started with no network, no secrets in its environment, a non-root user, and the cpu, memory and wall-clock caps declared in gate-spec.json (step 3; C6).
F00-R13If a pull request carries no precheck attestation, or one whose signature kind is not in gate-spec.json's accepted_precheck_signatures, or one older than precheck_max_age, then the gate shall emit a verdict of bounced without running steps 1–8 (D-4).
F00-R14When a pull request merges to main, a separate post-merge job shall sign the attestation with the gate signing key, fill merge_commit, and commit it to attestations/<id>.json; the gate job itself shall hold no secret and no write permission (C8).
F00-R15reproduce.sh, given a merged commit, shall rerun steps 1, 2, 4 and 5 inside the step-3 image and produce an attestation identical to the committed one once runner, merge_commit and signature are masked (D-5).
F00-R16While the Lean toolchain is absent from the machine, make verify shall pass using the fake Toolchain, and make verify-lean shall fail with a diagnostic that names the install script.
F00-R17The system shall read secrets and environment only through opn_gate.config, with a documented default for every non-secret value (C6, C8).
F00-R18If any step raises an unexpected error, the system shall record it as that step's failure with the exception class and message in the diagnostic, never as a pass and never as a crash without a verdict (C7).
F00-R19When step 2 runs on a proof submission, the system shall verify that Proof.lean is Statement.lean with only the sorry body replaced — identical module header, identical declaration signature text — so that what steps 4 and 5 check is a proof of the statement and nothing else; any other difference fails step 2 naming the first divergent line.

6. Budgets / limits

  • make verify under 60 s on a laptop with no toolchain (conventions §2).
  • make verify-lean under 10 min on a laptop for the Mathlib-free fixture.
  • Authoritative gate on a hosted runner under 10 min for the tutorial node, cold.
  • Default step-3 caps in the seeded gate-spec.json: 2 cpu, 4 GiB, 600 s; tests use smaller caps (AC26).
  • An attestation under 64 KiB; diagnostics truncated with an explicit marker beyond 8 KiB.

7. Security & privacy notes

  • A contributor's Lean is arbitrary code at elaboration time. It runs only inside the step-3 container (CI) or on the contributor's own machine (pregate.sh, their choice). C9.
  • The gate job in gate.yml is granted permissions: {} and no secret; only the post-merge job on main receives the gate signing key and contents: write. C8 items 1 and 4.
  • The gate signing key is generated once by the founder, its public half committed to the graph at keys/gate.pub; the private half exists only as the Actions secret. Rotation is a visible commit adding a new public key with a start date.
  • Diagnostics quote at most the failing line of contributor text and are served as data, never rendered as markup (D-28 demarcation is F04/F08's job; F00 just keeps them plain strings).
  • Nothing in F00 stores personal data. The reviewer field in an attestation carries the approving GitHub login, which D-15 makes public on standard nodes.

8. Dependencies

  • Packages: jsonschema (runtime), pytest, ruff, mypy (dev) — justified in conventions §1; pinned and locked in uv.lock by T1. pyyaml for META.yaml — justified here: the stdlib has no YAML parser and D-3 fixes YAML for META; pinned in T3.
  • External tools: elan and the pinned Lean toolchain; lean4checker at the commit matching that toolchain; Docker; ssh-keygen (platform); GitHub Actions hosted runners.
  • Graph repo ../open_proof_network_graph: T8 seeds it; T9 needs it pushed to GitHub with Actions enabled and branch protection on main requiring the gate check and one approving review.
  • No feature dependency. F01–F10 depend on this.

9. Open questions / judgment calls

IDCall made — for review
F00-Q1Precheck attestation signature kinds — decided in D-4 (v3.9): the gate accepts service, contributor (SSH-signed) or none as listed per graph in gate-spec.json, and records the kind. Field names here: accepted_precheck_signatures, precheck_max_age. How it is attached: as a fenced json block in the pull-request body whose first line is opn-precheck-attestation; the gate parses the first such block. The PR body is not evidentiary; the authoritative attestation records the hash and kind of what it consumed (D-34). Same mechanism on both paths: POST /submissions writes the block, a git-path contributor pastes it.
F00-Q2gate-spec.json field names. D-28 (v3.9) lists the contents; F00 fixes the JSON keys: schema, graph_id, lean_toolchain, mathlib_sha (null when Mathlib-free), axiom_allowlist, hazard_checkers, olean_cache_url, devcontainer_ref, network_commit, step3_caps {cpu, memory_mib, wallclock_s}, accepted_precheck_signatures, precheck_max_age_s, gate_owner. A key rename is a schema version bump (D-34).
F00-Q3Attestation field names. D-34 (v3.9) lists the contents; F00 fixes the keys: graph_id, gate_spec_hash, network_commit, runner ∈ {hosted, local}, precheck_attestation {hash, signature_kind}, merge_commit, signature {kind, key_id, value, timestamp}. The D-5 comparison masks runner, merge_commit, signature. T3 addendum (2026-09-08): D-34 requires a timestamp and D-5 masks only those three fields, so the run timestamp lives inside the signature block (when the record was sealed) and is masked with it; the schema also carries graph_commit (the graph commit checked, null for a dirty local tree — F06-R6 needs it), tooling {model, harness} for D-23, a per-step steps list, and reviewer. Formats are enforced by explicit patterns, not JSON Schema format, which would need two more packages (C5).
F00-Q4Step 9 recording — decided in D-4 (v3.9): an approving pull-request review by an identity other than the author; the post-merge job writes the reviewer into the attestation; merge is mechanical on steps 1–8 green plus that approval. F00 implements the mechanical merge with branch protection requiring the gate check and one approving review, plus a post-merge job; the reviewer field is the approving GitHub login.
F00-Q5The rehearsal reviews its own author. T9's PR is authored and reviewed within the founding team. D-22 waives D-21 separation for the founding team at Stage 1; F00 applies the same waiver at Stage 0 and records the reviewer as the founder.
F00-Q6Tutorial-node attestations are committed like any other, and "permanently open" means always submittable. D-27 puts the tutorial node off-ledger, which is about credit, not verdicts; its META.yaml carries tutorial: true (D-3, v3.9). The first passing PR merges and fills Proof.lean (that is T9). Every later passing PR on the node is gated identically, its attestation committed, and its proof recorded as an alternate proof under attempts/ by the post-merge job with the PR closed unmerged — the same treatment D-25 gives a losing racer. So the node never stops validating an operator's setup. F00 implements the first merge; the alternate-proof path is F07.
F00-Q7native_decide is rejected outright in F00. D-4's waiver path (justification, reviewer sign-off, permanent flag) needs the hazard-checker plumbing and a review record; it lands in F02.
F00-Q8Attestation identity. attestations/<id>.json where id is the merged PR number zero-padded, unique per graph repo and human-readable; the record carries the merge commit for the unambiguous reference.
F00-Q9Tutorial statement. ∀ p q : Prop, p ∧ q → q ∧ p, Lean core only, so a cold hosted runner builds it in seconds. The fixture graph's root is (p ∧ q) ∧ r → r ∧ (q ∧ p) over interior nodes for swap and reassociation, so path checks and a three-node dependency shape are exercised.
F00-Q10lean4checker is leanchecker. Found at T2 (2026-09-08): the leanprover/lean4checker repository is deprecated; the same program has shipped inside every Lean toolchain since v4.28.0 as leanchecker. The gate runs leanchecker --fresh from the pinned toolchain and installs nothing else; wherever this spec or D-4 says lean4checker --fresh, that binary is meant. The pin is leanprover/lean4:v4.33.1, latest stable at T2. Also observed: a proof by native_decide shows up in #print axioms as an axiom named <decl>._native.native_decide.ax_<n>, so the step-5 axiom set alone detects it (R6).
