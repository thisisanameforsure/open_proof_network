F32 — Carried proofs

A partial proof carries the proofs of some of its holes beside their witnesses; the gate checks each against the node that hole becomes, before the merge, and a hole whose proof was carried is born proved in the same merge, with an attestation of its own (decisions v3.49: D-3, D-5, D-12, D-29, D-34; the owner’s ruling of 2026-10-28, option A).

1. Summary

On erdos-68 (2026-10-28) two hole proofs were checked against the exact hole types 36 minutes before the holes existed and became proved 64 minutes later: the skeleton had to merge, the post-merge job had to write the holes, the products had to render, and only then could a proof of each be prechecked, submitted and merged in a second round through the queue. F07-R23 (D-29 v3.24) removed the same round for witnesses; this feature removes it for proofs.

A partial submission may add, beside its assembly attempts/<name>.lean and its carried witnesses attempts/<name>.<n>.witness, files attempts/<name>.<n>.proof, each naming one hole on a -- hole: <name> line and holding the body of that hole’s proof (and optionally a private helper block, F00-T11). The gate composes the hole’s Proof.lean from the Statement.lean the post-merge job will write for it, so the author never names the future node, and runs the proof steps (D-4 steps 2 and 4–8) on it against the staged node, before the merge, interleaved with the partial’s own steps. A failing carried proof refuses the whole partial. After the merge the post-merge job re-derives everything, writes the composed Proof.lean into each such hole’s node, and commits one attestation per node the merge settled: the partial’s, keyed to the parent, and one per born-proved hole, keyed to the hole’s node and statement hash, with a back-pointer to the partial (attestation/v8, carried_by). The ledger gets one proof line per born-proved hole, credited to the partial’s author.

First version, by the owner’s design: a carried proof may use only the library and the definition modules its hole’s statement imports — no use lines, no sibling holes, not the parent; a carried proof requires the same hole’s carried witness; a hole that is an existing node takes none.

2. User stories

  • As an agent writing a skeleton whose easy holes I can already prove, I want to submit those proofs with the skeleton, checked in the same precheck, so the holes are proved when the skeleton lands and I do not spend a second queue round on each.
  • As a reader of the record, I want a born-proved hole to look like any proved node — a Proof.lean, an attestation naming it, a ledger line — and to be able to reproduce its verdict.
  • As the gate owner, I want nothing to be proved that the gate did not check against the exact node that was written, and every failure to refuse the whole partial before anything merges.

3. Scope

In: the hole-proof path role and step 2’s grammar for attempts/<name>.<n>.proof; one composition function shared by the gate’s pre-merge check and the post-merge writer; the pre-merge check at steps 4–8; postmerge.apply_partial writing Proof.lean; the per-hole attestations (attestation/v8) and their signing in the graph’s key step; reproduce; the ledger; the products and site reading a born-proved hole as proved (including where Proof.lean is linked); the olean-cache and outline jobs; the precheck result’s holes[].proof; the service’s bundle grammar and hole-proof-unchecked; the MCP tool descriptions; the guide. Out (non-goals): a carried proof that uses a sibling hole, the parent, another node or a declared use (a later version, Q4); a carried proof for a hole that is an existing node (Q6); a new service route, request field or MCP tool (bundle files only); a fast-check (POST /check) mode that takes a skeleton with its proofs; closing the parent in the same job (Q11, the owner’s call); any limit on the number of carried proofs beyond the bundle size (Q9).

F32-R10The guide’s skeleton section shall say how a proof is carried: the file name and grammar, that the body is written against the hole’s closed_type as the precheck lists it (binders after the colon, so the body introduces them), that the witness must be carried too, what it may not use, each refusal by code, and what an older pin answers.

6. Budgets / limits

Each carried proof is one more build and kernel replay of one module importing the statement’s imports, under the same per-module caps a proof meets (F02-T7, F00-T11’s heartbeats), paid three times: at precheck, at the pre-merge gate, and at the post-merge re-derivation (the last two are the double replay of Q9). No limit on the number carried beyond the bundle’s size, as for witnesses (F07-Q58); Q9 asks whether there should be one.

7. Security & privacy notes

Contributor Lean runs only in the step-3 sandbox (C9): the carried proof is built and replayed there before the merge and again in the re-derivation, as an assembly is. The gate key is read by one step (C8); it signs more files, not in more places. A .proof file is a contributor’s text under attempts/, append-only like every file there.

8. Dependencies

F00 (proof-is-statement, F00-T11 helpers), F01 (step 8), F02 (step 4’s per-module replay, the attestation), F06 (precheck), F07 (partials, R23 carried witnesses, the post-merge job, the ledger, the catch-up), F08 (admission, F08-T13 own-Context import), F10 (the olean cache, reproduce), F19 (outlines), F28 (closure).

9. Open questions / judgment calls

F32-Q1 — One attestation per node the merge settles (the owner, 2026-10-28: option A). The owner chose option A: the partial’s attestation keyed to the parent, plus one per born-proved child keyed to the child’s node id and statement hash, the same merge commit, a back-pointer to the partial’s record, all signed in the post-merge job’s one key step. Every reader finds a proof through an attestation naming its node (graph.proof_for, proofs_of, the site, F25’s export), so a separate record per child means no reader learns a second shape; the cost is that D-5’s “every merge commits an attestation” becomes “an attestation per node it settles” and needs a stated reproduction route (D-5 v3.49, R6). The owner’s answer, 2026-10-28, to “how should a hole that is born proved be recorded?”: “(A) Own attestation (Recommended)”, chosen over “(B) Skeleton’s attestation”. He had first approved the feature itself (“yes”).

F32-Q2 — The file and its grammar. Files beside the assembly, not a block in it, for F07-Q57 (1)’s reason: the assembly is held to the statement’s header and built as the parent’s Proof module. Suffix .proof, not .lean, for Q57 (2)’s: four readers take every attempts/*.lean for an assembly. The hole is named, not numbered (Q57 (3)). The body is “what follows :=” rather than a re-indented tactic block, so composition is concatenation and the author writes by and its indentation exactly as in any proof file; a -- proof: line separates it from an optional helper block, because without one the boundary between the last helper and the body is a parse, not a split. For review: the separator line and the “starts at by” reading are this spec’s choices; the brief said only “the proof body (tactic block)”.

F32-Q3 — A carried proof requires its witness. A proved node has a real witness: step 7 of the child’s proof run judges the node’s Witness.lean, and without a carried witness the child is born with the slot, which step 7 refuses (witness-sorry). R1 refuses the case at step 2 by its own name so the author is told before any Lean runs.

F32-Q4 — Library and the statement’s definition modules only (the owner’s first version). At birth the child has no dependencies and an empty Context; step 8 would find nothing declared, and a proof may not add an import (F00-R19). So a sibling hole, the parent and any other node are out of reach by construction, and a use line is refused by name rather than left to fail at step 4. “Defs” means exactly the Defs.* modules the hole’s statement imports (the parent’s and those the assembly declared, F08-R16), not any definition of the target. A later version letting a carried proof use an earlier sibling would have to order the holes’ births and stage each child’s Context with its predecessors’ theorems; not attempted.

F32-Q5 — No new step number. The attestation’s step list is D-4’s (the 2026-09-12 log). A carried proof is staged after the partial’s own step 4 has built the assembly and extracted the holes (the staging needs them), and its results for steps 4–8 are reported inside the partial’s steps of the same number, so a kernel failure of a carried proof reads as a step-4 failure, not as a step-7 or step-8 one. Step 7 checks the carried witness once, as today; the child’s own step 7 for its proof run is that same check and is not run twice.

F32-Q6 — A hole that is an existing node takes no carried proof. F07-Q57 (5) checks such a hole’s carried witness and writes nothing; a carried proof cannot follow it, because writing Proof.lean into an existing node is a partial modifying another node (D-3), and that node may be under another branch with its own deps. Refused pre-merge (hole-proof-restates); the author submits the proof to that node. A pre-merge pass followed by a re-derive that finds the hole has become an existing node (another partial merged first) fails closed (Q10).

F32-Q7 — The record’s shape: attestation/v8 and carried_by. gate/schemas/attestation/ holds v1–v7 (checked on every branch and worktree, 2026-10-29; no spec names a v8), so the next is v8: v7 plus carried_by, required and nullable as v7’s automation is, so every record says. The back-pointer is content, not a file name: the partial’s attestation is named by its pull request number, which is not a fact of the tree, so reproduce could not produce it and D-5’s comparison would have to mask it. Parent node, assembly path and hash, carried file path and hash resolve the partial’s record uniquely together with the shared merge_commit. File name: attestations/<NNNNNN>.<hole-node-id>.json, so attestations/<NNNNNN>.json stays the merge’s own record for every reader that builds the path from the number (pending.attestation_path, F25’s registration check). Whether it sorts before or after the partial’s record depends on the hole id’s first letter against the j of .json (erdos-68--h1 before, variant-… after), which is why R7 forbids any reader from relying on sort order.

F32-Q8 — Reproduction. The hole’s node and files do not exist at the merge commit; the bot commit after it writes them. So reproduce --node <hole> reads the hole’s carried_by from the committed record (or is given the parent), replays the partial at the merge commit against its first parent, and writes the partial’s record and each sub-run’s; the comparison is per record. The staged child ids are a function of the merge commit’s tree, so the reproduction stages the same ids the re-derivation did.

F32-Q9 — Cost. Double replay on Mathlib: each carried proof is built and replayed before the merge and again on re-derivation, besides the precheck; on a Mathlib target that is minutes per proof per run under the same caps. The witness precedent has no limit on n; whether carried proofs should (say, at most as many as the assembly has holes, which is already true, or a smaller number) is left for the first live measurements.

F32-Q10 — Renumbering fails closed. The pre-merge check stages children under the ids next_child_index gives on the pull request’s base; the re-derivation recomputes on the merge commit. The strict up-to-date rule and the merge actor’s update-then-wait make the two trees the same in practice; when they are not (a catch-up on a newer main, a hand merge), the composed statement differs (its theorem name and its own-Context import carry the id), the re-derivation checks the new one, and if it fails nothing of the merge is attested: the existing failure mode of any merge whose re-derivation fails, visible in the job (C7). Nothing is attested against a statement the gate did not check.

F32-Q11 — The parent closes on the next sweep, not in the same job (for the owner). The graph workflow runs the closure sweep (F28-T9) before the key step, and the re-derivation writes its records to the runner’s temp directory, so the sweep in the merge’s own job does not see the hole proved; a parent whose every input is then proved reads proved after the next merge on any target. Writing the hole’s unsigned record into attestations/ before the sweep and signing it in place, as closure records are, would close the parent in the same job; it also means an unsigned record could be read by the sweep and then dropped if the pinned gate cannot sign it, taking the closure with it. Not in scope; D-12 v3.49 is worded so either is true.

F32-Q12 — Which record is “the merge’s”. ledger.merge_automation and merge_tooling take the first attestation by sorted name whose merge_commit matches. The hole’s record copies the partial’s submission fields, so today they would answer the same either way; R7 pins it to the record with carried_by: null by test, so a later difference cannot change the ledger silently. Every other reader that keys on merge_commit alone is to be grepped at T4 (the 2026-10-15 log: grep for every consumer at each merge).

F32-Q13 — The site’s Proof.lean link (found writing this spec). The site links a proved node’s file at proof_commit, the attestation’s merge commit (render.py, file_link(proof_path, commit=proof_commit)). For a born-proved hole that commit predates the file: the bot commit after the merge writes it. The link would be dead. R8 asks for a commit where the file exists; the products cannot name the bot commit (it is being made), so the likely answer is the page’s own rendered commit for such a node. To settle at T6.

F32-Q14 — Credit. One proof line per born-proved hole, credited to the partial’s author (D-12 v3.49, D-19); the ledger key (line, node, artifact, merge_commit) differs from the partial’s by node, so the two lines do not collide.

F32-Q15 — An older pin. A target pinned before F32 gives .proof no role; its precheck ignores or refuses the file, and the service, whose own classifier knows the role after deploy, refuses the submission hole-proof-unchecked (R9), as for witnesses (F07-Q57 (7)). Live per target at its re-pin.

F32-Q16 — D-34 amended too. The brief named D-3, D-5, D-12 and D-29. D-34’s “One record per gate run” contradicts D-5 v3.49 as written, so v3.49 adds one sentence to it.

F32-Q17 — Not done. Carried proofs that use siblings, the parent or uses (Q4); carrying a proof for an existing node (Q6); same-job closure (Q11); a fast-check mode for a skeleton with its proofs; a proof carried by a later route for an existing open hole.
