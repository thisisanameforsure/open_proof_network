F20 — Drafted explainers and steward revisions

Every merged proof gets a machine-drafted explainer by default, anchored to its outline and labelled unverified. A steward then improves it version by version (create, revise, withdraw, sign), and nothing is ever edited in place.

1. Summary

The owner's model, 2026-10-04: “by default we will get some translation, but as the steward goes through it, they will improve it.” The protocol already has the slot. An explainer (D-3) is prose about a merged proof: content-hashed, attributed to a human author and any drafting model (D-23), immutable, labelled unverified (D-36), and since v3.17 signable by a steward or curator as a comprehension claim that alone counts toward digestion (D-33). Three things are missing:

  • Versions. “A correction is a new entry”, but nothing says which entry it corrects, and the site shows whichever explainer/*.md sorts first by hash (site/opn_site/model.py, explainer_files[0]).
  • Anchors. Nothing ties a paragraph to the Lean it describes.
  • A first draft. The live graph holds no explainer on any of its 114 nodes.

F20 adds them:

  • explainer/v1: front matter naming the proof described and the version superseded, with sections that name F19's outline steps.
  • Linear version chains, and withdrawal of a version by the v3.27 withdrawal record.
  • Digestion counted on a chain's current version.
  • A service route and MCP tools, so a steward's agent can revise.
  • A local command for stewards who prefer a hand-opened pull request.
  • A node page that shows the current version beside the steps it describes, with its history.
  • The drafter: a network workflow that writes a draft from the outline (never from the source text) and opens it as an ordinary explainer pull request attributed to the drafter and its model.

The research behind it is docs/reports/Lean proofs for mathematicians.md. The only measured pipeline that generates prose from proofs reached about 89% of steps correct on undergraduate calculus, with one grader. Nothing has been measured on research-level proofs. So a draft is a starting point, never an account. The project's own rule stands: “A model may draft; only a human signature counts.”

F20 changes no verdict. It needs decisions v3.28 parts (ii) to (v) (F19-Q1) applied first, plus two credentials only the owner can create (Q7).

2. User stories

  • As a steward, I want a drafted account already waiting on each proof of my problem, anchored to the steps it describes, so that my work is correcting and deepening rather than starting from a blank page.
  • As a steward, I want to revise an explainer, see my revision become the one shown, withdraw a version that is wrong, and sign the version I can stand behind, all without anyone's text ever being overwritten.
  • As a steward working through an agent, I want to do all of that through the MCP, with the outline's step ids in hand.
  • As a reader, I want to see whether the account in front of me was drafted by a model, written by a person, or signed by someone who can explain the proof, and to see what changed between versions.
  • As the owner, I want the drafter's spend capped and reported, and no draft opened that fails the checks a human's would fail.

3. Scope

In:

  • The explainer/v1 schema, its mode checks and the cited-name warning.
  • Version chains, withdrawal of explainers, and the derivation of each chain's current version.
  • Digestion on current versions.
  • POST /explainers, its pre-flight and the MCP tools; get_node's outline and chains.
  • The steward's local command.
  • The node page's explainer slot, history and diff.
  • The drafter library and its workflow, with a cost measurement.
  • The guide and the Docs page.
  • The live re-pin and a first steward revision walked end to end.

Non-goals:

  • Machine prose anywhere but the explainer slot (the owner's decision (b), D-36): no auto-translation panel, no generated captions on the outline.
  • A web editor or any input on the site (D-36 forbids it). The page links to the guide's revision section; editing goes through git or the service (D-28).
  • Drafting the whole live graph in this feature. T10 drafts three proofs and measures them, and the backfill of the remaining proofs is the owner's call on that cost (Q8).
  • Checking an explainer's mathematics. Nothing reads an explainer for truth (D-3); the anchor checks say which steps a section describes, never that it describes them correctly.
  • D-32 write-ups, which remain the steward's paper or note.

4. Requirements

IDRequirement (EARS)
F20-R1The system shall accept an explainer/v1 file: Markdown with front matter validated against its schema, naming the target, the node, the proof (the hash of the merged artifact described, its Proof.lean or an alternate), supersedes (an explainer hash or null), author (a login or pseudonym, null for a draft), drafter (null, or the drafter's name with the model, the model version and the outline's gate commit), the date and the licence. Its body shall be sections under level-2 headings; a section may name outline steps as {steps: s3 s4.1} at the end of its heading (Q2); the first section may name none. An explainer without this front matter (every explainer filed before F20) shall stay valid and be shown unanchored.
F20-R2If an explainer names a proof that is not a merged proof artifact of its node, or a step id absent from that proof's outline, or names any step when the proof has no outline, then the gate shall refuse it by name (explainer-proof-unknown, explainer-step-unknown); the check reads files and runs no Lean, so an explainer still needs no gate run (D-3).
F20-R3When a section cites a Lean name in backticks that occurs in none of the constants its named steps use, the gate shall emit the warning explainer-name-unanchored and not refuse (requirement C; untested as a detector, so it informs and does not block).
F20-R4If an explainer supersedes a hash that is not an explainer of the same node and proof, or one already superseded or withdrawn, then the gate shall refuse it (explainer-not-head, naming the current head). If it supersedes a version carrying a valid signature and its pull request is not by an active steward of the target or a listed curator, then the gate shall refuse it (explainer-signed-supersede); anyone may start a new chain instead.
F20-R5The system shall accept a withdrawal record (the next version of withdrawal, v3.27's record) naming one explainer version, from that version's author, an active steward of the target or a listed curator, with a reason; every reader shall read a withdrawn version as absent from its chain while the file stays in the tree.
F20-R6The products shall publish, per node and proof, each explainer chain: its versions in order, each with its hash, author or drafter, date, signatures and withdrawn flag, and its current version (the latest not withdrawn, or none). Chains shall be listed in record order, ranked by nothing (D-25).
F20-R7A node shall count toward a target's explained digestion state only while the current version of an explainer chain on its first proof carries a valid signature (v3.28 (iv)); signatures on superseded or withdrawn versions shall count for nothing.
F20-R8The service shall provide POST /explainers (an explainer, new or superseding) and POST /explainers/withdrawals, token-authenticated, each running R1–R5's checks as a pre-flight and refusing before any pull request opens (the owner's ruling of 2026-09-24), else opening an append/ pull request the merge actor merges; the MCP shall offer submit_explainer and withdraw_explainer, and get_node shall return the proof's outline and each chain, all under the untrusted-data demarcation and the bijection test (D-28).
F20-R9The system shall provide a steward's command, opn-gate explainer revise <target> <node>, that writes the current version to an editable file with supersedes filled in, and opn-gate explainer file <path>, that checks R1–R4, names the file by its hash and places it, so that a hand-opened pull request is right the first time.
F20-R10The node page shall show each chain's current version under D-36's fixed label, with a provenance line (machine-drafted by <model>, written by <author>, signed by <signer>). Each anchored section shall appear beside the outline steps it names. The page shall link to every earlier version with a diff to its predecessor, list withdrawn versions as withdrawn and never hide them, and give the guide's revision section as the way to improve the account.
F20-R11The drafter shall write a draft from a proof's outline/v1 (F19), never from the artifact's source text. It shall condition each section on the steps' claims and goals, summarise along the step tree, open with the idea and the method (requirement G), say “routine” of every automation-closed step rather than invent reasoning (D), use a result's standard name only where the outline records it (E), and for a hole node open with what the hole states (F19-Q8). It shall call the model through opn_gate.models, with the outline under the untrusted-data demarcation.
F20-R12Before opening a draft, the drafter shall run R1–R4 on it and require every non-first section to name at least one step. If a draft fails, then it shall regenerate once, and if that fails too, record the proof as not drafted with the reason and open nothing.
F20-R13When a merge adds a proof with an outline and no explainer chain, the drafter workflow shall be dispatched; it shall also run by hand on a named list. It shall stop at a per-run cap of proofs and a per-run token budget (config, C6), and on a provider error (429, spend limit, refusal) it shall stop and report what it left undrafted. A partial run is never a silent one.
F20-R14A draft shall earn no ledger line. A human version earns on the write-up line as any explainer does (D-19), credited to its author alone; superseding earns the superseding author nothing of the superseded version's credit.

6. Budgets / limits

  • Drafting cost per proof is unmeasured. T10 measures three, and nothing drafts in bulk until the owner has read that cost (Q8). The per-run caps (OPN_DRAFTER_MAX_PROOFS, OPN_DRAFTER_TOKEN_BUDGET) default to 5 proofs and 500k tokens.
  • An explainer stays an append. It runs no Lean, merges in the append lane, and never waits for a post-merge job (F07-T55–T57).
  • The anchor checks read the committed outline. If the outline is missing (F19-R5), an explainer can still be filed, unanchored.

7. Security & privacy notes

  • Two new credentials (Q7). Each has one home, to be entered in C8 before T9 ships:
    • The model key for the drafter workflow (OPN_MODEL_API_KEY, as F12's commands read it), an Actions secret on the network repository read by one step.
    • The drafter's service token, a write token like any contributor's (D-19). Losing either costs drafts; leaking the token lets its holder open explainer pull requests, which assert nothing (D-3).
  • The drafter is not trusted. Its input contains Lean names chosen by contributors, so the outline goes to the model under the untrusted-data demarcation. Its output is checked by the same rules as a human's, rendered escaped, and labelled machine-drafted.
  • Signatures stay F15's. They are signed by the signer's own key, over one version's hash. A revision cannot inherit a signature.
  • Withdrawal and supersede are gated by role (steward, curator, author), using F15's real_identities and v3.27's curator check. No new identity mechanism.

9. Open questions / judgment calls

IDCall made — for review
F20-Q1Decisions v3.28 (ii) to (v), drafted in F19-Q1, for the owner's approval. F20 builds nothing that depends on them until they are applied (T1).
F20-Q2Anchor syntax. Section anchors are written at the end of the heading: ## The bound on q {steps: s3 s4.1}. This keeps the anchor beside the text it governs, survives copy and paste in an editor, and reads acceptably as plain Markdown. A front-matter list keyed by section index was rejected because it breaks silently when a steward reorders sections.
F20-Q3Chains are linear. Superseding a version that is not the head is refused, so the current version needs no clock. The 2026-09-19 lesson was to ask who wrote the clock, and here nobody has to. Two stewards revising at once is a race the second loses with a message naming the new head, as racing proofs do (D-25 v3.21).
F20-Q4Several chains on one proof are all shown, in record order. A second author who does not want to supersede can start a chain. Choosing one to feature would be ranking (D-25).
F20-Q5Digestion follows the current version. An edit after signing drops the node to unsigned until it is signed again. That is published state matching actual state (the owner's first principle). The alternative, counting any signature in the chain, lets a signature vouch for text its signer never saw.
F20-Q6The drafter is a named identity, opn-drafter, holding a contributor token rather than a privileged one. Its pull requests are appends like anyone's, and the merge actor needs no change. It appears in the ledger with no entries (R14).
F20-Q7Credentials are the owner's. The model key on the network repository and the drafter's token. Until they exist, the workflow dry-runs and keeps its report (the F12-Q16 shape), so a missing credential never reads as a passing run.
F20-Q8Bulk drafting is the owner's call on T10's numbers. About 74 proofs are live. After T10 reports per-proof cost and his reading of three drafts, he chooses between drafting everything, drafting on demand only, or drafting only the closures of resolved targets. The workflow supports all three through its named list.
F20-Q9Dispatch, not a schedule. The post-merge job already holds the site dispatch token, which can start any network workflow (C8). The drafter is dispatched the same way, because a cron on GitHub Actions is a hope (2026-09-13).
