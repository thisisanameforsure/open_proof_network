F20 — Glosses and explainers, drafted then improved

Every Lean file on the graph gets a mathematical version: a gloss for each statement, witness, relation and definition module, and an explainer for each proof. Each is machine-drafted by default and labelled unverified. A steward then improves it version by version (create, revise, withdraw, sign), and nothing is ever edited in place.

1. Summary

The owner, 2026-10-04: “by default we will get some translation, but as the steward goes through it, they will improve it”, and later the same day, “all lean code should have a mathematized version, not just whole proofs.” The protocol has a slot for proofs only. An explainer (D-3) is prose about a merged proof: content-hashed, attributed to a human author and any drafting model (D-23), immutable, labelled unverified (D-36), and since v3.17 signable as a comprehension claim that alone counts toward digestion (D-33). D-3 refuses one on an unproved node. So the Lean a frontier reader most needs to read has no home for words. That covers open nodes, holes, variants' relations, witnesses and definitions. The site shows informal text only for a target's root, from its curated informal: field.

Four things are missing:

  • Coverage. Nothing exists for any Lean file but a proof. The live graph holds 114 statements, 23 relations, 3 definition modules and about 74 proofs.
  • Versions. “A correction is a new entry”, but nothing says which entry it corrects. The site shows whichever explainer/*.md sorts first by hash (site/opn_site/model.py, explainer_files[0]).
  • Anchors. Nothing ties a paragraph to the Lean it describes.
  • A first draft. The live graph holds no explainer at all.

F20 adds them:

  • gloss/v1: prose about one Lean file that is not a proof. It names the file and the hash of the exact text it describes, and is accepted on a node of any status.
  • explainer/v1: front matter naming the proof described, with sections that name F19's outline steps.
  • For both: linear version chains through supersedes, withdrawal by the v3.27 record, and signatures on one version.
  • Digestion counted on an explainer chain's current version.
  • One service route family and two MCP tools, so a steward's agent can revise.
  • A local command for stewards who prefer a hand-opened pull request.
  • A gloss beside every block of Lean the site prints, with its history.
  • The drafter: a network workflow that drafts each new file's gloss when a merge creates it, and each proof's explainer from its outline, and opens them as ordinary pull requests attributed to the drafter and its model.
  • The backfill: every Lean file already on the graph translated, checked by a coverage report that names every file and its words or the reason they are missing (Q8, R20–R21).

Why a model writes drafts, and why only drafts: the research (docs/reports/Lean proofs for mathematicians.md) found one measured pipeline for prose from proofs, at about 89% of steps correct on undergraduate calculus, with one grader. For statements, back-translation wrongly passes about a third (Herald's audit; D-9 v3.12). A model is the only way every file gets words by default. Its words must be a record that names the model, sits under an unverified label, and can be corrected and signed. They can never be a derived product: model output is not reproducible (D-35), and it must not borrow the kernel's credibility. The project's rule stands: “A model may draft; only a human signature counts.”

F20 changes no verdict, no status and no fidelity grade. It needs decisions v3.30 parts (ii) to (v) and (vii) (F19-Q1) applied first, plus two credentials only the owner can create (Q7).

2. User stories

  • As a mathematician browsing the frontier, I want each open statement in words beside its Lean, so that I can see what is being asked without reading Lean.
  • As a reader of a decomposition, I want each hole, witness and relation in words, so that I can follow how a problem was broken up.
  • As a steward, I want drafted words already waiting on every file of my problem, anchored to what they describe, so that my work is correcting and deepening rather than starting from a blank page.
  • As a steward, I want to revise any gloss or explainer, see my revision become the one shown, withdraw a version that is wrong, and sign the version I can stand behind. Nobody's text should ever be overwritten.
  • As a steward working through an agent, I want to do all of that through the MCP.
  • As a reader, I want to see whether the words in front of me were drafted by a model, written by a person, or signed, and whether they describe the Lean as it is now.
  • As the owner, I want the drafter's spend capped and reported, and no draft opened that fails the checks a human's would fail.

3. Scope

In:

  • The gloss/v1 and explainer/v1 schemas, their mode checks and the cited-name warning.
  • Version chains for both, withdrawal, gloss signatures, and the derivation of each chain's current version.
  • Digestion on current explainer versions.
  • The routes, pre-flight and MCP tools, and get_node's outline, glosses and chains.
  • The steward's local command.
  • Glosses beside every Lean block on the site, plus explainer history and diffs.
  • The drafter library and its workflow, with a cost measurement.
  • The guide and the Docs page.
  • The live re-pin and a first steward revision walked end to end.

Non-goals:

  • Machine prose outside a gloss or explainer record. No generated captions inside F19's outline and no product field holding model text. Every word a model writes is a committed record with its model named (D-35, D-36). The owner revised decision (b) on 2026-10-04 to cover every Lean file; this boundary is what kept.
  • Replacing a root's curated informal statement. A target's informal: statement is the one its fidelity grade was assigned against (D-6, D-9), and it stays the root's words of record. The drafter writes no gloss of a root (Q11).
  • Any change to fidelity. A signed gloss is not a fidelity certificate and changes no grade (D-9).
  • A web editor or any input on the site (D-36). Editing goes through git or the service (D-28).
  • Checking prose for mathematical truth. Nothing reads a gloss or explainer for truth (D-3). Anchors say what a passage describes, never that it describes it correctly.
  • Glosses of annexes and postmortems, which are prose already. (A merged partial assembly is Lean and is covered: it gets an explainer drafted from its outline, F19-R1.)

4. Requirements

R1–R9 are the records and their rules; R10–R12 the service and the steward's tools; R13–R14 the site; R15–R18 the drafter; R19 credit.

IDRequirement (EARS)
F20-R1The system shall accept a gloss/v1 file: Markdown with front matter validated against its schema, naming the target and the subject. The subject is a kind (statement, witness, relation or definition), the node or definition module, and lean_hash, the SHA-256 of the Lean file's text described. The front matter also names supersedes, author, drafter, the date and the licence, as in R2. A node's gloss lives at nodes/<id>/gloss/<hash>.md and a definition module's at targets/<id>/gloss/<hash>.md. It is accepted on a node of any status, by the path check alone, with no gate run.
F20-R2The system shall accept an explainer/v1 file: Markdown with front matter naming the target, the node, the proof (the hash of the merged artifact described: its Proof.lean, an alternate, or a merged partial assembly), supersedes (an explainer hash or null), author (a login or pseudonym, null for a draft), drafter (null, or the drafter's name with the model, the model version and the gate commit of its input), the date and the licence. Its body shall be sections under level-2 headings; a section may name outline steps as {steps: s3 s4.1} at the end of its heading (Q2); the first section may name none. An explainer without this front matter (every explainer filed before F20) shall stay valid and be shown unanchored.
F20-R3If a gloss's lean_hash is not the hash of its subject's file as the tree holds it at merge, then the gate shall refuse it (gloss-subject-mismatch, naming the current hash). When a subject's file later changes (a witness filled, a definition revised), every gloss of the earlier text shall be read as describing an earlier version, and never shown as describing the current one.
F20-R4If an explainer names a proof that is not a merged proof artifact of its node, or a step id absent from that proof's outline, or names any step when the proof has no outline, then the gate shall refuse it by name (explainer-proof-unknown, explainer-step-unknown). The check reads files and runs no Lean.
F20-R5When an explainer section cites a Lean name in backticks that occurs in none of the constants its named steps use, the gate shall emit the warning explainer-name-unanchored and not refuse (requirement C; untested as a detector, so it informs and does not block).
F20-R6If a gloss or explainer supersedes a hash that is not a record of the same subject (the same file, or the same proof), or one already superseded or withdrawn, then the gate shall refuse it (record-not-head, naming the current head). If it supersedes a version carrying a valid signature and its pull request is not by an active steward of the target or a listed curator, then the gate shall refuse it (signed-supersede). Anyone may start a new chain instead.
F20-R7The system shall accept a withdrawal record (the next version of withdrawal, v3.27's record) naming one gloss or explainer version, from that version's author, an active steward of the target or a listed curator, with a reason. Every reader shall read a withdrawn version as absent from its chain while the file stays in the tree.
F20-R8The system shall accept a gloss signature (gloss-signature/v1, on F15's signed-record seam) from an active steward of the target or a listed curator. It affirms one fixed sentence: I have read this against the Lean it names, and it says what the Lean says. A gloss signature shall change no status, grade or digestion state (Q12). Explainer signatures stay F15's.
F20-R9The products shall publish each gloss and explainer chain per subject: its versions in order, each with its hash, author or drafter, date, signatures, withdrawn flag and (for a gloss) whether it describes the current text; and its current version, the latest not withdrawn. Chains shall be listed in record order, ranked by nothing (D-25). A node shall count toward explained only while the current version of an explainer chain on its first proof carries a valid explainer signature (v3.30 (iv)).
F20-R10The service shall provide POST /glosses (a gloss or explainer, new or superseding; a proof subject is filed under explainer/) and POST /glosses/withdrawals. Both are token-authenticated and run R1–R7's checks as a pre-flight, refusing before any pull request opens (the owner's ruling of 2026-09-24); otherwise they open an append/ pull request the merge actor merges. Signatures stay with the signer's own key, filed by hand or by the local command, as F15's are.
F20-R11The MCP shall offer submit_gloss and withdraw_gloss, paired with those routes by the bijection test. get_node shall return the node's outline, each gloss chain of its files and each explainer chain, all under the untrusted-data demarcation (D-28).
F20-R12The system shall provide a steward's command, opn-gate gloss revise <target> <subject>, that writes the current version of a gloss or explainer to an editable file with supersedes and lean_hash filled in. It shall also provide opn-gate gloss file <path>, which checks R1–R6, names the file by its hash and places it, and opn-gate gloss sign, which writes a gloss signature as opn-gate explainer sign writes an explainer's.
F20-R13Wherever the site prints Lean, it shall print the current gloss of that file beside it, or the recruiting cue where there is none. That covers the node page's statement, witness and relation; the problem page's selected-statement card; the reading view (F19-R8); the frontier page (the gloss's first sentence); a node's dependencies; and each definition module. Each gloss shall carry a provenance line: machine-drafted by <model>, written by <author>, or read against the Lean by <signer>. A gloss of an earlier text shall be shown only in history, labelled so. For a root, the curated informal statement and its fidelity state shall come first, and any root gloss after it, labelled unverified.
F20-R14The node page shall show each explainer chain's current version under D-36's fixed label, with its provenance line and each anchored section beside the outline steps it names. For every gloss and explainer, the site shall link every earlier version with a diff to its predecessor, list withdrawn versions as withdrawn and never hide them, and give the guide's revision section as the way to improve the words.
F20-R15The drafter shall draft a gloss of the statement of every non-root node, of the witness and the relation (if any) of every node, roots included, and of each definition module, when the merge that creates the file lands. It shall work from the file's text at its lean_hash and the current glosses of the files it imports, never inventing a name the file does not use. It shall say in words what the Lean says, including every hypothesis, and add nothing about why it is true. It shall draft an explainer of each merged proof artifact (proof, alternate or partial assembly) from its outline/v1 (F19), never from the artifact's source text: conditioned on the steps' claims and goals, summarised along the step tree, opening with the idea and the method (G), saying “routine” of every automation-closed step rather than inventing reasoning (D), and using a standard name only where the outline records it (E).
F20-R16Before opening a draft, the drafter shall run the checks of R1–R6 on it, and for an explainer require every non-first section to name at least one step. If a draft fails, then it shall regenerate once, and if that fails too, record the subject as not drafted with the reason and open nothing.
F20-R17When a merge creates a Lean file or a proof that has no chain, the drafter workflow shall be dispatched; it shall also run by hand on a named list. It shall stop at a per-run cap of subjects and a per-run token budget (config, C6). On a provider error (429, spend limit, refusal) it shall stop and report what it left undrafted. A partial run is never a silent one.
F20-R18The drafter shall call the model only through opn_gate.models, with every piece of contributor-chosen text (Lean names, docstrings, comments) under the untrusted-data demarcation, and shall record the model, its version and the gate commit of its input in every draft.
F20-R19A draft shall earn no ledger line. A human version of a gloss or explainer shall earn on the write-up line (D-19), credited to its author alone; superseding a version earns its author none of that version's credit.
F20-R20The system shall provide opn-gate gloss coverage, which lists, for a graph at a named commit, every Lean file and merged proof artifact with its current gloss or explainer, or the reason it has none. Coverage is complete when every non-root statement, every witness, every relation and every definition module has a current gloss that describes its current text, and every merged proof artifact has an explainer chain with a current version. A root's statement is covered by its curated informal statement, and a Context.lean by the glosses of the statements it restates; the report says so per file rather than leaving it out.
F20-R21The system shall translate every Lean file on the live graph at the time of the backfill: the drafter run in batches under its caps until coverage reports complete. A subject left undrafted for a cause (an outline missing, a draft failing its checks twice, a provider error) shall be fixed and re-run, and the backfill is done only when no subject is left, or when each one left is recorded as an open defect with its cause and the owner has read the list (Q8).

6. Budgets / limits

  • Drafting cost is unmeasured. T11 measures seven drafts; from them the backfill's batch size and total spend ceiling are set and the projected total is reported to the owner before the first batch. The backfill itself is not optional (Q8). The per-run caps (OPN_DRAFTER_MAX_SUBJECTS, OPN_DRAFTER_TOKEN_BUDGET) default to 20 subjects and 500k tokens. A gloss is far smaller than an explainer: a statement is a few lines.
  • Glosses and explainers stay appends. They run no Lean, merge in the append lane, and never wait for a post-merge job (F07-T55–T57).
  • The drafter runs no Lean. A gloss is drafted from the file's committed text and an explainer from the committed outline. Where the outline is missing (F19-R5), the explainer is reported as not drafted, never drafted from the source.

7. Security & privacy notes

  • Two new credentials (Q7). Each has one home and must be entered in C8 before T9 ships:
    • The model key for the drafter workflow (OPN_MODEL_API_KEY, as F12's commands read it), an Actions secret on the network repository read by one step.
    • The drafter's service token, a write token like any contributor's (D-19).
    Losing either costs drafts. Leaking the token lets its holder open gloss and explainer pull requests, which assert nothing (D-3).
  • The drafter is not trusted. Its input contains contributor-chosen Lean names, docstrings and comments, so they go to the model under the untrusted-data demarcation (R18). Its output is checked by the same rules as a human's, rendered escaped, and labelled machine-drafted.
  • A signature is over one version's hash, by the signer's own key (F15's seam). A revision cannot inherit a signature, and a gloss of changed text keeps its signature only in history.
  • Withdrawal, supersede and signing are gated by role (steward, curator, author), through F15's real_identities and v3.27's curator check. No new identity mechanism.

9. Open questions / judgment calls

IDCall made — for review
F20-Q1Decisions v3.30 (ii) to (v) and (vii), drafted in F19-Q1, for the owner's approval. F20 builds nothing that depends on them until they are applied (T1).
F20-Q2Anchor syntax. Section anchors are written at the end of the heading: ## The bound on q {steps: s3 s4.1}. This keeps the anchor beside the text it governs, survives copy and paste, and reads acceptably as plain Markdown. A front-matter list keyed by section index was rejected because it breaks silently when a steward reorders sections. Glosses carry no step anchors: a gloss describes one whole file.
F20-Q3Chains are linear. Superseding a version that is not the head is refused, so the current version needs no clock. The 2026-09-19 lesson was to ask who wrote the clock, and here nobody has to. Two stewards revising at once is a race the second loses with a message naming the new head, as racing proofs do (D-25 v3.21).
F20-Q4Several chains on one subject are all shown, in record order. A second author who does not want to supersede can start a chain. Choosing one to feature would be ranking (D-25).
F20-Q5Digestion follows the current explainer version. An edit after signing drops the node to unsigned until it is signed again. That is published state matching actual state (the owner's first principle). Counting any signature in the chain would let a signature vouch for text its signer never saw.
F20-Q6The drafter is a named identity, opn-drafter, holding a contributor token rather than a privileged one. Its pull requests are appends like anyone's, and the merge actor needs no change. It appears in the ledger with no entries (R19).
F20-Q7Credentials are the owner's. The model key on the network repository and the drafter's token. Until they exist, the workflow dry-runs and keeps its report (the F12-Q16 shape), so a missing credential never reads as a passing run.
F20-Q8The owner's ruling, 2026-10-04 (third): all the Lean currently in the system is translated, “whatever it takes”. This replaces the earlier draft of this entry, which left bulk drafting to his call on T11's numbers. The backfill is now a requirement (R20, R21) and a task (T15). T11's numbers set its batch size and spend ceiling, not whether it runs. The live inventory at 2026-10-04: 114 statements (26 roots, each with a curated informal statement), 114 witnesses, 23 relations, 3 definition modules, 67 proofs, 7 alternates and 20 partial assemblies, so about 88 + 114 + 23 + 3 = 228 glosses and 94 explainers. Two things the ruling cannot buy: drafts are still unverified until a steward signs them, and the backfill still needs the two credentials (Q7). Anything merged after the backfill is covered by the dispatch (R17), and coverage shows any gap.
F20-Q9Dispatch, not a schedule. The post-merge job already holds the site dispatch token, which can start any network workflow (C8). The drafter is dispatched the same way, because a cron on GitHub Actions is a hope (2026-09-13).
F20-Q10The owner's ruling, 2026-10-04 (second): every Lean file has a mathematical version, not only proofs. This widens his decision (b) of the same morning, which had kept machine prose to the explainer slot. The boundary kept is that model text lives only in a committed, attributed, correctable record, never in a product (D-35). A gloss is a separate record from an explainer, not an explainer on an unproved node. D-3 refuses an explainer there for a reason that still holds: an explainer's signature is a digestion claim about a proof, and a statement has none to digest.
F20-Q11No drafted gloss of a root. A root's curated informal: statement is the text its fidelity grade was assigned against (D-9). A model gloss of the root's Lean is a back-translation, which D-9 v3.12 demoted to one input because about a third of its passes are wrong. Shown beside the statement of record, it would invite exactly the misreading the grade exists to prevent. A steward may still write one; it is shown after the curated statement, labelled unverified.
F20-Q12A gloss signature claims less than it might. Its sentence is that the signer read the words against the Lean and they agree. It is not a fidelity certificate: D-9 grades roots only, through its own QA pass, and interior nodes are exempt. So a signed gloss changes no grade and no state. Making signed glosses on a closure count toward something (a "statements read" state beside digestion) is a later decision for the owner, if readers want it.
