F05 — Identity and claims

The protocol service comes to life: POST /tokens under the D-19 identity rules, POST /claims and DELETE /claims/<id> per D-25, the live claim overlay on frontier.json, and the serverless foundation every later endpoint runs on.

1. Summary

F05 builds api/: a Starlette application deployed as one AWS Lambda function behind API Gateway, with DynamoDB for the operational tables D-35 names (tokens, claims, rate accounting). It issues write tokens to GitHub-proven identities (the account-free tutorial-proof path needs precheck and lands in F06), records advisory claims with declared TTLs inside published flat caps, auto-releases them on expiry, and serves GET /frontier.json — the committed file with the live registry overlaid, which is what list_frontier reads (D-35 v3.9). The service holds no authority: it opens nothing, signs nothing evidentiary, and can be rebuilt from the graph (D-35). Cites: D-19, D-22, D-23, D-25, D-26, D-28, D-35.

2. User stories

  • As an operator with a GitHub account, I want a write token in one browser round-trip, so my agent can claim nodes tonight.
  • As an agent, I want to claim a node with a TTL I choose and see who else has claimed it, so I can decide whether to race (D-25).
  • As the founder, I want every write rate-limited per identity with the policy published, so abuse is bounded without gatekeeping (D-19).

3. Scope

In: the Starlette app, config module, Store/GitHost/Clock seams with fakes, Lambda handler via Mangum; GitHub OAuth identity proof through the GitHub App; token issuance, hashing and bearer authentication; DCO acceptance at token creation (D-23 v3.9); pseudonyms; per-identity rate limits with the policy in info.json; claims with caps, expiry and history; GET /frontier.json overlay and GET /claims.json; the claims snapshot the post-merge job commits so F03's products carry it; CloudFormation for the stack; OIDC deploy workflow; deployed smoke test.

Non-goals:

  • Tutorial-proof (anonymous) tokens — F06, because the proof is a precheck.
  • Vouching identities, identity upgrades that raise limits — Stage 1 (D-19).
  • Any endpoint that writes to the graph — F07, F08. Bountied-node routing — Stage 3.
  • Ledger files — F07.

4. Requirements

IDRequirement (EARS)
F05-R1The system shall expose the api as one ASGI application with a Lambda handler; every route shall be declared in one table in opn_api.routes that names its D-35 row, so the bijection audit (F09) can read it.
F05-R2The system shall read secrets (GitHub App id, private key, client id and secret; token-signing secret) and configuration (table names, rate-limit policy, claim caps, graph repo) through opn_api.config only, from Parameter Store in deployment and from .env locally (C8), with documented defaults for every non-secret value (C6).
F05-R3When a browser opens GET /auth/github/start, the system shall redirect to GitHub's OAuth authorization for the App with a state nonce; when GitHub calls back with a code, the system shall exchange it, read the login and account-creation date, discard the GitHub access token immediately, and continue token issuance with proof kind github (D-23: the network never holds credentials).
F05-R4When identity proof succeeds, the system shall require a pseudonym (1–39 characters, [A-Za-z0-9-], unique, case-insensitive) and DCO acceptance (dco.version matching the current DCO text hash and dco.accepted: true), create an identity record {id, pseudonym, proof kind, proof reference, created}, and issue one opaque token shown once; the store shall hold only a salted hash of the token.
F05-R5When a request carries Authorization: Bearer <token>, the system shall resolve it to an identity in constant time or respond 401; write routes shall require it, read routes shall ignore it.
F05-R6The system shall enforce per-identity limits from config — invited-run defaults: 120 write requests per hour, 20 active claims, 1 token per GitHub login — and per-source limits on unauthenticated routes — default: 10 token starts per address per day — responding 429 with a Retry-After; the same policy shall be published in info.json rate_limit_policy (D-28 server_info).
F05-R7When POST /claims {node_id, ttl_hours?} is called, the system shall verify the node is present and claimable in the current frontier.json at the graph's main, clamp an undeclared TTL to the minimum and reject one above the maximum (invited-run defaults 1 h and 168 h, published as the D-25 flat caps), create a claim {id, node, identity, created, expires, released}, and return the receipt; multiple identities may hold claims on one node (D-25: racing permitted). Amended 2026-09-14 (T9, Q10): a node the frontier does not list is 404 node-unknown when no target's graph has it, 409 node-blocked with details {status, cause, unproved_deps} when its graph row is blocked (the message names the unproved dependencies, or POST /proposals/witness for a witness-missing hole; a proved dependency is never listed), and 409 node-not-open naming its status otherwise; a listed node with claimable: false is 409 node-not-claimable whose message explains each reason in the target's targets/index.json row (intake.explain) and whose details.not_claimable is that list.
F05-R8When DELETE /claims/<id> is called by the claim's holder, the system shall mark it released; by anyone else, respond 403; claims past expires shall be treated as released on every read without a background job (auto-release, D-25).
F05-R9When GET /frontier.json is called, the system shall fetch the committed frontier.json at main (cached by ETag, at most 60 s stale), overlay per node claims.active as [{pseudonym, expires}] for unexpired, unreleased claims and claims.history_count as all claims ever, and return it validating against frontier/v1; GET /claims.json shall return the registry alone in the same shape. Amended 2026-09-14 (T10, Q9): every committed file the service reads, by route or MCP tool, shares one freshness generation keyed on info.json's ETag — once per window the service revalidates info.json, and when it answers with a new ETag every other cached file revalidates by its own ETag on its next use; a marker that cannot be read invalidates nothing and each file serves its last good copy (C7).
F05-R10When the post-merge job runs, it shall fetch GET /claims.json, commit it as claims.json at the graph root, and F03's generator shall merge it into the committed frontier.json; if the service is unreachable the job shall keep the previous claims.json and log the failure (C7), never block a merge.
F05-R11The system shall log every request with method, route, identity id (never the token), status and duration; no request or response body above DEBUG (conventions §5).
F05-R12The system shall provision, via CloudFormation in api/infra/: the function (Python 3.13), the HTTP API, three DynamoDB tables (identities, tokens, claims) with on-demand capacity, the Parameter Store paths, an execution role limited to those tables and parameters, and a deploy role assumable only by this repo's api-deploy workflow via OIDC.
F05-R13If any table or parameter is missing at startup, then the function shall fail its health check with the missing name and serve 503, never a partial service (C7).
F05-R14When a body-taking write route receives a top-level key outside its allowlist, in a JSON or a form body, the system shall answer 400 unknown-field naming every such key and listing the accepted ones (details {unknown, accepted}) before any other effect; a key nested inside a field is that field's business and is not refused (T8, Q11).

6. Budgets / limits

  • p50 under 300 ms for claim and overlay routes from a warm function; cold start under 2 s.
  • Token: 32 random bytes, base64url; identity ids ULIDs; claim ids ULIDs.
  • Cost at Stage 0 volume: on-demand DynamoDB and Lambda, expected under a few dollars a month.
  • Request body: the api refuses any request body larger than OPN_API_MAX_BODY_BYTES (default 1 MiB, above F06 §6's 512 KiB bundle with room for its JSON envelope; C6) with a 413 body-too-large naming the cap, enforced once, in app.py's BodyCap middleware, before authentication, rate limiting or any parsing. The content type is not enforced (Q7).

7. Security & privacy notes

  • Stored per identity: pseudonym, proof kind, GitHub login (for github proofs) and created date. No email. Nothing else (C9).
  • The GitHub access token from OAuth lives in memory for one request and is never persisted or logged (D-23).
  • OAuth state nonces are single-use and expire in 10 minutes. Tokens can be revoked by the founder via a CLI against the store; revocation is a ledger matter only once credit exists (F07).
  • The service's own credential set is exactly C8 item 3; the function role has no permission beyond its tables and parameters.

8. Dependencies

  • F03 (required): frontier.json and the post-merge job. F00: schemas.
  • Packages (C5): starlette — the ASGI framework the MCP SDK (F09) requires anyway; one HTTP stack for api and MCP. mangum — pure-Python ASGI-to-Lambda adapter, the smallest way to run an ASGI app on Lambda without a running server. httpx — HTTP client for GitHub calls, and Starlette's test client needs it; also an MCP SDK dependency. Dev: boto3 for the network-tier tests (present in the Lambda runtime, not bundled). All pinned and locked.
  • GitHub App created by the founder on the personal account, installed on the graph and precheck repos; ids and keys into Parameter Store per C8.

F05-Q1Claims are advisory and non-exclusive (D-25: racing permitted), so the only thing a claim does is appear in the frontier with its holder and expiry. No endpoint refuses a submission for lack of a claim.
F05-Q2Rate-limit and TTL numbers are config defaults, not protocol; D-25 calls the caps "published" and D-19 says "rate-limited", neither fixes values. Mike chose the looser invited-run set on 2026-09-07 (double the first proposal, TTL cap one week) so a handful of operators never hit a wall; tighten on evidence. Published through info.json so a change is visible.
F05-Q3The committed claims.json snapshot is how D-35's "served back read-only in frontier.json" is honored deterministically: F03's generator needs its inputs in the repo to be reproducible. It is bot-owned and operational in origin, never evidentiary.
F05-Q6AC19's claim round trip needs graph content F05 does not own. The live graph holds one node and it is proved, so nothing is claimable and the deployed round trip cannot run — the service is correct, the graph is empty. The remedy is a second, unproved node, which is a mathematical act belonging to the graph (D-35) and to F11's intake, not to this feature. Recorded here so the criterion is closed deliberately rather than quietly reinterpreted.
F05-Q5The snapshot has its own schema, claims/v1, rather than reusing the frontier's inline claim shape: the post-merge job commits a whole document and the gate validates it before letting it near a product, so it needs a schema of its own (D-34). Adding it changed info.json's schema index, which the F03 goldens carry; they were regenerated in the same commit.
F05-Q4GitHub OAuth is a human flow. Agents get tokens through F06's tutorial proof; a person can also do the OAuth flow once and hand the token to their agent, which is what D-19 means by the agent acting under its operator.
F05-Q7The coverage sweep's findings, and the body cap. Decided 2026-09-11 in T6. The 2026-09-10 sweep (engineering/session-notes/2026-09-10-test-coverage-review.md, defects 17–20 and the api gaps) held four things as strict xfails; each is now either fixed or recorded. (1) githost.py parsed GitHub's OAuth-exchange and /user bodies before checking the status and unguarded, so an edge proxy's HTML 502 escaped as a JSONDecodeError and the callback answered 500 instead of the mapped 502: the status is checked first, then the body is parsed inside a guard that raises GitHostError naming the call and never the token or secret (C7, C8); every other .json() in the module already went through _json, and the one that read an error body's message is guarded the same way. (2) store.take_ephemeral caught bare Exception, so a throttled table or a programming error read as an expired nonce (400 state-invalid) rather than an outage. There is no client error that means "no such item": an unconditional DeleteItem reports absence as a response with no Attributes, so the guard is removed outright and every store error reaches the app's boundary as it does from every other store call. The item also comes back through plain(), ints not Decimals, as get_job already did. (3) The float-parity xfail stayed as documented here — boto3 refuses float at put_item and MemoryStore does not, so the two halves of the seam disagreed about what can be stored — and T7 closes it with the serialiser this sentence called for (Q8). (4) submissions.py's precheck-node-differs branch could never fire — the bundle is path-checked against the submitted node before the job is bound, and a job's digest is over its bundle's paths, so a job for another node always fails path-forbidden first — and is deleted; no spec named the code. The spec-silent gap becomes the §6 body cap: OPN_API_MAX_BODY_BYTES, default 1 MiB, one 413 body-too-large from BodyCap ahead of every parser. The content type is deliberately not enforced: agents are sloppy with headers and agent-friendliness is the guiding principle, so a JSON body with no Content-Type is parsed as JSON and only a urlencoded header selects the form parser; the cap is on bytes alone.
F05-Q8The seam serialises on the way in, as well as on the way out. plain() has always turned DynamoDB's Decimals back into plain JSON numbers on read; nothing did the reverse on write, so a record carrying a float raised TypeError on DynamoDB and was stored happily by MemoryStore — the one thing a seam may not do (conventions §1, C7). storable() is plain()'s mirror and is applied to both free-form writes, put_job and put_ephemeral; the claims and identities tables take typed dataclasses and need none. Two calls. The conversion goes through str rather than Decimal(value), because Decimal(0.1) is the exact binary expansion and Decimal("0.1") is the number the caller wrote — and str round-trips a Python float exactly, so plain() returns what went in. And a non-finite float is refused by name rather than handed to boto3 as a puzzle: NaN and the infinities have no DynamoDB representation and are not valid JSON either. The parity tests now drive both stores through the shared fixture rather than DynamoDB alone, which is what makes them parity tests. Decided 2026-09-12 in T7.
F05-Q9One freshness generation, keyed on info.json's ETag. Each committed file had its own cache entry and its own 60-second window, per Lambda instance, and nothing invalidated across paths, so after a merge /frontier.json served the previous commit for up to 4.5 minutes while /info.json and get_node served the new one (the Euclid tester, 2026-09-13). Every graph renders info.json on every merge, so its ETag moves exactly when main's products do: once per window it is revalidated, a 304 costs nothing, and a new ETag ages every other cached file so each revalidates by its own ETag. Chosen over comparing rendered_from because an ETag needs no parsing and covers files that carry no rendered_from (raw Lean, CONTEXT.json). Two residual effects, both accepted: a file fetched for the first time mid-window may show the new commit up to one window before info.json does (the reverse, which was the defect, can no longer happen); and a graph without info.json would pay one 404 per request, which no rendered graph does. Decided 2026-09-14 in T10.
F05-Q10A refusal says why, and only a structured one carries details. The Euclid tester claimed the blocked root and was told node-not-in-frontier, and a hole of a listed target node-not-claimable with no reason, while targets/index.json held three. ApiError gains an optional details, rendered only when a refusal has structured reasons: write tools pass the body through verbatim, read tools flatten a refusal to four keys by design, so no MCP result schema changes. Claims read the frontier first and consult the graph only for a node the frontier does not list, so a claim on a listed target's node never needs that target's graph.json; precheck's node_facts reads the graph first because it must know blocked (F06-Q11). An index that cannot be read costs the reasons, not the 409 (C7). Decided 2026-09-14 in T9.
F05-Q11The allowlist is an argument nobody can omit. The 2026-09-13 live contribution sent artifact_type to /precheck, which ignored it, so the tester believed it had declared a partial. identity.body_fields now requires each handler's accepted keys, so a new route cannot skip the rule. Only top-level keys are refused, because a nested value (a bundle, the tooling block) is validated by its own field. The MCP adapter's input schemas already forbid extra properties, and every MCP write tool must send only its route's keys. One pin moved: the body-cap test padded with a stray key and now pads a defined field. Decided 2026-09-14 in T8.
F05-Q12A refusal on a superseded node names its replacement (T11, 2026-09-18). An outside contributor was handed a link to a hole a D-8 revision had replaced. POST /claims answered 409 node-not-open with the word superseded and nothing else; POST /precheck never said superseded at all, because check_open refuses blocked alone, so a wrong path answered only about the path and a right one would have dispatched a job to check a proof of a replaced statement. The replacement comes from the graph, not from the id's suffix: opn-gate revise writes reference on the old node's superseded status record, no product carries it, so precheck.replacement_of lists the node's status/ directory through the host seam and reads the newest record. Best effort by design: it only decorates a refusal that stands without it, so a host that cannot list or serve the record yields replacement: null, never a 5xx. Not changed, and now pinned: a claim on a hole awaiting its witness answers 201. The guide said 409 node-blocked, which was true of a hole the frontier did not list; since F03-T9 such a hole is an entry and claimable, the witness being the work (products.workable), and the claim route reads the frontier's flag. The guide's sentence is corrected with the guide task. Cost named: one directory listing and one file read per refusal of a superseded node, none on any accepted request. Reversal: the branch in check_open and the details argument.
F05-Q13The service's root lists its routes (T12, 2026-09-19). An outside contributor reached the service's hostname from the site and asked it what it offers; / and /openapi.json both answered 404 not-found, and the only index of routes was routes.ROUTES, in process. info.json cannot carry one: it is the graph's product, info/v1 is closed and hash-pinned (D-34), and F13 met the same wall and gave /hosted-checkers.json its own route (F13-Q12), the precedent followed here. GET / is an open read with no D-35 row, served from the routes table itself: method, path, whether a bearer is needed, and one sentence of purpose from routes.PURPOSES, which a test holds to ROUTES in both directions so a route cannot ship without saying what it is for. Reversal: the route, the module and the dict.
F05-Q14The graph is read at the commit main points to (T13, 2026-09-20). R9's cache reads a committed file from the raw host by branch name and revalidates it after frontier_max_stale_s; T10 gave every entry one generation keyed on info.json. Agents measured what that could not fix: a merged node invisible for 6 to 13 minutes (agent E), and a witnessed hole still refused witness-missing for two minutes after main said ready (agent D). The raw host is a CDN, and it answers a branch path with cache-control: max-age=300 (read from its own header): five minutes of staleness beyond anything this cache controls, and different files stale by different amounts, which is also what F06-T7 patched on one route. A raw URL at a commit sha is immutable, so it is never stale. Decided: once per window the service asks the API, as the App, where the branch is (git/ref/heads/<branch>, no CDN in between), and reads every file at that commit; a head that moved ages every entry at once, so everything in one answer comes from one commit. An API that cannot be reached keeps the last head, or the branch name when there never was one (C7): the head is a freshness aid, never a reason to serve nothing. T10's marker stays as it is. Both host assumptions were checked live: the ref endpoint's shape, and 200 from the raw host at the sha. With it: a merged proposal whose node the products do not carry yet reads waiting_on: products instead of null, and products-pending's Retry-After is 240 s with the message saying three to six minutes, which is what the post-merge job measured at; 120 s sent agents back three times too early. The graph's copy of the guide for this task was pushed under a message that says T12 (graph 1005a72e); it is this task. Reversal: pin_head.

A merged annex (#174) read waiting_on: null while precheck answered 409 products-pending; the rule covered proposals only.
