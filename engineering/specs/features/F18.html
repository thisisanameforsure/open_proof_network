F18 — Proof structure on the record

Say, on the graph and on the page, which nodes each proof of a target actually rests on, which proofs a target has, what a crux statement was proposed for, and which outline a decomposition followed.

1. Summary

The owner, reading erdos-1050's problem page on 2026-10-03, could not tell which branches make the proof, which nodes it does not need, how the six spec-* nodes relate to the problem, or where the natural-language outlines are. The record answers three of the four and publishes none of them. The proof that stands is root → erdos-1050--h1-v2 → --h3; h1-v2 declares four holes and its proof term names one, but the page draws declared dependencies because step 8's footprint is computed and discarded (F08-Q38). A target can be proved several ways — the root's proof, its alternates (D-25 v3.13), and each proved resolves variant (D-30) — and no product lists them. The specs are crux statements (D-14 mechanism 2) whose purpose lives only in their doc comments. Outlines are annexes (D-31); the skeleton names the one it followed, and the link is never kept.

F18 builds on F08-T26 and F08-T27 (the service takes a use line; the products say what a proof used) and adds: the target's proofs, each with its closure by use; a site that draws one proof at a time; the skeleton–annex link on the graph; stepped annexes whose steps a skeleton's holes must name (decisions v3.26, D-31); and a proposed-for record that points a crux at the node it serves (v3.26, D-14). It changes no verdict: every new field is derived from the tree or from a signed attestation.

2. User stories

  • As a mathematician reading a resolved target, I want to see the one tree that proves it, and the nodes it did not need, so that I can read the argument rather than the history.
  • As a reader of a target with several proofs, I want to switch between them, so that I can see Euclid's route and each variant's route on their own.
  • As a prover who proposes a crux, I want to say which node it is for, and to have a proof that uses it shown as using it, so that the lemma is found and credited.
  • As a contributor reading an outline, I want to see which skeleton followed it and how far each step has got, so that I know what is left.

3. Scope

In: graph/v4 fields target_proofs, decompositions, outline, proposed_for (beside F08-T27's uses and proofs); the proof selector and closure drawing; annex links and the outline checklist on the problem page; annex/v2 and its step-2 check; proposed-for/v1, its path rule and its service field; the footprint backfill workflow; the re-pin, re-render and record backfill on the live graph; the guide and Docs page.

Non-goals:

  • Changing target status: a target is still resolved exactly when its root is proved (F03). A proved resolves variant is listed as a proof; it does not resolve.
  • Retrofitting step ids into existing annexes: annexes are content-hashed and immutable (D-31); a v1 annex is linked, never checklisted.
  • Rewiring merged proofs to use existing cruxes: a merged Proof.lean is never modified (D-3 v3.13); reuse appears through alternates and later proofs.
  • Any ranking of proofs: the order is the record's order (D-25 forbids ranking).

F18-R2The closure of a proof shall be the node ids reached from it by following, at each node, the used set (F08-T27) of that node's first merged proof; where a node's used is unmeasured the entry shall say so (unmeasured) and the closure shall follow its declared dependencies, never silently.

F18-R4The system shall publish, for each node with a merged partial, decompositions: the partial's path, the annex it cites (or null) and each hole's name and child node, read from the tree and the partial's attestation.
F18-R5The problem page shall show each node's annexes, attached to the node, each marked as followed by the skeletons that cite it or as not followed, always as untrusted data (D-28, D-31).

F18-R7Waits on v3.26 (Q1). For a decomposition citing a stepped annex the products shall publish outline (each step, its node or null, the node's status) and the page shall show it as a checklist with the limit stated.
F18-R8Waits on v3.26 (Q2). The system shall accept, from a node's proposer or a curator, an append-only proposed-for/v1 record naming one other live node of the same target, refuse it from anyone else, and publish the latest as proposed_for.
F18-R9Waits on v3.26 (Q2). The page shall draw a crux's proposed_for as a dashed link, and, once a merged proof uses the crux, the use edge instead.

6. Budgets / limits

  • No new work in the post-merge job beyond reading the attestation it already has; footprints of merges before attestation/v6 are computed once, by the backfill, never by the products.
  • The page stays within 390 px without horizontal page scroll; new SVG labels fit their boxes (measured, not eyeballed).

7. Security & privacy notes

  • Annex prose and proposed-for notes are contributor text: served only under the untrusted-data demarcation (C9, D-28).
  • The backfill workflow runs merged Lean only inside the pinned gate image's sandbox (C9, D-4 step 3) and is granted no secret; the curator commits its output by hand.

8. Dependencies

  • F08 (required): T26 (uses through the service), T27 (attestation/v6 footprint, graph/v4 uses and proofs).
  • F03, F04, F07: the products, the page, the partial and annex machinery.
  • Packages: none. Screenshots use Playwright through uv run --with, an evidence tool, not a dependency of any shipped package.

A skeleton that cites a stepped annex names each hole after one of its steps, and the gate refuses one that does not; a step with no hole is carried by the assembly. A matching name shows the decomposition followed the outline's structure; it says nothing about whether the Lean means what the prose says, which only the kernel and a reader can answer.” The owner chose this stage on 2026-10-03; the wording is his to approve.
