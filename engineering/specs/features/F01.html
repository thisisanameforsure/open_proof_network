F01 — Witness and dependencies

Gate steps 7 and 8 (D-4): the non-vacuity witness is present and proves the statement's hypotheses are satisfiable, and a proof depends on nothing the node did not declare. Introduces the Lean-side metaprogram package the later steps build on.

1. Summary

F00 checks that a proof is a proof. F01 checks two things about what it is a proof of: that the statement's hypotheses can be met at all (step 7, the witness — without it contradictory hypotheses make every conclusion provable), and that the proof's dependency footprint matches the node's declared structure (step 8 — a proof pulling in undeclared nodes makes the graph and the ledger lie). Both need to inspect Lean terms, so F01 adds a Lake package under gate/lean/, pinned to the same toolchain, exposing two small executables the Python pipeline calls through the Toolchain seam. Cites: D-3 (Witness.lean, Context.lean, deps in META.yaml), D-4 steps 7–8, D-29 (statement-side checks at admission reuse these), D-34 (verdict shape).

2. User stories

  • As a prover, I want a clear failure when my proof quietly uses another node's lemma I did not declare, so my merged proof never misrepresents the graph.
  • As a statement reviewer, I want every node to carry a witness that the gate has checked, so I never spend review time on a vacuous statement.
  • As the gate owner, I want the Lean-side checks to be ordinary Lean programs in a pinned package, so a toolchain bump is a visible diff and nothing else.

3. Scope

In: the gate/lean/ Lake package with opn-witness-type and opn-used-constants; step 7 (witness present, typechecks, has the expected type); step 8 (used constants originate only from toolchain/Mathlib, defs/, or declared deps; Context.lean signatures match the deps' statements); warnings for declared-unused deps; fixtures and both test tiers; the step-3 image builds the package.

Non-goals:

  • Hazard checkers (step 6) — F02, though they live in the same Lake package.
  • Admission of new nodes (running these checks on a proposed node) — F08 calls into F01.
  • Cycle detection over the whole graph — F03, where the graph is derived.

4. Requirements

F01-R1The system shall provide a Lake package at gate/lean/ pinned to the repo's lean-toolchain, whose executables read a Lean file and print one JSON document on stdout; a non-zero exit with a JSON error document on any failure.
F01-R2When step 7 runs, the system shall fail if Witness.lean is absent, does not elaborate under the pinned toolchain, depends on sorryAx, or depends on any axiom outside the allowlist.
F01-R3When step 7 runs, the system shall compute the expected witness type from Statement.lean — the existential closure of the theorem's hypotheses over its binders, True when there are none — and shall fail if Witness.lean does not contain exactly one declaration named witness whose type is definitionally equal to it.
F01-R4When step 8 runs, the system shall collect every constant the proof declaration depends on, transitively through declarations introduced in Proof.lean, and classify each by origin module: toolchain or Mathlib at the pinned SHA, the graph's defs/, a node directory, or the submission itself.
F01-R5If any depended-on constant originates from a node not listed in META.yaml deps, then step 8 shall fail naming the constant, its module, and the undeclared node.
F01-R6When step 8 runs, for every declared dep the system shall verify that the signature in Context.lean hash-equals the dep node's Statement.lean signature at the graph commit being gated, and shall fail naming the dep on mismatch.
F01-R7If a declared dep contributes no constant to the proof, then step 8 shall record a warning naming it and shall pass.
F01-R8The system shall run steps 7 and 8 after step 5 and before step 9's data is written, in that order, under the first-failure rule of F00-R7.
F01-R9If a metaprogram exits non-zero or prints malformed JSON, then the step shall fail with the exit code and the first 8 KiB of output in the diagnostic, never pass (C7).
F01-R10The system shall build the Lake package inside the step-3 image so reproduce.sh, the authoritative gate and pregate.sh run identical binaries (D-4: three invocations, one codebase).

6. Budgets / limits

  • Each metaprogram under 30 s on the Mathlib-free fixture; the Lake package builds in under 2 min cold on a hosted runner.
  • Metaprogram output capped at 1 MiB; beyond that the step fails with a truncation marker.

7. Security & privacy notes

  • Both metaprograms elaborate contributor files and therefore execute contributor code; they run only where step 1 runs — inside the step-3 sandbox or on the contributor's own machine (C9).
  • Context.lean is not a submission-editable path (D-3), so a mismatch in R6 indicates graph corruption or a bad admission, not a contributor action; the diagnostic says so.

8. Dependencies

  • F00 (required): pipeline, seam, fixtures, image, pregate.sh.
  • Packages: none new in Python. Lean: the Lake package depends on Lean core only; when a graph pins Mathlib (F11) the package must build against that Mathlib too, which the image handles per graph.

9. Open questions / judgment calls

IDCall made — for review
F01-Q1Witness shape. D-4 says "present and typechecking"; F01 makes it "has exactly the type the gate derives from the statement", because a witness that typechecks but proves something unrelated defends nothing. The derivation is: for theorem s : ∀ (x₁ : α₁) … (hₖ : Pₖ x), C x, expected type ∃ x₁ … , P₁ x ∧ … ∧ Pₖ x, with hypotheses identified as binders whose type is a Prop. Statements with no Prop binders get True.
F01-Q2Origin classification is by module name prefix: Mathlib.*/Init.*/Lean.*/Std.* → library; Defs.* → defs/; Nodes.<id>.* → node; anything else declared in the submission → submission. Module naming is therefore part of the D-3 layout contract and is fixed in F00's layout validator (T1 here adds it).
F01-Q3Unused declared deps warn, never fail. Over-declaring is honest about intent and harmless to structure; failing it would make provers trim deps mid-proof.
F01-Q4Context is substituted at gate time (found at T1, 2026-09-08). The repo's Context.lean holds the deps' signatures with sorry bodies (D-3) so a prover can work before the deps merge; but a proof compiled against it would depend on sorryAx and fail step 5. So the gate builds the node with a generated Nodes.«id».Context that imports each declared dep's merged Nodes.«dep».Proof, and the repo's file is checked textually instead (R6: its signatures hash-equal the deps' statements — exactly the guarantee that makes the substitution sound). Consequences: every node file is a module under Nodes.«<id>» (hyphenated ids need the guillemets; Lean resolves them), a node's Statement.lean imports only its own Nodes.«id».Context, Defs.* or the library (the validator enforces this), and a node whose deps are unproved cannot pass steps 4–8 — which is F03's blocked status seen from the gate. The metaprograms find the sysroot through LEAN_SYSROOT and are always invoked under elan run. The fixture's witnesses were rewritten to R3's shape (theorem witness : ∃ …) and the interior and root proofs added so AC11/AC12 have real inputs.
