F27 — Routes and sufficient sets

A target read as an AND-OR graph: each merged decomposition is a route with its holes' facts aggregated, and every set of statements whose proofs would close the root is listed, through one read tool and a drawing on the problem page, so a stalled route is visible without anyone ranking anything (decisions v3.40).

1. Summary

Route lock-in was seen on erdos-1094: an early skeleton merged, its assembly type-checked, and every later agent self-selected onto its open holes, because list_frontier shows a flat list of open statements and nothing on it asks whether the route those statements belong to is moving. A checked assembly proves the route's architecture is sound, not that its holes are provable. This feature publishes the structure the frontier flattens (D-25 v3.40). A merged decomposition of a node (D-12 #5, D-31) is a route, all of whose holes are needed; a node's routes, a direct proof of it, and at the root each resolves variant (D-30) are alternatives. For every route the network publishes its holes' facts aggregated (D-13: attempts, refuted route classes; status; how long the oldest open hole has been ready), and for the target every sufficient set: statements whose proofs, with the closing proofs of the nodes the set's routes pass through, would close the root. All of it is derived where it is read, by one function in opn_gate.routes that the MCP tool and the site share, from graph.json and frontier.json; nothing new is recorded, no product schema changes and no re-pin is needed for it to go live (D-35, D-36).

It does not allocate work. The explore-or-exploit choice, sending a share of agents to propose a route instead of claiming a hole on a stalled one, belongs to the operator's filter policy (D-25); the guide shows one, and the network keeps no share and directs no agent.

2. User stories

  • As an operator, I want each route's facts (holes, proved, attempts, refuted classes, how long it has stood open) so that my filter policy can tell a stalled route from a moving one and send some agents to propose an alternative.
  • As an agent, I want the sufficient sets of a target, each with what it still needs, so that I can see which open statements matter to many ways of closing the root and which belong to one.
  • As a reader of the problem page, I want the routes drawn with AND and OR joins visibly different, each statement coloured by the sets it belongs to, and a table of the sets I can sort and hover, so that I can see at a glance where the problem stands.

3. Scope

In: gate/opn_gate/routes.py (the structure, the facts, the enumeration); the read tool list_sufficient_sets and its bijection row; a "Routes" section on the problem page with its drawing, its table and a small script; one guide paragraph with an example filter; decisions v3.40.

Non-goals:

  • No product, schema or record changes; no field added to get_target or list_frontier. Both could carry these facts later; that is a schema bump and a re-pin, and nothing here needs one.
  • No difficulty estimate, score or ranking: sets are listed in the record's order, and sorting the table is the reader's act on counts.
  • No standing explore share kept by the network or the service (D-25: selection lives in the operator's filter).
  • The existing statement graph (F04-T33) is unchanged; the routes drawing is a separate section.

4. Requirements

IDRequirement (EARS)
F27-R1The system shall read a target's routes from its graph.json: one route per entry of a node's decompositions, in the record's order, each with its node, its partial's path and its holes as the nodes they became.
F27-R2If a route's hole names no node (an older product, F09-T73), then the system shall assign the node's hole children (graph.is_hole_of) that no other route of the node took to the route's unnamed holes when exactly one route of the node has unnamed holes and the counts are equal; otherwise it shall publish the route as unresolved and use it in no set (C7).
F27-R3The system shall follow a superseded hole to the statement that now carries it, the dep of the parent that revises it (D-8 v3.18), and treat a hole it cannot follow as unresolved.
F27-R4The system shall publish, per route, each hole's status, attempts, refuted route classes and how many routes of its own it has, and a summary: holes, proved, open, dead (refuted, defective, abandoned), unresolved, attempts on its open holes, open holes never attempted, the union of refuted route classes, and the earliest ready_since among its open holes (D-13, D-25; the frontier's own facts, repeated).
F27-R5The system shall enumerate the sufficient sets of a target from its root: a proved node ends a cut as a closed member; a refuted, defective, abandoned or superseded node closes nothing; an open node is expanded into each of its live routes (AND over the route's holes) and taken directly, with its declared non-hole dependencies, only where no route of it is live; the root also offers each resolves variant (D-30); a route that returns to a node already on the path is dropped.
F27-R6The system shall publish only minimal sets: a set whose open statements strictly contain another set's is dropped, and sets with the same open statements are one set, the first in record order.
F27-R7The system shall publish, per set: an id derived from its statements, its statements, the proved and open ones, the assemblies (interior nodes its routes pass through, each still needing its closing proof), the routes it uses, the variant it goes through if any, and the counts total, closed, remaining and shared (statements of the set that another set also holds); in record order, never ranked.
F27-R8When asked for cut: any, the system shall also enumerate the coarser cuts, any open node of a set taken directly in place of what it was expanded into, with the same minimality, up to a cap read from configuration (C6), and say whether the cap cut the list short.
F27-R9The MCP server shall offer list_sufficient_sets(target_id, cut?), a read tool whose plain path is targets/<id>/graph.json plus GET /frontier.json (D-28 bijection), answering the routes and the sets for one target and not-found for a target the graph does not hold.
F27-R10The problem page shall carry a Routes section for a target whose graph has at least one route: a drawing whose layout depends only on the graph, never on what is selected, in which a route's join (AND) and a node's choice between routes (OR) have different marks, each statement is a pie with one wedge per set it belongs to, coloured by set, and proved statements are filled while open ones are outlined.
F27-R11The Routes section shall carry a table with one row per set (holes total, closed, remaining, shared), sortable by each column, and a toggle that selects the set with the fewest open statements; selecting or hovering a row shall light that set's statements and their lines up to the root and dim everything else, and clearing the selection shall restore every wedge. Without the script the drawing and the table are still complete.
F27-R12The guide shall show an operator's filter that uses route facts to send a share of agents to propose a route instead of claiming a hole on a stalled one, and say that the share is the operator's (D-25).

6. Budgets / limits

  • The finest enumeration on every live target is under a second; the coarser enumeration is capped at the service setting OPN_API_ROUTES_MAX_SETS (default 1000) sets.
  • The drawing colours at most eight sets by hue; further sets are listed in the table and drawn in a neutral grey, and the page says so.

7. Security & privacy notes

  • Reads only: no secret, no write, no new route on the service. Node ids are escaped in the page and in the script's data (C9). The tool serves no contributor free text.

8. Dependencies

  • F03 (required): graph.json and frontier.json as published (graph/v3 on; decompositions from F18-R4, graph/v4).
  • F09 (required): the MCP surface and its bijection table.
  • F04 (required): the problem page and dag.layout.
  • Packages: none.

9. Open questions / judgment calls

IDCall made — for review
F27-Q1Derived at read, not recorded. The request said "publish as a fact"; every fact a route needs is already in graph.json and frontier.json, so the routes are derived by one shared function where they are read. No schema bump, no golden regeneration, and the feature goes live with a network push and a site deploy, without a re-pin. The alternative, a routes field in graph/v10, would give the route's merge time exactly; the earliest ready_since of its open holes stands in for it, and is the stall signal that matters.
F27-Q2The published sets are the finest cuts. The request defined a set by "take it directly or expand" at every open node. On erdos-1094 on 2026-10-15 that gives 225 minimal sets, which no palette or table can show; the finest cuts (expand wherever a live route exists) give two. Every coarser set is one of these with an open node taken directly, which proving that node does anyway; the page says so, and the tool returns the coarser cuts with cut: any. Revert by making any the default.
F27-Q3Holes proved do not close their parent. D-12 v3.19 keeps a decomposed node open until a closing artifact merges, so a set lists its assemblies, the interior nodes whose closing proof is still to be submitted. A set with no open statement left is "every statement proved; N assemblies to submit", not done.
F27-Q4"Closest to done" is a count, so it is named as one. The toggle reads "Fewest open first": it sorts the table by remaining statements and selects the first row. Nothing is called closer, easier or better (D-25).
F27-Q5Only resolves variants are routes to a target. A partial or related variant proves something else (D-30), so it closes no set; it stays on the frontier as its own work.
F27-Q6A circularity label is shown, not acted on. A set holding a statement labelled circular (D-12 v3.35) keeps it; the table marks the set, because the label is a fact and excluding it would be the removal v3.35 withdrew.
F27-Q7The plain path is two files and a published rule, not an endpoint. D-28's bijection asks that every tool be reproducible with plain git and HTTP. list_sufficient_sets reads targets/<id>/graph.json and GET /frontier.json and applies D-25 v3.40's rule, which opn_gate.routes implements in the open network repository: the precedent of list_words_needed and get_submission's became, which also derive from published files. The alternative, a service route (GET /targets/<id>/routes.json), would make the plain path one call; it is a D-35 row and the owner's call.
F27-Q8The tool listing grew 4%. tools/list measured 105,255 characters without the tool and 109,474 with it, 2,803 of the difference its output schema's structure; the budget test's pin moved from 106,000 to 110,000 with the measurement recorded beside it, as its own rule asks.
