F03 — Merge products

The files the graph repo regenerates on every merge — frontier.json, info.json, targets/index.json, each target's graph.json — derived deterministically from nodes, attempts and attestations, carrying exactly the D-25 observed facts.

1. Summary

Everything an agent or the site reads about the graph's state is a file in the graph repo regenerated by the post-merge job (D-35 layout; D-28 read tools). F03 defines those files, the node status model they publish, and the generator that produces them byte-identically from the same inputs. The frontier is the entire allocation mechanism (D-25: self-selection over published facts, no ranking, no score), so its fields are fixed here and nothing else may be added without a schema version. Claims are operational state (D-35) and are overlaid by the service (D-35 v3.9); F03 leaves the claim fields present and empty, and F05 fills the snapshot at merge time. Cites: D-3, D-8, D-12, D-13, D-14, D-18, D-25, D-28, D-29, D-30, D-33, D-34, D-35.

2. User stories

  • As an agent, I want one JSON file that lists every node I could work on with the facts D-25 promises, so I can pick without a matchmaker.
  • As the site, I want graph.json per target with statuses and edges, so a page is a rendering of a file.
  • As the gate owner, I want the products regenerated by the bot alone, deterministically, so two people running the generator on the same commit get the same bytes.

3. Scope

In: schemas postmortem/v1 (D-13), graph/v1, frontier/v1, targets-index/v1, info/v1; the node status model; DAG validation; ready_since carry-forward; the generator command opn-gate products; library tags via F01's constant scanner; wiring into the graph repo's post-merge job; golden and determinism tests.

Non-goals:

  • Claim registry and its overlay endpoint — F05 (F03 emits empty claim fields).
  • Ledger files — F07. Fidelity grades and target status changes — F11 and curator tooling.
  • Compiler-derived children from partial proofs (D-12, D-29) — F07 creates the nodes; F03 just publishes them.

4. Requirements

IDRequirement (EARS)
F03-R1The system shall derive each node's status ∈ {ready, blocked, proved, speculative, superseded, stale, disputed, abandoned}: proved when an attestation with verdict: pass and a merge_commit exists for the node's current statement hash; else blocked when any dep is not proved; else ready; the last five are set by curator or adjudication records (D-8, D-14, D-18, D-33) and, when present, take precedence in the order listed.
F03-R2The post-merge job shall write the derived status into each node's META.yaml status field; that field is bot-owned, and the path check (F00) continues to reject any submission touching META.yaml.
F03-R3If the dependency relation over a target's nodes contains a cycle or a dep that does not exist, then the generator shall fail with the cycle or the missing id named, and the post-merge job shall commit nothing (C7).
F03-R4The system shall emit targets/<id>/graph.json (graph/v1): target id, root node, every node with status, deps, origin, statement hash, relation label (D-30) for variants, tutorial flag, trust_base when an attestation says compiler, and the merge commit of its proof if proved.
F03-R5The system shall emit frontier.json (frontier/v1) listing every node whose status is ready or speculative, plus every variant node not yet proved, each entry carrying exactly: node_id, target_id, statement_hash, relation, origin, tags.deps, tags.library, attempts (count of D-13 records), refuted_route_classes, failure_class_histogram, ready_since, claims {active: [], history_count}, annex_present, bounty, claimable, tutorial; no other field, no ordering other than lexical by node_id.
F03-R6The system shall compute tags.library as the sorted set of top-level Mathlib namespaces referenced by Statement.lean, using F01's opn-used-constants; on a Mathlib-free graph the set is empty.
F03-R7The system shall compute attempts, refuted_route_classes (route classes of records with outcome: refuted-route) and failure_class_histogram from the node's attempts/*.yaml validated against postmortem/v1; a file failing validation shall be counted under invalid in the histogram and named in the job log, never silently dropped.
F03-R8The system shall carry ready_since forward from the previous frontier.json when a node remains ready, and set it to the merge commit's committer timestamp when a node becomes ready; no wall-clock time enters any product.
F03-R9The system shall emit targets/index.json (targets-index/v1): every target with id, root statement hash, fidelity grade (D-9; mechanical-only until F11), status (D-33 set), pinned Mathlib SHA, node counts by status, and claimable.
F03-R10The system shall emit info.json (info/v1): protocol version, schema index (name → versions), per-target gate_spec_hash and network_commit, rate_limit_policy (null until F05), and the graph commit the products were rendered from.
F03-R11Every product shall validate against its schema before being written, and two generator runs over the same graph commit shall produce byte-identical files (sorted keys, fixed float formatting, LF line endings, trailing newline).
F03-R12When the post-merge job runs on a merge, it shall regenerate all products and commit them together with the attestation in one commit whose message is gate: <pr> <verdict>; when it runs on a non-merged gate run it shall commit the attestation only.

6. Budgets / limits

  • Generation under 10 s for 1,000 nodes on a hosted runner, excluding the Lean tag scan, which is cached per statement hash in targets/<id>/.tags-cache.json (bot-owned, deterministic).

7. Security & privacy notes

  • Products contain no contributor free text; postmortem detail is never copied into the frontier (D-28 demarcation is unnecessary because prose is excluded by schema).
  • The post-merge job is the only writer of products and META status; it runs with contents: write and no other permission (C8).

8. Dependencies

  • F00, F01 (required). F02 (soft): trust_base flag is read if present.
  • Packages: none new (pyyaml from F00).

9. Open questions / judgment calls

IDCall made — for review
F03-Q1META.yaml status is bot-owned. D-3 lists status in META and makes META submission-immutable; someone must update it, and the only writer that is not a contributor is the post-merge job. Statement hash covers Statement.lean only, so this never touches immutability of the statement.
F03-Q2Timestamps come from git, never from the clock, so products are reproducible (D-5's discipline applied to derived files).
F03-Q3Curator and adjudication records (abandoned, superseded, stale, disputed, dormant) are read from targets/<id>/status/ and nodes/<id>/status/ as schema-checked files; F03 defines only their effect on status and a minimal node-status/v1 schema {status, cause, author, date}. The tooling that writes them is F08 and later.
F03-Q4claimable is a per-node boolean derived from the target's claimable (D-6: listed is not claimable until fidelity reaches back-translated and the D-10 posting is made) and the node's status; true for the tutorial graph.
F03-Q6check_products.py asks every bot commit for an attestation; only a proof merge has one (2026-09-12, AC13). R12 was written when every gated merge built a proof. Run over the eight bot commits the live graph now has, the tool reported no attestation in the commit for the six intakes and the annex append — correctly, since the post-merge job signs nothing for a mode that builds no proof (F07-R9, F08-R13) — while every one of the eight reproduced its products byte for byte. AC13 is met by the one merge of the kind R12 describes (the skeleton, gate: #19 pass). Not fixed here: making the attestation requirement conditional on the merged mode means running the classifier inside the checker, which is a change to what the tool is, and the criterion does not need it. Left for whoever next uses the tool on an append; the evidence records the reading so the line is not mistaken for a defect in the graph.
F03-Q5Target-level facts need a home (T1, 2026-09-09). R9 publishes a target's D-33 status, D-9 fidelity grade and claimable, and R4 its root, but no D-3 file carries them (gate-spec.json and META.yaml are frozen schemas with other jobs). F03 adds target-status/v1 at targets/<id>/status/<date>-<n>.yaml — the curator's signed declaration D-33 already calls for, carrying status, claimable, fidelity and, when the DAG has more than one sink, root; latest by date then file name wins. With no record: root is the unique node no other node depends on (the generator fails if that is ambiguous), fidelity is mechanical-only, and the target is listed and not claimable unless its root is the tutorial node (D-27), which makes it active and claimable. Also: D-13's example header reads schema: d13/v1; the record is published as postmortem/v1, the name D-28's get_schema and this spec use, with D-13's fields and enums verbatim.
F03-Q6AC12 cannot be run as written before F11 (T3, 2026-09-09). No graph pins Mathlib and the Lake package is Lean-core-only, so no fixture statement can import two Mathlib namespaces. The R6 classification (Mathlib.Order.Basic → Order) is proved on synthetic module names in the fast tier; the real seam path (scan_statement: compile the repo Context, run opn-used-constants on the statement) and the per-hash cache are exercised at the lean tier on the Mathlib-free fixture, where the result must be empty. A Mathlib-free graph never scans or writes a cache (its tags are [] by R6), and the products command refuses a Mathlib-pinned graph until F10 wires the sandboxed scan. F11 owes AC12 its two-namespace fixture.
F03-Q7R12's second clause is not wired (T5, 2026-09-09). "When it runs on a non-merged gate run it shall commit the attestation only": the pull-request job runs with no write permission (C8: the job that builds is secretless and cannot write), so it cannot commit anything; it uploads its attestation as a run artifact (F00). Publishing failed public runs to the graph (D-5, D-13) needs a writer that is not the PR job — the service (F06/F07) or a post-close job; left to F07 with the ledger. The merged case is wired as written: one bot commit gate: #<pr> <verdict> with the attestation, the four products and every node's META status.
