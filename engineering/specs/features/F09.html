F09 — MCP adapter

The reference MCP server (D-28): a lens over the git and HTTP path, one tool per D-28 row, each exactly reproducible with plain git and HTTP, holding no state, served from the same function as the api.

1. Summary

F09 mounts an MCP server built on the official Python SDK inside the F05 Starlette application, so any MCP-speaking harness participates in one tool call. Every read tool renders a graph file or a service endpoint; every write tool calls exactly one F05–F08 endpoint with the caller's bearer token; the adapter itself stores nothing. The bijection rule is made checkable: a table maps each tool to its plain-path row, a test freezes the tool surface to D-28's list, and equivalence tests assert each tool's result equals the plain-path response for the same request. Contributor prose in tool results is demarcated as untrusted data. Cites: D-1, D-19, D-25, D-28, D-31, D-35.

2. User stories

  • As an operator, I want to point Claude Code, Codex or a custom harness at one URL with my token and have the agent claim, precheck and submit, so participation is one configuration line (D-28).
  • As an auditor, I want proof that nothing on the MCP surface is impossible over git and HTTP, so convenience never re-centralizes the protocol.
  • As an agent, I want postmortem text from strangers clearly marked as untrusted data in my context, so a prompt injection is a labeled string, not an instruction.

3. Scope

In: the server mounted at /mcp with Streamable HTTP; opaque bearer verification through F05's token store; the nine read tools and eleven write tools of D-28 plus one polling read tool (Q1); the bijection table; surface-freeze and equivalence tests; untrusted-data demarcation; deployment on the existing function; a smoke run from a real MCP client.

Non-goals:

  • Any tool without a D-35 row (bijection rule); any authority-bearing operation (D-28).
  • Server-side sessions, notifications, subscriptions, or resources beyond tools; the protocol path is sessionless and the server holds nothing.
  • OAuth authorization-server features; tokens come from POST /tokens (F05, F06).

4. Requirements

IDRequirement (EARS)
F09-R1The system shall serve the MCP server at /mcp from the F05 application over Streamable HTTP, sessionless, with the SDK's session manager lifespan entered by the host application (SDK requirement for mounted apps).
F09-R2The system shall verify bearer tokens with a TokenVerifier that resolves a token to an identity through F05's store; read tools shall work without a token, write tools shall fail with the SDK's unauthorized result without one (D-28).
F09-R3The system shall declare exactly these tools and no others: reads server_info, list_targets, get_target, list_frontier, get_node, get_defs, get_gate_spec, get_submission, get_schema, get_precheck; writes claim_node, release_claim, precheck_submission, submit_proof, submit_postmortem, submit_informal_annex, submit_approach_record, file_defect_claim, file_revision_request, propose_speculative_node, propose_variant; with the parameter lists D-28 gives.
F09-R4The system shall keep a bijection table in opn_api.mcp.bijection mapping every tool to its plain path: a graph file path pattern at main, or one or two F05–F08 routes; a tool with no entry shall fail the suite.
F09-R5Read tools that map to graph files shall fetch the file at the graph's main through the GitHost seam with ETag caching and return its parsed content unchanged, except list_frontier, which shall read the service's GET /frontier.json (the overlay, D-35 v3.9) and apply the caller's filters as equality or containment on named fields with no ranking (D-25).
F09-R6get_node shall return the D-28 context bundle — Statement.lean, Context.lean, Witness.lean, META.yaml, the attempt log, claim status, annex entries — with every contributor free-text value (postmortem detail, annex text, approach route, acknowledgment and waiver justifications, explainers) wrapped as {"untrusted": true, "source": <path>, "text": <verbatim>} and a top-level untrusted_note string, never as bare strings (D-28, D-31).
F09-R7Write tools shall forward the call to their endpoint with the caller's bearer, pass through the endpoint's status and body, and add nothing; precheck_submission shall return the job id and the polling instruction, and get_precheck(job_id) shall return GET /precheck/<id>'s body.
F09-R8The system shall enforce no rate limit of its own; limits are the identity layer's (D-19, D-28) and 429s pass through.
F09-R9Every tool result shall be structured output validated against a per-tool JSON Schema published by get_schema under names mcp/<tool>/v1, so a client can rely on the shape.
F09-R10If the graph or the service is unreachable, a read tool shall return an error result naming the source, never a partial bundle (C7).

6. Budgets / limits

  • Every tool call completes within API Gateway's 30 s limit; nothing blocks on a workflow (hence get_precheck).
  • get_node bundle under 1 MiB; attempt logs truncated to the newest 50 records with a marker.

7. Security & privacy notes

  • The adapter holds no state and no credential of its own; the caller's bearer is forwarded in-process, never logged (C8, C9).
  • Prompt injection through postmortems is a live attack (D-28): R6's wrapping is mandatory and tested; free-text caps are F07's.
  • The MCP endpoint is outside the trust base (D-28, D-35): a compromised adapter can inconvenience, not merge.

8. Dependencies

  • F08 (required): all endpoints exist. F05: app, tokens.
  • Packages (C5): mcp, the official Model Context Protocol Python SDK, pinned within its 1.x line; it is the reason Starlette and httpx were adopted in F05. Justified because D-28 requires an MCP server and the SDK is the reference implementation of the transport and auth contract.
