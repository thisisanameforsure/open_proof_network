Constitution

Non-negotiables. Read first, every build session, before any spec or code. If this page and a feature spec conflict, this page wins. The engineering rules (C1–C7) are stable and apply to any project; the security rules (C8–C9) are derived from the stack lock of 2026-09-07 (conventions §1) and the protocol's own boundaries. What the network is is not decided here — see C10.

Engineering

C1 — Verification is evidence, not assertion. A task is done only when its named verification command has run, its output is captured to engineering/evidence/FXX/, and it passes — a screenshot or recording for visual work. No manual "looks good" gates.
C2 — Vertical slices, test-gated. Build a thin working thread through all layers before thickening any one of them; tests hold the line between stages. Every acceptance criterion in a spec names the test case that proves it — a criterion without a test is a bug in the spec.
C3 — Work from specs. Code implements the current feature's spec (engineering/specs/features/FXX.html); the build order and status live in engineering/specs/index.html. Deviations get logged in the spec, not smuggled into code.
C4 — Scope discipline. Build exactly what the current task names — no drive-by refactors outside its files, no unrequested features. Drive-by changes are how a codebase rots.
C5 — Dependencies are a liability. Prefer the platform and standard library first; every added package is a supply-chain and audit cost that must be justified in the spec, pinned, and locked.
C6 — Config over constants. Anything plausibly environment- or user-specific lives in config with a documented default, never a magic constant buried in code.
C7 — Fail safe. On error or ambiguity, degrade gracefully and visibly — never fail silently, never corrupt data, never leave the user worse off than doing nothing. Errors are logged; the failure mode is the boring one.

Security

C8 — Secrets live behind one door. The complete inventory, each with its single home:
  1. Gate signing key (ed25519): an Actions secret on the graph repo, nowhere else; its public key is committed to the graph. Signs authoritative attestations (D-5) in the post-merge job.
  2. Precheck signing key (ed25519): an Actions secret on the precheck scratch repo, nowhere else; its public key is committed to the graph. Signs precheck attestations (D-28).
  3. GitHub App private key and client secret (the App also serves as the OAuth app for GitHub-proof identities, F05) and the api token-signing secret: AWS Systems Manager Parameter Store (SecureString), read by the api function at startup.
  4. Deploy credentials: none stored. CI assumes an AWS role via OIDC; the role ARN is config, not a secret.
  5. Founder bootstrap AWS credentials: the git-ignored .env on the founder's machine only — never in GitHub, never in any deployed environment.
Three doors, then: the local .env, Parameter Store, and Actions secrets for signing keys alone. Code reads every secret through the one config module named in conventions §1; no other module touches the environment. Secrets never appear in client bundles, logs, git history, generated site pages, or attestations. The authoritative gate's build step is secretless by construction (D-4 step 3): the job that runs it is granted no secret and no write permission; only the separate post-merge job holds the signing key.
C9 — Data handling & trust boundaries. Two kinds of store, never confused.

Evidentiary — lives only in the graph repo and only changes through a merge the gate has checked: nodes and defs/ (D-3), attestations (D-5, D-34), attempts (D-13), annexes (D-31), schemas (D-34), frontier.json and info.json (D-25, D-35). Append-only or versioned; nothing in this repo may mutate one in place, write one directly, or hold a copy that could be mistaken for the original.

Operational — rebuildable from the graph without changing any verdict (D-35): the api's tables of hashed tokens, claims, precheck jobs and rate-limit counters; precheck job workspaces, deleted when the job ends; the rendered site bucket. Losing any of these is an outage, never a dispute.

Never: log a token, a signing key, or a raw submission above DEBUG; serve annex, postmortem or any contributor free text to an agent or a page without the untrusted-data demarcation (D-28, D-31); run a contributor's Lean outside the sandbox the gate uses (D-4 step 3 — elaboration executes arbitrary code); let the api, the MCP server or the site become a second source of truth.

Personal data: the site's CDN access logs contain visitor IP addresses; kept ninety days, used for aggregate counts only, never joined to ledger identities. Contributor identity is whatever the token holder asserted (D-19, D-22); the network stores no email or credential for it at Stage 0.

Product

C10 — What this is, and what it refuses to be, is decided elsewhere. The architecture decisions (docs/architecture_decisions_v_3_11.html) define the network: its promises, anti-goals, roles, and stages, each decision with a rationale and an overturning condition. Build specs cite them by D-number and never restate or override one. A spec that cannot follow a decision logs the deviation as a proposed overturn; the decision changes only through that document's own process. Product questions this constitution does not answer are answered there.
