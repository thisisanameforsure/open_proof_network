== 1. The defect

At 923a6ce `opn-gate classify` refused both acts a curated target needs to become claimable:
- `intake post`'s diff (target.yaml M, posting null -> {venue,url,date}):
  path-forbidden: a target-record may not be modified  (target-record not in MODIFIABLE_ROLES)
- a lone certificate (fidelity/<subject>-<n>.yaml A):
  intake-incomplete  (fidelity is an INTAKE_ROLE, so every such diff went to _classify_intake)
Held as five strict xfails in gate/tests/test_finding_a_post_fidelity.py.

== 2. The rules as implemented (Mike's decision of 2026-09-13)

Routing, modes.classify: a diff with a target-intake role goes to _classify_intake only when it
adds target.yaml or touches gate-spec.json / defs/*.lean (F11-R2, unchanged). Otherwise:
  roles == {target-record}  -> _classify_posting   (mode curator)
  roles == {fidelity}       -> _classify_certificate (new mode `fidelity`)
  anything else             -> mode-mixed, "each a pull request of their own (F11-R3, R5)"
paths.MODIFIABLE_ROLES gains target-record (A/M); D stays path-forbidden. Certificates stay
add-only, so a rewrite or deletion is path-forbidden before any mode is asked.

Posting (F11-R5, D-10). _classify_posting: author must be in curators.json, else
curator-unlisted; reviewers = the other curators (curator mode's F08-R8 rule).
modes.check_posting (reads the base like check_witness_completion):
  posting-unverified  no base reader given, or no readable target.yaml at base
  record-invalid      head target.yaml fails target/v1 (e.g. a posting with no url)
  posting-fields      any field other than `posting` differs between base and head (names them)
  posting-recorded    base already had a posting (rewrite or removal)
  posting-absent      head posting still null (e.g. a comment-only change)

Certificate (F11-R3, D-9, F12-R9). Mode `fidelity`: needs_gate, needs_admission and
needs_review all false (the signature is the review; nothing builds). _classify_certificate:
  certificate-subjects  files name more than one subject (fidelity/<subject>-<n>.yaml)
modes.check_certificate, in order:
  certificate-uncurated   targets/<id>/target.yaml absent (head == base: the PR adds certs only)
  certificate-invalid     declares a version outside fidelity.READABLE_SCHEMAS, or fails the
                          version it declares; also an earlier certificate that no longer loads
  certificate-name        file name's subject != the certificate's `subject`
  certificate-subject     subject is not the root or a defs/ name of the target
  per certificate:
  certificate-unpinned    not fidelity/v2 (a new v1 certificate counts for nothing; F11-T9)
  certificate-stale       v2 statement_hash != fidelity.current_hash(target, subject) at head
  certificate-attestor    `attestor` != the PR author (Classification.author; OPN_PR_AUTHOR /
                          --author). The attestor need not be a curator.
  certificate-author      `subject_author` != the author on record (earliest existing cert)
  certificate-self-signed grade >= screened-and-signed and attestor == subject_author
  certificate-qa-incomplete  any grade >= screened-and-signed and
                          qa.require_complete(target, subject, routed=qa.routed_by_claims(...))
                          raises (files only; the exhibit replay of F12-R9 is the command's)
mechanical-only certificates skip the non-author rule and the QA rule.

Activation at merge (F11-R4, R5; D-33; F11-T10). modes.check_activation, run on every
target-status record whose status is `active` (check_status_record): on a target with no
target.yaml nothing changes (F08-R11). Otherwise it applies F11-T10's one rule,
intake.activation_refusal, through a new intake.activation_refusal_from(destination, doc,
current), with `current` = records.load_target_status(target, exclude=<status files this PR
adds>) — the status before the PR, since the head's latest record is the PR's own.
  activation-refused   not from listed/dormant (D-33), or not claimable (names D-9 / D-10)
Small API additions for this: records._latest_record / load_target_status(exclude=frozenset()),
intake.activation_refusal_from (activation_refusal now delegates to it; behaviour unchanged).
Classification gains `author` (not published by as_dict).

== 3. Behaviour changed for existing tests, and why

- test_intake_mode.py::test_the_refusals_are_named: asserted a lone certificate is
  intake-incomplete. Now it classifies as mode `fidelity` with no problems (the content rules
  are check_certificate's); the "target file alone is an incomplete intake" coverage moved to a
  lone defs/Other.lean, which is still intake-incomplete.
- test_finding_a_post_fidelity.py: the five xfail marks removed. The ten refusals now assert
  their own codes (curator-unlisted, posting-fields, posting-recorded x2, path-forbidden,
  mode-mixed, path-forbidden, certificate-self-signed, mode-mixed, mode-mixed) instead of any
  refusal. The fixture commits a complete QA pass for the root on the base (a signature needs
  one now); certificate PRs are classified with the attestor as author (the owner settled the
  file's "open decision": the attestor opens it); hand-written certificates are v2 with the
  current hash. test_an_authors_own_signature... is opened by the author so its only refusal is
  certificate-self-signed.
- Not pinned by any test, changed: an intake that *modifies* target.yaml was path-forbidden, is
  now mode-mixed ("an intake adds a target that did not exist"); an intake carrying an `active`
  status record on its new target is now held to activation's rule.

== 7. What the rules above do not settle

1. Identity spelling. `attestor` is compared with the GitHub login that opened the PR, but
   `subject_author` is provenance.author as the curator typed it, and curators.json is the only
   pseudonym<->login map. A subject's author whose login differs from the provenance spelling
   passes the non-author rule by signing under their login. Needs one mapping (curators.json
   style) or a rule that subject_author is a login.
2. Who merges a certificate PR. The mode names no reviewer and builds nothing, so it is green on
   classify alone. Any GitHub account can then sign any target whose QA pass is complete. That
   is the owner's rule, but the merge click still needs someone with write access (F07's
   merge-on-green actor does not exist), so in practice a curator merges unreviewed-by-rule PRs.
3. Exhibit replay. F12-R9's grade gate replays the exhibits a pass rests on; fidelity mode
   starts no sandbox, so check_certificate trusts qa.pass_state's file checks (present, hash,
   no sorry). F12-T8 re-runs a QA record's claimed passes on the QA record's own PR, which
   closes most of this, but a certificate PR does not re-replay.
4. Additions beyond the listed rules, each small and tested, for the owner to keep or drop:
   certificate-name, certificate-subject (a low cert for a non-subject would drag the published
   minimum down), certificate-unpinned/-stale (the lead's request after F11-T9), and posting-absent.
5. Activation is checked on any `active` target-status record, so an intake PR whose status
   record says active is held to it too (intake new writes `listed`, so no live path hits it).
6. Drift. activation_refusal (F11-T10) does not pass `drifted` to claimability; a target frozen
   by F12-R11 can still be declared active at merge, exactly as by the command.
7. Several status records in one PR: the prior status excludes all of them, so listed ->
   {dormant, active} in one PR is judged from listed.

== 8. Proposed spec text (for the lead; engineering/specs not edited here)

F11-R3 (amend, add): "When a pull request adds only certificate files under
targets/<id>/fidelity/ for one subject of a target whose target.yaml exists, the gate shall
classify it as mode `fidelity`, which builds nothing and asks no reviewer, and shall refuse it
unless every added certificate: validates against the version it declares; is fidelity/v2
pinned to the subject's hash at head; is named for its subject, a subject of the target; names
the pull request's author as attestor; names the subject's author on record; and, from
screened-and-signed up, is attested by a non-author on a QA pass complete for the statement as
it stands (F12-R9). An existing certificate may not be modified or deleted."
F11-R5 (amend, add): "When a pull request by a listed curator modifies only
targets/<id>/target.yaml, the gate shall classify it as a curator pull request and refuse it
unless the base and head records differ only in `posting`, from null to a posting target/v1
accepts. A target record may not be deleted. When a pull request adds a target-status record
declaring a curated target active, the gate shall refuse it with the reason
intake.activation_refusal gives, judged from the status before the pull request. A posting, a
certificate and any other change are each their own pull request."
Acceptance criteria (next free AC numbers; tests in gate/tests/test_finding_a_post_fidelity.py):
- Given a listed curated target, when its curator opens the PR `intake post` writes, then
  classify passes it as curator mode building nothing
  (test_a_curator_posts_a_listed_target_by_pull_request); a stranger's is curator-unlisted
  (test_a_non_curator_may_not_post); one editing another field is posting-fields
  (test_a_post_may_change_no_other_field_of_the_target_record); a rewrite or removal is
  posting-recorded (test_a_posting_is_recorded_once).
- Given a target whose root QA pass is complete, when a non-author opens the PR
  `opn-gate fidelity ... screened-and-signed --by <them>` writes, then classify passes it as mode
  fidelity (test_a_non_author_certificate_enters_by_pull_request); opened by anyone else it is
  certificate-attestor (test_a_certificate_opened_by_someone_other_than_its_attestor_is_refused);
  by the author it is certificate-self-signed (test_an_authors_own_signature_is_refused_at_the_gate);
  with no complete QA pass it is certificate-qa-incomplete
  (test_a_certificate_with_no_qa_pass_is_refused); at v1 or against another hash it is
  certificate-unpinned / certificate-stale (test_a_v1_certificate_is_not_added,
  test_a_certificate_for_another_statement_is_refused).
- Given a curated target, when a PR adds an active status record while the target is not
  claimable or is already active, then it is activation-refused naming the missing condition
  (test_an_active_declaration_on_an_unclaimable_curated_target_is_refused,
  test_an_active_target_is_not_declared_active_again); dormant -> active on a claimable target and
  an active record on a pre-F11 target pass (test_a_dormant_claimable_target_may_be_declared_active_again,
  test_a_pre_f11_targets_active_declaration_is_unchanged).
- Given posting, signature and activation as three PRs in that order, each passes and the target
  is claimable (test_post_sign_and_activate_as_three_pull_requests_make_the_target_claimable);
  bundled in one PR they are mode-mixed (test_post_sign_and_activate_bundled_are_refused).
