THE FIVE SCHEMAS, AND WHY THAT IS THE NUMBER
--------------------------------------------
target/v1 and fidelity/v1 are new records. The other three are the rung rename's real cost:

  target-status/v2   R12 as written.
  targets-index/v3   NOT v2. F07-R8 published a targets-index/v2 on 2026-09-10 and D-34 says
                     versioned, never edited — the exact F02-R9 precedent, paid a second time
                     (F11-Q9). The spec now says v3, and AC13 reads v3.
  frontier/v2        R4 wants a dormant target's status as a fact on each of its frontier
                     entries, and frontier/v1 is additionalProperties: false. Budgeted here
                     because a schema bump reaches every consumer: opn_gate.products,
                     the api's /frontier.json route and its MCP field filter, both smoke tools,
                     the deploy check and the site's accepted-versions map all name a set of
                     versions now rather than one pin.

THREE JUDGMENT CALLS, RECORDED IN THE SPEC
------------------------------------------
Q9   the version numbering above.
Q10  R1 listed `fidelity` and `claimable` among target.yaml's fields while R3 and R4 derive
     both. Two writable homes for one value is how a record disagrees with itself, so the record
     carries the inputs and targets/index.json carries the outputs (with `not_claimable`
     beside them). Added `paraphrase` and `qa_summary`, which R10 needs and R1 did not list.
Q11  Two compatibility rules. A target with no target.yaml keeps F03-Q4/Q5's rule exactly, so
     the live tutorial graph is untouched by any of this. And the site's link checker still
     refuses every off-site link (F04-R13); R10's source link is allowed by an allowlist built
     from the *validated* target records, so the renderer cannot invent an outbound link.

WHAT IS NOT EVIDENCED HERE
--------------------------
`opn-gate intake new` runs F08's admission on the root and a plain elaboration on each defs/
file through a seam (intake.Checker). The fast tier drives that seam with a fake, as conventions
§2 requires and as every other Lean-facing module does; the real implementation in cli.py
(intake_checker / _elaborate_definition) has no lean-tier test yet, because this container has
no toolchain and no docker. It is exercised for real in T4, which seeds the on-ramp graph and
whose verification command is `make verify-lean`. Called out rather than left implied: the log
already records that a new Lean-facing seam deserves one lean-tier test, and this one is owed.
