THE WORKFLOW, AND WHAT DRY-RUNNING IT FOUND
--------------------------------------------
qa-screens.yml runs `opn-gate qa screen <target> root --graph <clone> --sandbox --image <ref>
--no-build` over every root in the live targets/index.json, weekly and on workflow_dispatch, and
reports each verdict to the job summary. It lives in the network repo, holds `contents: read` and
no secret (C8), clones the public graph read-only and pushes nothing: `qa screen` leaves a QA
record in its working tree, which here is a runner's scratch clone that is thrown away. Recording
a screen on the graph stays the curator's act, by pull request.

A finding fails the job deliberately — `qa screen` already exits non-zero for a finding and for
anything short of a clean pass, because an inconclusive screen is not one either (F12-R3, C7),
and a red scheduled run is how anyone learns of one. The schedule is weekly because a cron on
Actions is a hope, not a schedule (F04-Q7: site-deploy's */5 ran every two to five hours for two
days), so workflow_dispatch is how it is run on demand.

Checked without Actions:
  - the YAML parses, and both `python3 - <<'PY'` heredoc bodies and their PY terminators sit at
    column 0 after YAML strips the block-scalar indent (an indented body is an IndentationError
    that only a scheduled run would ever show).
  - both python snippets were executed against the live graph clone:
      24 targets read out of targets/index.json;
      2 distinct devcontainer_ref digests, not 1 — the Mathlib image for 23 targets and the
      plain image for the core-only tutorial (mathlib_sha None).
    The loop already pulls each distinct digest once; the header comment had claimed a single
    image and was corrected. The dry run is the only reason that was caught.
