`erdos-1050` is proved: graph origin/main ee5c6d100d's graph.json says `proved`, and it has a
merged Proof.lean. But it carries status/20260917T220741Z-calib-lead-83dd.yaml (`stale`, the

commit ancestry (graph.stale_lifted: the attestation's graph_commit must descend from the commit
that added the record). `run_close` worked on `export_tree` = `git archive`, a tree with no
history, so `stale_lifted` had nothing to ask and the record stood: the sweep saw the proved
calibration root as `stale`, `closing.closable` offered `erdos-1050@1` as ready, and the job
pulled the Mathlib image and composed a join on every merge. (That join then failed for the
reason in 2: the root's Statement.lean predates the own-Context import.)

2. tutorial variant-93e79cb5@2: the join is right to refuse as F28 is written. NOT FIXED.
---------------------------------------------------------------------------------------
The node's Statement.lean (merged 2026-09-11 by the F08 smoke) has no import at all — it
predates F08-T13 (2026-09-20), which made every statement the network writes import its own
Context. The join elaborates the merged assembly as the node's Proof module "so its imports are
the statement's" (Close.lean; F28's spec: "A route's children need no use line: they are the
node's declared dependencies, their signatures in its own Context.lean, and step 4 imports their
proofs in place"). The staged Context does import Nodes.«variant-93e79cb5--h3».Proof, but
neither the statement nor the assembly (attempts/20261030T130000Z-lead-f32-e364-partial.lean)
imports that Context, so `variant_93e79cb5__h3` is not in the environment and fillHole reports
"is not declared".

Reproduced locally with the real toolchain (LocalToolchain, core Lean, `close.sweep` over a
`git archive` copy of graph ee5c6d100d):
  [{"node": "variant-93e79cb5", "link": {"id": "variant-93e79cb5@2", "inputs":
    ["variant-93e79cb5--h3"]}, "ok": false, "reason": "join-failed",
    "detail": "hole h₁: no child closes it: variant-93e79cb5--h3: variant_93e79cb5__h3 is not declared"}]
Probe (scratch only, nothing kept): the same staged work dir, `opn-close` run by hand on the
assembly with one line `import Nodes.«variant-93e79cb5».Context` prepended:
  {"axioms":[],"decl":"OpnProp.and_left_of_and_swap","holes":[{"child":"variant-93e79cb5--h3",
   "hole":"h₁"}],"ok":true,…}
and without the line, on the same build: the "is not declared" refusal. So the mathematics is
sound (the child states the hole exactly; the kernel accepts the joined theorem, no axioms) and
the only obstacle is the import, which the 2026-09-20 rule says such nodes cannot gain ("nodes
already merged without the line close only by a direct proof or a D-8 revision"). Whether the
join may add the node's own Context import itself is a change to what F28 says the join
elaborates, so it is left for the owner (options in the report). After this task the sweep
still tries this join on every merge, on the core image (~43 s pull + seconds).

Live closures after the fix: none. erdos-1050 (a calibration root) is no longer attempted at all
— it is proved, and no closure record will be written for it. variant-93e79cb5 still fails as
before. No closure would be wrong: none is made.
