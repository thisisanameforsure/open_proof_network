F13-T28 — pre-flights fail closed when the caller's check budget is spent (audit 2026-10-04;
the owner's ruling 2026-10-04 amending F13-Q22)
==========================================================================================

Finding: every pre-flight (checks.preflight_witness, _hazards, _relation, _exhibit) caught the
budget's 429 from ratelimit.check_check and answered "unavailable", so the pull request opened
anyway. A caller whose hourly checks were spent could open as many proposals, witnesses, defect
claims and revision requests as the write limit allowed, none of them checked first. And a
proposal needing two or three checks could spend some and skip the rest.

Fix:
- Store.bump_counter takes `by` (MemoryStore adds it; DynamoStore `ADD #c :n`, still one atomic
  update with the TTL set once). Seam test on both stores: test_store_seam.py
  ::test_bump_counter_adds_by_any_amount_in_both_stores.
- ratelimit.reserve_checks(ctx, identity_id, n) -> Reservation: n checks from the same hourly
  counter check_check uses, all or none (over the limit it is taken back at once and the 429
  "rate-limited" with Retry-After is raised). Reservation.take() per checker call;
  release() gives back what was not taken.
- checks.reserved(ctx, identity_id, runs): each pre-flight is first run with a probe that stops
  it at the point where it used to be charged (the reads before that point are cached committed
  graph files, side-effect free), so the count reserved is exactly the count that will ask the
  checker; then one reservation; then the runs side by side; then release. Each public
  preflight_* reserves its own check when called alone; preflight_proposal reserves for all of
  its two or three at once. No caller changed (proposals.py, requests.py untouched): the 429
  escapes from the pre-flight, which every route calls before it opens a branch.
- A checker that fails (outage, error, timeout, no hosted environment) is unchanged: the PR
  opens and the receipt says "unavailable".
- /check's heartbeats measurement skip on a spent budget is untouched (it opens no PR).

Known edge, for the owner: the charge point was, and still is, before the hosted-environment
lookup, so a target whose pin has no hosted checker is charged (and now refused at a spent
budget) although the checker would not be asked. Every live target has an environment (F13-Q9
forwards Mathlib-free pins to the core environment), so this is theoretical today.

Restated: test_finding_witness_preflight.py::test_the_pre_flight_is_charged_and_logged_as_a_check
(pinned "spent budget -> 201 unavailable"; now 429, no PR, no checker call).

  F13-Q29 — A spent check budget refuses; an absent checker does not (T28, the owner 2026-10-04,
  amending Q22). Q22 left "when the checker is unavailable or out of budget the pull request still
  opens" as the owner's call; the audit of 2026-10-04 showed the budget half let a caller with no
  checks left open unchecked pull requests up to the write limit. The owner reversed that half: the
  checks a route's pre-flights need are reserved together before any is asked, and a budget that
  cannot cover them is 429 rate-limited with Retry-After, with no branch, no pull request and no
  checker call, and nothing spent. The other half stands: a checker that is down, errs, times out
  or has no environment for the pin lets the pull request open with "unavailable", because that is
  the network's failure and the gate decides (D-4 v3.14). Reversal: checks.reserved and
  ratelimit.reserve_checks; restoring the old try/except at the four charge points restores Q22.
