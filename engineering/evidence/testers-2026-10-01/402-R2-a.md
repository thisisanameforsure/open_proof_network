## Bugs
- B1 (minor, API): while a hole's witness pull request is open, POST /precheck on the hole answers `409 node-blocked … cause witness-missing … a witness goes in through POST /proposals/witness`, i.e. it tells the submitter to do what is already done. The annex case names the open pull request (`annex-pending`); the witness case should too (e.g. `witness-pending`, naming #342). Repro: POST /proposals/witness on a fresh hole, then POST /precheck on it at once.
- B2 (minor, API): GET /submissions.json lists `open` entries with `waiting_on: null` for every entry and gives no order/position; GET /submissions/<n> gives waiting_on but no position (R1-a's B4 / F4 again). To estimate a wait one must count the open list by hand.
- B3 (throughput, design): each step down a hole chain costs two full queue passes before the next partial can even be prechecked: partial merges → post-merge job → witness PR → queue → merge → render → precheck → partial PR → queue. Today that was 12:02Z (#331 opened) → 12:59Z (hole exists) → ≥13:40Z (witness rendered): about 100 minutes of waiting for a witness that is the parent's witness with one line changed. See F1.
- B4 (minor, /check): `mode: verify` on a partial answers `okay: false` with only `sorry-present`/`sorry-reported` lint and an empty error list; there is no way to ask "is this a valid partial for node X" (header/signature byte-identical, every sorry a named have-hole) on the fast path. One learns it only from the multi-minute precheck.
- Not a bug, confirmed: R1-a's prediction of the hole's Statement.lean (precheck's holes[0].closed_type) was exact, and the witness checked in advance matched.

## Feature requests
- F1 (strong): let a partial's submission carry a witness per hole (the precheck result already prints each hole's `expected_witness` type). The post-merge job would then write a filled Witness.lean and the hole would be born ready; when every hole has the parent's hypotheses (the common case in a contradiction-free chain like this one) the witness is the parent's, verbatim. Saves one whole queue pass per level.
- F2: `witness-pending` (B1) and a queue position/ETA in GET /submissions/<n> (B2).
- F3: a `/check` mode `partial` with node_id (B4), returning the holes and their closed types as precheck does.
- F4 (from R1-a, still wanted): a hole whose statement has unsatisfiable hypotheses can never be witnessed; the guide should say "state remaining cases as disjuncts of the conclusion". Related new observation: two universally quantified lemma-holes in one skeleton are also unwitnessable in practice, because the second inherits the first (an open ∀-statement) as a hypothesis; I merged two lemmas into one hole with a conjunction as conclusion in skel3/skel4 to avoid that.
