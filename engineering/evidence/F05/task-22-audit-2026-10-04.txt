  The api stack's guards are template parameters (ThrottleBurstLimit 50, ThrottleRateLimit 25,
  ReservedConcurrency 20, MonthlyBudgetUsd 50, alarm thresholds), applied by a change set with
  UsePreviousValue, read before execute. Two judgment calls: (a) the function's LoggingConfig moves
  to JSON at INFO, because Lambda's plain-text default keeps WARN and above only and the runtime's
  root handler makes basicConfig a no-op, so the INFO lines the metric filters match (the access
  line, "<kind> <id> opened <html_url> for <identity>") would otherwise never reach CloudWatch;
  that the INFO lines are absent today is inferred from AWS's documentation, not read from the live
  log group. (b) The `live` alias is created at $LATEST and the integration is NOT moved onto it:
  a published version freezes the environment, so UsesFrom/AnnexStepsFrom change sets would stop
  reaching the service until a code deploy. The three-step order is in the README. No service
  line names a minted identity; the filter keys on the access line for POST /tokens with 201.
  Side note: the execution role lists `dynamodb:TransactWriteItems`, which is not an IAM action
  (cfn-lint W3037); transactions are authorised by the item actions, so it is inert. Left alone.
