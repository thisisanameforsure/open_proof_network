== What the graph's `outline` job does, step by step ==
needs: postmerge; if: needs.postmerge.outputs.cache == 'true' (a merge that built and passed — a
proof, an alternate or a partial: the cache job's own condition); permissions: contents: read.

1. Check out the graph at `main` as it is when the job starts (fetch-depth 0, no persisted
   credential). Not the commit the post-merge job pushed: an artifact is outlined only once its
   attestation is on main (graph.proofs_of / partials_of), which holds of main after that push and
   of anything newer, and the command extracts every artifact of the target with no outline, so a
   newer main is a superset and also catches up an outline a lost run left behind. It needs no
   new post-merge output.
2. `pin`: for each target the post-merge job names (id validated, gate-spec.json present on this
   main) read network_commit; a target pinning another gate than the first is left to its next
   merge. Outputs base, pin, targets; run=false if there are none.
3. Check out the network at that pin into network-render (no persisted credential); setup-uv.
4. Extract (no secret in the step's environment): `uv sync`, then the pinned gate's own
   `opn_gate.cli --help`. If its command list has no `outline` ([{,]outline[,}]) the step prints a
   ::notice:: and sets run=false: inert on a pin that predates the command. If the gate does not
   start, a ::warning:: and run=false. Otherwise, per target,
   `opn_gate.cli outline --graph . --commit HEAD --target T --no-build --out $RUNNER_TEMP/...`:
   the pinned image (devcontainer_ref) is pulled, never built, and every build and extraction runs
   in the step-3 sandbox mounting one work directory under $RUNNER_TEMP. Exit 1 (a named failure)
   is a ::warning::, never a red run (R5).
5. Commit and push — the only step given OPN_GRAPH_DEPLOY_KEY, the key file removed by a trap on
   every path out. `collect` takes only untracked targets/<T>/outlines/<sha256>.json for the
   outlined targets and refuses (exit 1, nothing pushed) if the extraction changed a tracked file
   or wrote anything else. Nothing new: exit 0 before the key is written. Otherwise one commit
   `outline: N for <targets>` as opn-gate, and `publish`: push to main; on a refusal fetch main;
   stop with `pin-moved` if any target's network_commit changed (the outlines name a gate main no
   longer pins; the next run extracts with the new one); keep each outline that still describes
   main — not already there (another run's stands), naming its own target and hash, and the
   artifact it names present at that path with exactly the bytes it outlines; stop with
   `nothing-left` if none remain; else commit them again on main as it is and push. Six attempts,
   then a ::warning:: (`gave-up`), never red: the next run extracts what is still missing.

Why it is safe against the post-merge races (F07-T29, T55): the outline commit touches only
targets/*/outlines/, which no post-merge render, ledger line or record writes, so neither side's
catch-up ever conflicts with the other; its subject starts `outline:`, never `gate:`, and it is no
merge, so it credits nothing and the batch planner walks past it. It is authored as opn-gate, so
the push run's postmerge finds no pull request (run=false) and that run's site-deploy dispatch is
skipped; and the outline job runs only after a postmerge whose `cache` output is true, so its own
push never starts another outline job.

Not run here: the docker tier (no container run of `opn-gate outline` against a real step-3
image), and no live run of the graph job, which waits for the push and the re-pin.
