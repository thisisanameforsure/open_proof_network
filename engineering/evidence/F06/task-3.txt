AC3 (test_dispatch_recorded) — the branch and the dispatch R3 requires:
  push   repo=<precheck_repo> branch=job/<id> base=main
         files = {job.json, bundle/targets/propositional/nodes/and-reassoc/Proof.lean}
         job.json carries id, node_id, target_id, statement_hash, graph_commit, bundle_digest
  dispatch repo=<precheck_repo> workflow=precheck.yml ref=job/<id> inputs={job_id: <id>}

  The dispatch ref is the job branch, not main. The branch is main's tree plus the job's two
  kinds of file, so the workflow that runs is the scratch repository's own — the api pushes no
  runnable code — and the run is findable by `?branch=job/<id>` without a run-name convention.

The signature reader (api/opn_api/sshsig.py), and why it exists
---------------------------------------------------------------
The gate signs with `ssh-keygen -Y sign` because the gate always runs where OpenSSH is installed.
The api does not: the Lambda image carries no ssh-keygen, so a subprocess verifier would have
failed in production and passed every test on this laptop. F06-Q5's `cryptography` covers this
too — the module parses the SSHSIG wire format and hands the bytes to a vetted Ed25519 verify.

Every test in test_sshsig.py checks it against real `ssh-keygen` output rather than a fixture
this repository generated, including the fingerprint (`ssh-keygen -lf` agrees byte for byte) and
the namespace (a signature made with `-n git` does not verify as `-n opn-attestation`).

Cross-check performed by hand before the tests were written:
  $ ssh-keygen -q -t ed25519 -N "" -f k && printf 'hello opn' > msg
  $ ssh-keygen -Y sign -f k -n opn-attestation msg
  fingerprint mine : SHA256:zaoAIoK9lgnLE7dTAJpTxyctAIAW21sVKPv2l8dwhjs
  ssh-keygen says  : SHA256:zaoAIoK9lgnLE7dTAJpTxyctAIAW21sVKPv2l8dwhjs
  verify good      : True
  verify tampered  : False
  verify wrong ns  : False
