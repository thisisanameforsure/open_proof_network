== What changed and why ==
B-F3. The stated cause is right. site/infra/site.cfn.yaml's one CustomErrorResponse maps S3's 403
(a missing key behind origin access control) to 404 with ResponsePagePath /index.html, so every
unknown path showed the home page.
 - The generator writes 404.html (Renderer.not_found): it says "Page not found", links to / and
   /problems/, and says a statement lives at /problems/<problem>/#node=<id>. No script.
 - The generator writes problems/<target>/<node-id>/index.html for every node of every target. Each
   is the existing Q14 meta-refresh redirect page (it now takes a `words` argument: "This
   statement is shown on its problem's page, at") pointing to /problems/<target>/#node=<node-id>.
   These are written after the problem's own pages and never replace one (review/, proofs/).
   This half needs no infrastructure change and ships with the next site-deploy.
 - The template's ResponsePagePath is now /404.html. This half is a CloudFront change. It is
   written in site/infra/site.cfn.yaml and NOT deployed. Until the stack is updated (a change set
   with UsePreviousValue for every parameter, per the 2026-09-11 log), an unknown path still shows
   the home page under a 404. The guessed node paths work either way. The existing `s3 sync`
   uploads 404.html.

D-F-D4. RELATION_ROLES["partial"] was "a partial route to the problem". It is now "a weaker
version of the problem: partial progress, never a proof of it", which opens with the drawing key's
own label for relation-partial ("a weaker version of the problem"). I checked the other roles
