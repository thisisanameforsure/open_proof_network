F-D9: a path is held while it is opening and while an open PR adds it, and no longer
======================================================================================
The lead's reading of the cause was right. holding_name keyed its counter `name#<path>` with no
window and never dropped it after a success. The memory store never expires a counter. DynamoDB's
ADD sets expires_at only if_not_exists and keeps counting an expired item. So on every path that
can recur, the hold lasted hours after its second.

What changed in api/opn_api/appends.py, and why:
- Standing guard. append_pr now records `path:<path>` among the submission's fingerprints. No
  schema change was needed: Submission.fingerprints is already a free tuple, and nothing compares
  a path print with a content print or a words key. holding_name first asks path_holder for an
  open submission that carries the print and can still merge (duplicates.blocks: a closed,
  withdrawn, merged, gate-failed or conflicting one holds nothing). If one exists it refuses
  409 record-name-taken and names it (pr_number, pr_url, submission_id), for as long as that
  submission stays open.
- In-flight guard. The counter is keyed `name#<path>#<window>` (NAME_HOLD_S = 60). It also reads
  the previous window (a bump by 0), so two concurrent requests either side of a window boundary
  still count as one. A refused request gives its count back (a bump by -1). The counter is
  dropped as soon as the submission is recorded (release_name, after pending.record), or at once
  if the PR did not open. If the PR opened and the recording failed, the counter is kept and
  lapses with its window, after one to two minutes.
- Messages. A <timestamp>-<pseudonym> path keeps the same-second wording and Retry-After: 1. Any
  other path (content-named words and annexes, numbered stewards/motions/votes) is told which
  open PR holds it, that waiting does not free it, and that it is free once that PR merges or is
  withdrawn. That refusal carries no Retry-After. An in-flight refusal on such a path says another
  request is opening it at that moment, with Retry-After: 1. The gate catalog entry
  (gate/opn_gate/codes.py, record-name-taken) is reworded to cover both cases.
- hold_name=False (names/<pseudonym>.yaml, F25-R6) still skips both guards; append_pr uses a
  no-op hold there. The path print is still recorded.
- name_holder, which matched by kind, pseudonym, owner and creation second, is removed. The path
  print finds the holder exactly, whatever its pseudonym.

Submissions opened before the deploy carry no path print, so the standing guard cannot see them.
By kind of path:
- Timestamp-named paths cannot recur, so nothing is lost.
- Content-named paths are still covered by the duplicate rule (same text, open, same node) and by
  the words one-writer rule.
- Numbered paths (stewards/<n>.yaml, panel motions and votes) are the gap. Until such a PR merges
  or closes, a new record can take its number, and the gate's append-only rule then refuses
  whichever merges second.
The old stuck counters sit under the old keys with no window, which nothing reads any more. A
check of open steward, motion and vote PRs on deploy day (GET /submissions.json) covers the gap.

Left unchanged, worth knowing. The duplicate rule's own slot (duplicates.counter_key, 120 s window)
is also never dropped after a success. So withdrawing and re-filing the *identical* text inside the
same two-minute window is refused 409 duplicate-submission, with a correct Retry-After. I tried
releasing that slot after the record as well, and reverted it. duplicates.open_rivals matches on
node_id only, so for target-level records (steward records, approach records) that counter is the
only double-click guard. Releasing it turned two tests red:
test_stewards_route::test_the_same_form_sent_twice_is_one_submission and
test_finding_duplicate_submissions::test_the_same_postmortem_or_approach_record_from_two_authors_is_a_copy.
The open_rivals gap for records with no node is a separate defect, for the lead.
