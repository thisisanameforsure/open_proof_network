0. The gap and the rule

   A qa/v1 row for a clean screen or a compile carries exhibit: null (F12-Q15: clean screens leave no
   file), so a record whose every floor row says pass reads the same typed by hand as written by
   `opn-gate qa screen`. F12-R15 closes the forgery for rows that name a file; nothing closed it for
   rows that name none, and CI checked a qa-record pull request by schema and curator membership only.
   The strict xfail gate/tests/test_finding_de_qa_status.py::test_d_a_hand_typed_pass_does_not_raise_
   a_grade_through_the_command held it.

   Rule, as decided by Mike on 2026-09-13: when a pull request adds or changes a QA record, the gate
   re-runs, in its sandbox toolchain, the checks the record claims passed without an exhibit file —
   compile and the four soundness screens — for that subject's statement as it stands at head, and
   refuses the pull request if any re-run disagrees, naming each disagreeing row. Rows with exhibit
   files stay R15's. Brief and back-translation rows need a model key the gate job must not hold
   (C8), so they are not re-run, and the report says so.

1. The seam as built

   gate/opn_gate/qa_rerun.py (new; qa.py, modes.py and paths.py are untouched, to keep the parallel
   branches' merges clean)
     records_in(located) -> [path]        the qa-record paths a diff adds; what classify reports
     reason_not_rerun(subject, row)        None for a row the gate must re-run, else the stated reason
     verify(graph_root, record_paths, rerun) -> Report
                                           loads each record from the tree at head, splits its rows,
                                           checks the record is for head's statement and pins, calls
                                           rerun(target, subject) at most once per subject and only
                                           when some row needs it, and compares each claimed pass
                                           with every fresh row of the same check
     agrees(verdicts)                      a pass stands only if the check ran and every run passed:
                                           fail, inconclusive (timeout, budget, error) or no row at
                                           all is a disagreement (C7)
     head_copy(graph_root, dest)           the tree without .git, for the re-run to write into
     context(copy_root, target, toolchain, workdir, settings)
                                           a RunContext over the copy's root node, as `qa screen`
                                           builds one
     rerun_subject(ctx, subject, ...)      root: qa.screen itself (so the re-run cannot drift from
                                           the command that writes honest records); a definition:
                                           the target's definitions compiled through the seam
                                           (a definition has no screens, F12-Q10)

   What is re-run and what is not (each skipped row is listed in the report with its reason):
     compile, screen-statement, screen-negation, screen-false, screen-consequence with verdict pass
       and no exhibit                                      re-run
     brief, backtranslation (any verdict, file or not)     REASON_MODEL — asks a model; no key in
                                                           the gate job (C8); held to R15 and the
                                                           writer's coherence rules (F12-Q18)
     any row naming an exhibit file                        REASON_EXHIBIT — R15 hash and replay
     any row with verdict fail or inconclusive             REASON_NOTHING_CLAIMED
     equivalence pass with no file                         REASON_EQUIVALENCE — outside the floor
                                                           (Q3), evidence only through its exhibit
     a screen row on a definition subject                  REASON_DEFINITION_SCREEN (Q10)

   Diagnostic codes
     qa-rerun-disagrees     a recorded pass the re-run at head does not reproduce; details carry
                            record, subject, check, recorded: pass, rerun: [verdicts], notes
     qa-rerun-unverifiable  a record pinned to another statement hash, toolchain or Mathlib (R5),
                            an unknown subject, or a path that is not a record in the tree at head

   Where it writes: qa.screen records its run and, on a finding, stores an exhibit and files a
   screen-finding claim. All of it lands in <out>/head (the copy), never in the checkout under check.

   gate/opn_gate/cli.py
     opn-gate classify    two new keys: qa_records (the records the diff adds) and needs_qa_rerun
     opn-gate qa-rerun --graph G --base B [--head H] [--sandbox [--image T] [--no-build]] [--install]
                       [--out DIR] [--date TS]
                          exit 0 when every claimed pass is reproduced, 1 naming each disagreement
                          (stdout JSON, stderr one line per problem, <out>/qa-rerun.json), 2 for a
                          diff that adds no QA record or an environment error. --sandbox builds the
                          seam `qa screen --sandbox` builds: the copy's root node read-only, the work
                          directory read-write, never installing. A record with nothing to re-run
                          starts no toolchain and no image.
     It is a top-level command beside `exhibits`, not a `qa` action: it is the pull request's check,
     not a curator act, so it answers refusals as exit 1 rather than {"ok": false, "refused"}.

4. The tests have teeth: nine in-memory mutants

   Each mutant is a pytest plugin (-p) that monkeypatches opn_gate.qa_rerun in pytest_configure; no
   file is changed. The driver runs test_qa_rerun.py and test_finding_de_qa_status.py once clean and
   once per mutant, and reports every F12-T8 test that fails under no mutant and every mutant no
   test catches. Result: all 28 F12-T8 tests fail under at least one mutant; no mutant survives.
     mutant_trust_record        nothing is re-run; every row is left to the record's word (D3 undone)
     mutant_only_fail_disagrees only a finding contradicts; inconclusive or missing is accepted (C7)
     mutant_rerun_exhibits      rows with exhibits and rows with no pass are re-run too (R15 split)
     mutant_rerun_briefs        a brief or back-translation pass is sent to the re-run (C8 carve-out)
     mutant_in_place            the re-run screens the checkout itself, writing into it
     mutant_silent_classifier   classify never names a QA record, so the workflow never reaches it
     mutant_ignore_stale        a record for another pin or statement is re-run as if fresh (R5)
     mutant_skip_missing        a path that is not a record in the tree passes silently
     mutant_no_usage_error      a diff with no record is not refused as misuse

7. Costs and limits

   Time per QA pull request. The Lean is cheap and the image is not. F12's own measurement
   (engineering/evidence/F12/budgets.txt, hosted runner): a clean root costs ~3.3 s of Lean for the
   compile and three screens, plus one attempt per declared consequence; a finding costs ~55 s more,
   almost all of it leanchecker --fresh replaying the found proof; the per-subject budget (300 s,
   OPN_QA_SUBJECT_BUDGET_S) bounds attempts plus replays, and each attempt has 60 s. The local lean
   run above (one finding) took ~57 s end to end. On top, the gate job must have the step-3 image:
   for a Mathlib graph that is the published image by digest (~3.5 GiB compressed) pulled on a cold
   runner, which is minutes and dominates. A record of briefs alone costs nothing: no image, no Lean.
   The job is paced by the post-merge bot commit under the strict up-to-date ruleset anyway (log,
   2026-09-13).

   Not re-run, and why. brief and backtranslation: they ask a model; the gate job holds no model key
   and must not (C8; OPN_MODEL_API_KEY lives in the curator's .env). They remain held to R15 and the
   writer's coherence rules, and R2 keeps a brief from raising a grade on its own. Rows with exhibit
   files: R15's hash check at every reader and the kernel replay before a grade counts them.
   equivalence with no file: it counts for nothing (outside the floor, and cited only through its
   exhibit).

   What the rule does not settle (for Mike):
   a. A typed record whose claims are true is accepted. The rule verifies what a record claims, not
      who wrote it. That is the decided reading; it means `tool:`/`produced_by:` stay unverified
      labels.
   b. Exhibit files in a QA pull request are not elaborated in CI. R15's replay runs where
      `opn-gate fidelity` runs — the attestor's machine, sandboxed only if they pass --sandbox — and a
      qa-file does not trigger `needs_exhibits` (that is append mode's). A hand-made exhibit with a
      matching hash and no sorry merges; it cannot raise a grade without the replay, but the replay
      is not a CI act. Moving the replay to this same step would close it, at ~55 s per exhibit.
   c. A record for another statement or pin is refused as qa-rerun-unverifiable. The alternative is
      to accept it, since a stale record counts for nothing (R5). Refusing was chosen as the
      fail-safe direction (C7) and costs no sandbox; it does block a curator who ran the screens on
      a base that has since moved (re-run at head, or rebase).
   d. A slow runner can refuse a true record: an attempt that passed locally within budget and times
      out in CI is inconclusive, so the pull request fails and must be re-run. Tactic results can
      also differ between machines (`exact?`, `aesop`); a proof found in CI and not locally is a
      real finding, and CI refusing is right, but the curator then routes it (R4) with no exhibit
      from the CI run — the exhibit and claim exist only in the job's scratch copy, and only
      qa-rerun.json is uploaded.
   e. A definition's compile re-run builds all of the target's definitions; one that fails before
      the subject's module is reached makes the subject's compile row disagree (named in the note).
   f. Only records a pull request adds are re-run. Records already on main are grandfathered; the
      live graph has no targets/*/qa/ directory today (checked on the local graph checkout), so
      nothing is.
   g. No docker-tier test drives `qa-rerun --sandbox` in the real image. The command reads the head
      copy on the host (inputs only) and every Lean process goes through the same SandboxToolchain
      `qa screen --sandbox` and admission use, and nothing it learns about the image's filesystem
      comes from a host Path — but the log's rule is one docker-tier test per sandboxed check, and
      that is owed before the re-pin.
   h. Merge points with the parallel branches: qa_rerun calls qa.subject_hash, qa.spec_of,
      Record.stale and qa.screen; if the fidelity/qa branch moves subject_hash, mypy --strict will
      name the call. cli.py's run_classify gains two summary keys, and classify's exact-output test
      in test_modes.py lists them.
