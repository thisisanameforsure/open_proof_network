F07-T69 (audit 2026-10-04): queue position is counted per target lane.

Finding: the merge actor has been strict per target since F07-T56 (one lane per target, lanes in
parallel; a pull request in no single target is EVERY_LANE, waits until first, then holds every
lane: graph .github/workflows/merge.yml, lane_of_paths / decide). The service's queue block
(api/opn_api/pending.py queue_order / queue_block / entry_queue) counted every open pull request on
the graph, and QUEUE_ORDER and the MCP get_submission / list_submissions descriptions described the
whole-graph queue.

Fix: lane_queue(order, lanes, number) restricts the actor's order to the pull request's lane. The
lane is the one target the service's own record names (Submission.target_id; every route that opens
a pull request records the target it touches). A pull request the actor takes that the service has
no open record of has no known lane and is counted in every lane (EVERY_LANE = "*"), so the position
stays an upper bound; one whose own lane is unknown counts the whole queue. queue.order at the top
of GET /submissions.json stays the actor's order across every lane. No response field added (the
MCP output schemas are closed; a `lane` field would be a schema change, not taken).

verification `uv run --frozen pytest api/tests/test_finding_queue_lanes.py api/tests/test_finding_queue_position.py`.
