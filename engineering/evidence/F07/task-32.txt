Root causes: (1) the check-run view lags the check; (2) a hold ends the run and nothing re-wakes it
when what it held for already happened; (3) a push run's status lags its jobs by minutes; (4) the
concurrency group drops pending wakes; (5) the cron is best effort; (6) mergeable=null read as "no
conflict"; (7) a failed act wakes nothing. The api's waiting_on shared (3) and had no word for a
conflict (#150 read "merge").

Fix (graph branch f07-t32-queue, commit below; api/opn_api/githost.py):
- pick.settle: a hold is decided again every 20 s from fresh reads, for at most 15 min; job timeout 20.
- pick.postmerge_running_from: a push run is running while one of its jobs is (or none started).
- decide: conflicted() None (host computing) is a hold, never an update.
- gate.yml postmerge: last step `if: always()` dispatches merge.yml with its own token (actions: write);
  workflow_dispatch is the one event GITHUB_TOKEN may start a run with (docs.github.com,
  "GITHUB_TOKEN", checked 2026-09-23).
- merge.yml `rewake` job: needs merge, if failure(), actions: write only, dispatches once more.
- cron */15, called a last resort.
- api waiting_on: jobs are the gate's word while the run lags; mergeable_state dirty -> "conflict".
