F07-T83 — a queue position counts its own sub-lane (bug B1's service half, agent run 2026-11-19)
================================================================================================

Finding
-------
B1 (6 of 9 agents): green appends sat 20-50 min behind proofs and partials on their target. The
merge actor now splits each target's lane into two halves that do not wait for each other
(F07-T81/T82, another agent, the graph's merge.yml): appends (append/ branches) and building pull
requests (propose/, submit/). A pull request the service cannot place in one target still waits
for every lane. The service's `queue` block (GET /submissions/<id>) and each entry's `queue` in
GET /submissions.json counted the whole target lane, so an append was told it stood behind
proofs that can no longer delay it.

Fix (api/opn_api/pending.py)
----------------------------
* `Lane = (target_id, "append" | "build")`; `UNPLACED = ("*", "*")`.
* `sub_lane(record, entry)`: the open listing's `head_ref` decides (the actor decides by the
  branch: build on propose/ or submit/, append otherwise). Fallback, with no listing entry: the
  record's `kind` (`BUILD_KINDS` = POST /submissions' artifact types + speculative, variant,
  witness). Justification: the record's kind decided the branch when the route opened it —
  POST /submissions opens on submit/ (racers' conversion keeps submit/), proposals.open_proposal
  (speculative, variant, witness) on propose/, every other route through appends.append_pr or
  reviews on append/ (or review/, curate/, which the actor does not take). With neither, build
  (the stricter half). `branch_sub_lane(branch)` is the same rule for a branch about to be opened
  (used by F07-T84's caps).
* `place(ctx, listed, records, order)` gives every pull request of the actor's order its Lane;
  `lane_queue` keeps the same (target, half) plus every UNPLACED one; an UNPLACED pull request
  itself still counts the whole order. `queue_block`, `entry_queue` and `snapshot` all go through
  `place`, so the per-id answer and the listing agree.
* QUEUE_ORDER and QUEUE_NOTE describe the two halves; the guide's queue passage
  (gate/agents/AGENTS.md, "One gate round is not the time to merge") says so and drops "an annex
  or a postmortem ... can wait one round behind a proof", which is no longer true.
