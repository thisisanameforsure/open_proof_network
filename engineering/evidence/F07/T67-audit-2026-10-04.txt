F07-T67 — open pull requests capped per pseudonym and for the graph (audit 2026-10-04)
======================================================================================

Finding: nothing bounded how many pull requests one identity held open (the write limit is per
hour, so a caller could add to the queue every hour without end), and nothing bounded the whole
queue. The merge actor considers open pull requests in number order (F05-Q19), so one caller's
backlog delays everyone behind it, and every open pull request is a gate run on the graph's
runners.

Fix: submissions.check_open_caps, called first thing in submissions.open_pr — the one place
appends, proposals (speculative, variant, witness) and submissions open a pull request.
- Per pseudonym (pseudonyms are unique, D-19): count Store.list_open_submissions() by
  pseudonym; only at the cap, reconcile the caller's own records through the existing path
  (pending.open_listing + pending.listed_state + pending.reconcile, exactly as
  GET /submissions.json does; pending.py not edited) and recount. Still at the cap: 429
  `open-pull-requests-cap`, details {cap, open: [{submission_id, pr_number, pr_url, kind,
  target_id, node_id}]}, Retry-After 300 (the guide says every 429 carries one).
- Global: when the store's open count reaches the cap, recount against the host's open listing
  (one listing call per pull_listing_max_stale_s, cached); still full: 503 `queue-full`,
  details {cap, open}, Retry-After 300 (about one merge, F07-T33).
- Settings OPN_API_OPEN_PRS_PER_IDENTITY (default 10) and OPN_API_OPEN_PRS_GLOBAL (default 150).
  THE OWNER HAS NOT SIGNED OFF THESE DEFAULTS.
- Published in rate_limit_policy as open_pull_requests_per_identity and
  open_pull_requests_global. info/v1's rate_limit_policy is {"oneOf": [null, {"type":"object"}]},
  an open object (checked in gate/schemas/info/v1.json), so no schema change.

Behaviour to know:
- Soft caps: two requests at the cap's edge can both pass (no atomic reservation).
- A merge is seen within the listing's window (60 s default): a caller at the cap whose pull
  request merged seconds ago may be refused until the listing refreshes.
- Pull requests opened by hand (not through the service) are not counted: the store only knows
  what the service opened.
- Cost: one list_open_submissions per opened pull request (on DynamoDB one get per open record,
  as GET /submissions.json already pays), and host reads only at a cap.

Restated: test_health.py::test_rate_limit_policy_shape (two new keys);
test_finding_queue_position.py::test_the_queue_costs_no_read_per_record (one author's 25 open
pull requests now run with the per-identity cap at 25).
