F07-T18 (R19, AC40): a hole's statement must survive being written.
2026-09-17, after the F15-T14c calibration run found four live holes stating something other than
the obligation their assembly discharged.

WHY, IN ONE LINE
  The extractor printed a hole's closed type with `ppExpr`'s defaults, so `(ω n : ℝ) / 2 ^ n` came
  out as `↑(ω n) / 2 ^ n`, which elaborates again over ℕ where the division truncates. The child
  node published that reading, looked well formed, and could not admit a proof of the real
  obligation: step 7 answered `witness-elaboration` and `POST /check` refused the proof, both
  saying the calc expression had the ℝ type but the node expected the ℕ one.

THE DESIGN WAS PROBED BEFORE IT WAS WRITTEN (POST /check, lean-4.33.1, the graph's own pin)
  Three sample obligations, printed bare and then under the options, each read back and compared
  with `isDefEq`:

    bare:  ∀ (n : ℕ), ↑n / 2 = ↑n / 2                       round-trips: false
    fixed: ∀ (n : ℕ), (↑n : ℝ) / (2 : ℝ) = (↑n : ℝ) / (2 : ℝ)  round-trips: true

    bare:  1 / (2 ^ 3 - 1) = 0                              round-trips: false
    fixed: (1 : ℝ) / ((2 : ℝ) ^ (3 : ℕ) - (1 : ℝ)) = (0 : ℝ)  round-trips: true

    bare:  ∑' (n : ℕ), ↑(ω n) / 2 ^ n = ∑' (p : Nat.Primes), 1 / (2 ^ ↑p - 1)   round-trips: false
    fixed: ∑' (n : ℕ), (↑((ω : ℕ → ℕ) n) : ℝ) / (2 : ℝ) ^ n
             = ∑' (p : Nat.Primes), (1 : ℝ) / ((2 : ℝ) ^ (↑p : ℕ) - (1 : ℝ))    round-trips: true

  So `pp.coercions.types` plus `pp.numericTypes` is the cure and the round trip is the detector,
  both confirmed at the pinned toolchain rather than assumed. `Parser.runParserCategory` +
  `Term.elabType` + `isDefEq` are the API names that work there.
