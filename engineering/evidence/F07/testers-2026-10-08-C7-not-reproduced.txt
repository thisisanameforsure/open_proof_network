== What the field is documented to be (not a defect even when it is old) ==

api/opn_api/pending.py:
  last_read(): "``waiting_on`` for a pull request as the service last read it, and when: from the
    cache of per-id reads, whatever its age, and never a read of its own."
  entry_queue() publishes it beside "waiting_on_read_at", so its age is in the answer.
  QUEUE_NOTE (served in the answer): "each entry's queue.waiting_on is what the service last read
    for that pull request, with when; null means not read (GET /submissions/<id> reads it), never
    that it waits on nothing."

engineering/specs/features/F05.html, F05-Q19 (T18, 2026-10-01): "No route reads a pull request it
was not asked about, which is why a list entry's waiting_on is the last per-id read the service
holds, with its time ... Not built, for the owner: a waiting_on for every list entry would take
one more host call per window (the gate runs of all open heads in one listing), which is a new
read and was outside 'facts the service already reads'."

The guide (gate/agents/AGENTS.md, the queue paragraph) says the same: each ahead entry carries
"the `waiting_on` the service last read for it".

Tested already: api/tests/test_finding_queue_position.py
  test_a_submission_says_where_it_stands_and_what_is_ahead (waiting_on with waiting_on_read_at,
  null where unread) and test_the_listing_gives_every_entry_its_position_in_queue_order
  (queue.waiting_on_read_at present in the list).

Published state is actual state "as of waiting_on_read_at", which the answer carries, so a list
entry's waiting_on cannot be mistaken for a live read. A live waiting_on for every entry is the
owner's open option in F05-Q19, not a defect.
