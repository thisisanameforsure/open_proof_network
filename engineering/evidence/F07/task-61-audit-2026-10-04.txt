F07-T61 — the pin step fails closed and takes the pin from the base (audit 2026-10-04)
=====================================================================================

Graph branch: audit-b-workflows, commit 0fd4d5b72 (gate.yml, the gate job's pin step). Not pushed.

Finding. (1) A pull request touching no target and not policy.json exited "nothing to gate" with
run=false, so the required check reported success for anyone's change to a workflow, curators.json,
keys/, schemas/ or a product. (2) The pin was read from the PR's own tree (targets/$target/gate-spec.json
at the merge ref), so a submission that rewrote its target's pin chose the gate that judged it.

Fix (the pin step only; no gate CLI flag, inert on the current pin 3422bb4).
- changed.txt is `git diff --name-only --no-renames base...HEAD` (a rename out of curators.json shows
  its deletion too).
- Any path not matching ^targets/<id>/.+ or ^policy.json$ -> exit 1 "not a submission", unless
  OPN_PR_AUTHOR (env, from github.event.pull_request.user.login) is a github_login in
  `git show $base:curators.json`. A listed curator's PR with no target stays run=false (review only);
  with a target it goes on to the pinned classifier as before.
- The pin is `git show $base:targets/$target/gate-spec.json`; a target new on the PR takes the first
  target's pin on the base (and fails if the base has none). policy.json's pin is taken the same way
  from the base instead of the working tree.

Red tests (run against the step as it stood: 9 failed, 3 guards passed):
  test_finding_gate_pin_step.py::test_a_workflow_change_by_a_stranger_fails_the_check     exit 0, run=false
  ::test_a_pull_request_cannot_list_its_own_author_as_a_curator                           exit 0
  ::test_anything_outside_a_target_fails_for_a_stranger[x4] (target+README, targets/index.json,
    keys/, curators.json deleted)                                                          exit 0
  ::test_a_submission_cannot_choose_its_own_gate                                           pin was PIN_B
  ::test_a_new_target_is_gated_by_the_pin_the_base_carries                                 pin was PIN_B
  ::test_the_author_reaches_the_script_through_the_environment                             no env
Guards green before and after: a curator's workflow PR is review only; a submission gates on its
target as before; policy.json still reaches the classifier with the base's pin.

Deployment note. The ruleset requires the gate check; after this lands, a non-curator's pull request
that touches anything outside a target is red and cannot merge. The live curators.json lists only
thisisanameforsure, which is who opens the graph's workflow and guide pull requests.

Proposed Q entry (F07-Q65): "The pin step fails closed: a pull request is a submission only if every
changed path is under targets/<id>/ or is policy.json; anything else fails the required check unless
its author is a curator listed on the base, whose such pull request is review only. The pin is the
base's: a pull request never chooses the gate that judges it (D-4); a new target is gated by the pin
the base's targets carry."
