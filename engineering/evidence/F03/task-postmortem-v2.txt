postmortem/v2: model_and_tooling on a postmortem (D-23, D-13; D-34 versioning)
Owner approval: Mike, 2026-10-28. Branch postmortem-v2 (worktree opn-postmortem-v2), based on e68-fixes.

== Required or optional: REQUIRED (nullable) ==
The three precedents: annex/v2 (2026-10-03) optional; approach-record/v1 (2026-09-10) required;
literature/v2 (2026-10-19, the newest) required. Following the newest, postmortem/v2 lists
model_and_tooling in `required`, with null allowed: a v2 record always states its model, or
states that none was used, so "not declared" and "nothing drafted it" cannot be confused.
The property is approach-record/v1's byte for byte (oneOf null | string 1..200, "As declared by
the operator (D-23); never verified"), asserted by test_v2_field_is_approach_record_v1s_field_exactly.
v1 is untouched (D-34); v2 = v1 + the field ($id, title, schema const and description rewritten together).

== Design call the brief did not cover: the deploy window ==
A target's pinned gate validates appends against its own SCHEMAS_FOR_ROLE, so a v2 postmortem
sent to a target pinned before this commit would be refused at classify: a red pull request that
can never merge, for every postmortem, until the re-pin. So the service writes v2 only when the
target's pinned network commit carries gate/schemas/postmortem/v2.json (asked once per pin on the
raw host at that commit, cached for the process; a host that cannot say, or an unreadable
gate-spec, answers v1, C7). On an older pin it writes postmortem/v1 exactly as before: a null or
absent model is dropped, a declared model is refused 400 record-invalid naming why, before
anything opens. Same shape as annex/v2's steps (F18-T5) but keyed on the pin's own files rather
than an OPN_API_*_FROM setting, so no stack parameter is needed. Consequence: after the re-pin
every target writes v2 without any further act.
