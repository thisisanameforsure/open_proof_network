## 2. Decisions I made for you — please review

1. **`cryptography` is in, pinned at 50.0.1** (you approved it in your message; it was F06-Q5,
   open since this morning). Two uses, both of them "never roll your own": RS256 for the GitHub
   App JWT, and Ed25519 for verifying a precheck attestation. Nothing else in the repo may reach
   for it — the gate keeps signing through `opn_gate.signer`.

   Q5's other half was a warning that it is a large wheel and the Lambda package is cross-built
   for arm64. Checked, exactly as `api-deploy.yml` builds it: the aarch64 wheel resolves with its
   compiled extensions (no source build on the runner), 23 MiB unzipped against a 250 MiB limit,
   6.6 MiB zipped against 50 MiB. **The deploy workflow needs no change.**

2. **The api verifies signatures without `ssh-keygen`** — new module `api/opn_api/sshsig.py`,
   logged as F06-Q6. This is the one I most want you to look at. The gate signs by shelling out
   to OpenSSH, which is fine because the gate always runs where OpenSSH is. **The Lambda image
   has no `ssh-keygen`**, so a subprocess verifier would have passed every test on this laptop
   and failed the first time a real result came back. The module parses the SSHSIG wire format
   and hands the bytes to `cryptography`'s Ed25519 verify — format parsing here, no primitive.

   Its tests check it against real `ssh-keygen` output, never against a fixture this repo
   generated, including the fingerprint (`ssh-keygen -lf` agrees byte for byte) and the namespace
   (a signature made with `-n git` does not verify as `-n opn-attestation`).

3. **The workflow is dispatched at the job branch, not at `main`** (Q7). The branch is `main`'s
   tree plus `job.json` and `bundle/`, so the workflow that runs is the scratch repo's own — the
   api pushes no runnable code — and the run is then findable by `?branch=job/<id>`. Dispatching
   at `main` would have needed a `run-name` convention to tell one job's run from another's.
   Verified against real GitHub: the pushed branch came out exactly as designed (§4).

4. **The tutorial exchange advances the job itself** (Q8), rather than making an agent remember
   to poll `GET /precheck/<id>` before spending its nonce. No new exposure — that GET is itself
   unauthenticated — and one fewer step for an agent to get wrong.

5. **The tutorial exchange shares the token-start address limit** (Q9), default 10 per day.
   `POST /tokens` has no identity to rate-limit by, and both routes answer the same question:
   how many identities may one address try to mint in a day. The honest flow costs one.

6. **A job pins `frontier.json`'s `rendered_from`, not the graph's current `main`** (Q10). R3's
   wording says "the graph commit at `main`" and did not anticipate these differing — they differ
   right now, because the F06-T2 key commit did not re-render products. I kept `rendered_from`
   and wrote down why: the service's whole view of the graph (which nodes exist, their statement
   hashes, which one is the tutorial) comes from the rendered products, so pinning the commit
   those were rendered from keeps the job consistent with the facts the bundle was validated
   against. Pinning `main`'s head would name a commit the service cannot see inside.
   **If you disagree, this is the one that should change** — say so and I will amend R3 instead.

7. Two housekeeping changes: `.playwright-mcp/` added to `.gitignore` (an earlier session's
   scratch output was sitting untracked), and `api/tools` added to mypy's path so the smoke tools
   can import each other.

## 3. What needs you — the only thing blocking F06

**The GitHub App may not dispatch a workflow.** Probed with a ref that does not exist, so no run
was ever created:

```
POST /repos/.../actions/workflows/precheck.yml/dispatches
  → 403 Resource not accessible by integration
```

The installation carries `{contents: write, metadata: read, pull_requests: write}` — no `actions`
permission. Adding one is the App owner's act: it must be changed on the App and then approved on
the installation, which cannot be done from a build session.

Curiously, the Actions *reads* already work (listing workflows and runs returned 200) because the
scratch repo is public. So only the dispatch is blocked.

### Do these in order

1. **GitHub App `open-proof-network` → Permissions → Repository → Actions: Read and write.**
   Save, then approve the request on the installation (GitHub emails a link; it is also under
   Settings → Applications → Installed GitHub Apps → Configure).
   The probe that tells granted from not-granted, without starting a workflow run, is written out
   in `engineering/evidence/F06/task-5.txt`. A `422 No ref found` means granted.

2. **Push `main`.** This deploys — `api-deploy.yml` fires on any push touching `api/`.

3. **Run the criterion:**
   ```sh
   uv run python api/tools/smoke_precheck.py https://api.openproofnetwork.org
   ```
   It takes no account and no token. It reads the graph, finds the node marked tutorial, sends
   that node's own committed proof anonymously, waits for the run, exchanges the nonce for a
   token, uses the token on a write route, and checks the nonce is refused a second time. It
   prints the latency of each state change — that is the Stage 0 series §6 asks for.

4. Append its output to `engineering/evidence/F06/task-5.txt`, mark T5 done in `F06.html` and in
   `specs/index.html`, and tag `F06-done`.

### Why I did not push

Pushing deploys. Deploying before step 1 would put a `POST /precheck` on the live service that
answers **502 for every caller** — worse than today's, which accepts a job and never runs it. The
permission and the deploy belong in the same sitting, and the permission is yours.
