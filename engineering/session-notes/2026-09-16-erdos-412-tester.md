## The mathematics, and this session's check of it

Erdős 412: do the σ-iteration trajectories of any two integers ≥ 2 eventually meet? The
decomposition proves `~` ("orbits meet") symmetric and transitive — transitivity is where forward
determinism enters — collapsing the two-variable claim to `m ~ 2`; strong induction then reduces
that to a descent, and **every m that lies on the orbit of a smaller start is discharged inside
the kernel-checked file**. One hole remains, carrying the hypothesis that the free case removed.

This session checked it two ways rather than taking the report's word:

- **The proof structure**, read by hand: the chain `descent → (strong induction + transitivity) →
  m ~ 2 → m ~ n` is valid, and the `Function.iterate_add_apply` arithmetic in `trans` is written
  out rather than waved at.
- **The arithmetic**, recomputed from scratch with an independent σ (`verify-sigma-orbits.py`,
  Pollard rho, no shared code with the tester): **88** of the 238 values of m in 3..240 are
  downstream of a smaller start, **128** of the rest have a visible descent partner, **22** remain
  — `[5, 16, 19, 27, 29, 33, 49, 50, 52, 66, 81, 85, 105, 146, 147, 163, 170, 189, 197, 199, 218,
  226]`. Identical to the report, list included, and its three named witnesses check.

**What it is not.** The hole and the conjecture imply each other: it is a reduction of shape, not
of depth. The tester said so plainly in its report *and* in the committed annex, and declined to
split one hole into three to hit the brief's "two to five". That honesty is the most encouraging
result of the run — an agent that pads a decomposition to look productive would be worse than
useless here, and this one argued against its own score.

## After the merge: two corrections and one new defect

PR #70 merged 08:23, PR #71 09:10 (both by the owner), and the post-merge job passed on
`cdf91ae4`. It created `erdos-412--h1` from the `descent` hole, attested `000071.json` with
`submitter: agent-sigma-4f1d`, regenerated the products and reached the site in about four
minutes. No duplicate `attempts/` file. The target does **not** read resolved.

**Correction 1 — register #65 is refuted, and this session's guide edit acting on it was wrong.**
The generated hole's `META.yaml` carries `origin: skeleton-hole`; `postmerge.ORIGIN_SKELETON` is
`"skeleton-hole"`, and both `meta/v3` and `meta/v4` list it in the origin enum. The guide's
original wording was right; the edit was reverted and the test now reads the constant instead of
either remembered answer. The 2026-09-10 log entry calling it "an enum value no code can emit"
was true when written and went stale once F07/F11 gave it a caller. **Three guide statements were
wrong, not four.** The lesson is the log's own: resolve the constant before believing a claim
about its value — `postmerge.py:310` was open on screen and the value was one line away.

**Correction 2 — a frontier lag is not a bug.** Four minutes after the bot commit the api served
the previous products; at 09:19 it had caught up on its own. Re-checking before filing is what
kept this out of the register.

**New defect — updating a branch reassigns the ledger credit.** `proposer_of` took the merge's
second parent as the contributor. Because the ruleset forces a branch up to date before merging,
that commit is the *update* merge, authored by whoever pressed it. So the ledger resolved the
earner as the owner and D-21 barred the line, since the owner curates `erdos-412`; the
contributor earned nothing and `ledger/agent-sigma-4f1d.json` was never written. PR #38 escaped
only because its branch was never updated. Where the merger is not a curator it is worse: the
contributor's proof line lands in the merger's ledger, which the end-to-end test demonstrates. **And it has already happened:**
`ledger/thisisanameforsure.json` carries two `attempts` lines for postmortems written by
`agent-t16-2a4b` (merges `a70cc60e`, `82eca2a7` — both with an update merge as second parent), so
another contributor's credit is live on the Contributors page under the owner's name. That is the
D-19 record being wrong about who did the work, and it is worse than the missing proof line.
Every pre-existing ledger test commits linearly, so this path had never been exercised. Fixed by
reading the commits the merge actually brought in (`^1..^2`, no merges); five tests, three red
first. **The live ledger still owes `agent-sigma-4f1d` a proof line** — repairing it needs a
re-pin and a way to re-run the ledger for merge `42f94ef`, which is the owner's.

**Still open, and the practical cost of the merge:** `erdos-412` now has no claimable node at
all. The parent is blocked on its hole and the hole is `blocked: witness-missing`, so the
committed frontier carries no row for the target (23 entries → 22) while the target page still
says "This target is open for claims". And the bot-generated hole carries `3 ≤ m`, `2 ≤ m'` and
`m' < m` with **no `acknowledged_hazards`**, where the parent acknowledges `off-by-one-range`
twice — so F07-Q19 ("a node the gate itself creates must still pass the gate") is armed here.
**Confirmed the same day** on a Mathlib-free mock through the gate's own step 6 and the locally
pinned Lean: `verdict: fail`, three `off-by-one-range` findings at `2 ≤ m'`, `2 ≤ x` and `3 ≤ m`,
none acknowledged. The control matters as much as the result: the four euclid holes are proved
with no acknowledgements on a spec running the same checker, because their bounds are `0 < k` and
variable-to-variable, which the checker does not flag. Carrying the parent's acknowledgements down
would not help — the child's bounds come from the decomposition, not the parent — so the fix is a
design choice, and it is the owner's.

## Lessons

- **An agent will tell you its decomposition is shallow if you ask it to.** The brief said "if
  your best decomposition has one hole that is still essentially the whole problem, say so plainly
  rather than dressing it up", and it did, in the permanent record as well as the report. Ask for
  the honest assessment explicitly; it is cheap and it is what makes the artifact trustworthy.
- **Verify the tester's arithmetic independently.** Recomputing the σ-orbits cost one script and
  turned "it says 22 residual cases" into a checked fact. A report that cannot be re-derived is a
  claim.
- **The orchestrator sees what the tester cannot, and should look.** The tester was forbidden `gh`
  by design; that is exactly why its "four PRs open for two days" reached this session as a
  puzzle rather than a grievance, and the puzzle was the best bug of the run. Take a baseline of
  the record before the run so the diff afterwards is cheap.
- **A green check on a stale base is not a verdict about the tree that will exist.** #71 was
  `BEHIND` after #70 merged and its bot commit landed; the gate diffs from the pull request's
  base, so bypassing would have recorded an attestation for a tree that never existed. Update the
  branch, never bypass — the strict rule is doing its job.
- **Merge order between a skeleton and its annex is load-bearing**, and nothing enforces it before
  the merge (register #8). `apply_partial` raises when the cited annex is not on the node, and a
  post-merge job that fails loses its ledger line for good.
