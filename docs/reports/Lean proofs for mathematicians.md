# Build the blueprint before the prose

No existing system takes an arbitrary, agent-written Lean 4 proof and produces mathematics that a subfield expert can follow while every sentence stays traceable to the Lean. The tools that are maintained and usable on a static site (Verso and SubVerso from the Lean FRO, leanblueprint, LeanArchitect) either show Lean with its goal states, or link *hand-written* prose to Lean declarations by name. The one tool that turned ordinary tactic proofs into expandable English automatically (Massot and Miller's "informalization") exists as a 2023 demo page and a paper still "in preparation", with no public code. The LLM pipelines that do generate prose from proofs have one small measured result: about 89% of steps correct with a templated pipeline on undergraduate calculus, graded by a single annotator. Nothing measures research-level or agent-written proofs. For the Open Proof Network the best fit is therefore staged. First, render each target as a blueprint, as a pure function of the graph. That meets the owner's link-back requirement now and needs no protocol change. Second, add a gate-extracted outline of each proof, with goal states, as a committed product. Third, offer model drafts only through the existing D-3 explainer path, where a named human signs. The owner's second requirement, that a subfield expert can follow the proof, is not met by any automatic system on the evidence. On this site it is met by a signed human explainer. What the network can build is the scaffolding that makes such an explainer cheap to write and mechanically anchored. Throughout, **(measured)** marks a number from an experiment or a count of the repository, and **(inference)** marks a conclusion drawn from the evidence rather than tested.

## Nine candidate systems, none of which meets both requirements

The landscape splits by what each system starts from. Systems that start from **hand-written prose** link that prose to Lean by declaration name. In leanblueprint, `\lean{}` names a declaration and `\uses{}` records dependencies. Status comes from the author's hand-placed `\leanok`, and `checkdecls` only confirms that the names exist ([leanblueprint](https://github.com/PatrickMassot/leanblueprint)). Over 40 projects use it, from sphere eversion to FLT, and it is Apache-2.0, but its last push was December 2025. Verso Blueprint, the Lean FRO's successor-in-practice, computes progress "by analyzing the associated Lean code and declarations, including incomplete declarations such as `sorry`". FLT, Carleson, Sphere Packing and Noperthedron serve as its reference blueprints ([verso-blueprint](https://github.com/leanprover/verso-blueprint)). LeanArchitect goes the other way: `@[blueprint]` attributes in the Lean source generate leanblueprint LaTeX, with dependencies inferred from the constants each declaration uses ([LeanArchitect](https://github.com/hanwenzhu/LeanArchitect); [arXiv 2601.22554](https://arxiv.org/abs/2601.22554)). All three satisfy the link-back requirement at lemma granularity. None writes the mathematics: in every one of them, a person writes the prose.

Systems that start from **the Lean** show the Lean better. Verso renders highlighted Lean with hovers and "rendered intermediate proof states in tactic proofs" as static HTML ([Verso](https://github.com/leanprover/verso)). SubVerso extracts highlighting, hovers and anchor-marked proof states as JSON, and has been checked on every Lean release since 4.0 ([SubVerso](https://github.com/leanprover/subverso)). Paperproof draws a tactic proof as a tree of hypotheses and goals "resembling pen-and-paper", but it is a VS Code panel with no documented static export ([Paperproof](https://github.com/Paper-Proof/paperproof)). LeanInk, the bridge to Alectryon's line-by-line goal display, has been **archived since August 2024** ([LeanInk](https://github.com/leanprover/LeanInk)). These meet the link-back requirement completely, because the Lean is the page. They do not meet the followability requirement, because the page is still Lean.

Systems that **generate English** are the thinnest category. Massot and Miller's demo page (`Last-Modified: 15 Feb 2023`) has the right shape. It carries a tree of `Explanation` nodes: 45 expandable refinements, 76 tooltips and 23 goal states rendered as English hypothesis lists ("is a regular topological space"). It loads only local assets ([demo](https://www.imo.universite-paris-saclay.fr/~patrick.massot/Examples/ContinuousFrom.html)). Avigad describes it as translating "a formal proof to one that is written in formulaic but otherwise ordinary English", with plus and minus buttons to expand and collapse justifications ([Avigad, arXiv 2311.00007](https://arxiv.org/pdf/2311.00007)). Miller's CV lists the paper as "In preparation" ([CV](https://kmill.github.io/cv/cv.pdf)), and no repository was found. Its English appears to come from per-concept phrasing data: the page stores "is a regular topological space" with a separate plural form. If so, Mathlib notions without phrasing data would fall back to weaker output **(inference from the data shape; the authors do not say)**. Lean Verbose produces paper-like Lean only for proofs written in its own controlled language ([verbose-lean4](https://github.com/PatrickMassot/verbose-lean4)). Agent proofs are not. Herald and Hattori et al. are the two published LLM methods for proof informalization, covered in the next section. Naproche reaches research material (perfectoid rings, [ITP 2025](https://drops.dagstuhl.de/storage/00lipics/lipics-vol352-itp2025/LIPIcs.ITP.2025.6/LIPIcs.ITP.2025.6.pdf)), but it does so by making the controlled-language source itself the readable text, and it targets Isabelle, not Lean.

The gap the owner's two requirements open, followable *and* anchored, is exactly where nothing ships.

## One measured study puts proof informalization at roughly 89% of steps correct

The faithfulness evidence for prose generated *from proofs* is small and should be quoted at its real size. Hattori, Matsuzaki and Fujiwara informalised each tactic step from the tactic and the goal states before and after it. They used per-tactic templates and a "premise library" of plain-language descriptions of the lemmas cited, then summarised recursively along the proof's dependency structure. On **1,242 steps from 38 calculus proofs, graded by the first author alone**, the full pipeline was 89.05% correct with 5.15% misinformation. Without templates it fell to about 54% correct **(measured)** ([arXiv 2509.09726](https://arxiv.org/pdf/2509.09726)). Two of their results matter for design. Misinformation *rose* with templates (5.15% against 2.50%), because more specific prose names more hypotheses and lemmas that can be wrong. And without recursive summarisation, four of 17 proof summaries "included reasoning not in the original proof", against none with it **(measured, n = 17)**. Herald, the other method, translates line by line using goal states. It reports only qualitatively that the output "faithfully reflects the proof strategy" but is "closer to formal language than natural language", with Mathlib identifiers leaking into the LaTeX. It skips term-mode proofs entirely ([Herald, arXiv 2410.10878](https://arxiv.org/pdf/2410.10878)).

No study measures how often an LLM judge or back-translation wrongly passes a *proof* informalization. The nearest proxy is statement-level. Herald's compile-plus-back-translate pipeline passed 151 statements, of which human experts found **101 correct, 24 with minor errors and 26 with major errors: about a third of passes wrong (measured)** ([Herald, App. D](https://arxiv.org/pdf/2410.10878)). The project's own fidelity research records a back-translation checker at 33.3% accuracy on research-level FATE-X ([research_statement_fidelity_2026-09](../research_statement_fidelity_2026-09.html)). A separate evaluation found that 80% of the cases evaluators disagreed on most were proofs with "sophisticated presentation but fundamental logical errors" ([arXiv 2510.13888](https://arxiv.org/pdf/2510.13888)). The project's own reading already drew the consequence: "No 2025–2026 paper measures the faithfulness of prose summaries of formal proofs", and any readability score the network published "would be an invented number" ([research_math_and_ai_2026-09 §3](../research_math_and_ai_2026-09.html)).

Carrying these numbers onto the live graph takes care. The graph's 67 merged proofs total 655 KB, with one top-level theorem each, every helper lemma written as a nested `have`, and heavy automation. Across the 87 proof and partial files there are 3,849 `have`, 1,168 `omega`, 552 `norm_num` and 452 `simp` **(measured, repository count)**. The largest are the erdos-1050 Lagrange-interpolation holes at 716 to 845 lines. A calculus textbook proof and an 822-line agent proof of an integrality bound are different populations. A working figure of "one step in ten to twenty wrong or misleading" is the best case, and research-level agent proofs are likely worse **(inference; nothing measures them)**. There is also a structural reason. A step closed by `omega` or `field_simp; ring` has no human-meaningful reasoning to translate, so a model either says "routine computation" or invents an argument. Only the first is honest.

## Experts read for idea, method and modules, and Lean statements already serve them

The owner's second requirement needs an operational meaning, and the reader research supplies one. The Proof Comprehension Assessment Model, built from interviews with mathematicians, splits understanding into three local dimensions (meaning of terms, justification of each claim, logical status of each statement) and four holistic ones (high-level idea, general method, modular structure, application to examples) ([Educ. Stud. Math. 2020](https://link.springer.com/article/10.1007/s10649-020-09984-x)). Research mathematicians read published proofs mainly for insight and method, often modularly, and lean on the authority of whoever has checked the proof ([Weber & Mejía-Ramos 2011](https://link.springer.com/article/10.1007/s10649-010-9292-z)). In a survey of 83 mathematicians, 88% try to prove a theorem before reading its proof and 87% compare the proof's approach with their own **(measured)** ([ERIC ED584498](https://files.eric.ed.gov/fulltext/ED584498.pdf)). A formal check can replace the "authority" strategy for correctness. That frees the page to serve idea, method and modules, the very things a tactic script hides **(inference)**.

What mathematicians say about Lean points the same way. Scholze in 2021: "The definitions and theorems are surprisingly readable, although I did not receive any training in Lean. But I cannot read the proofs at all". He also asked for "a completely normal mathematical manuscript that is cross-linked with the Lean code" ([Xena](https://xenaproject.wordpress.com/2021/06/05/half-a-year-of-the-liquid-tensor-experiment-amazing-developments/)). A commenter on the same post named the defect: a tactic script "only contains the word 'induction'" and not the goals and hypotheses, and asked for a tool that prints them at each step. Tao's ICM 2026 lecture names the failure of AI exposition: it "dwells at length on trivialities, while passing very briefly through (or even obscuring) the most interesting and novel portions", and over-polish removes the "natural friction" that tells a reader where the hard part is ([ICM 2026 slides](https://teorth.github.io/tao-web/slides/age-of-ai-icm-2026.pdf)). His own Sendov digestion is the precedent closest to OPN's situation. He did not informalise the 90,000-line Lean. He digested the argument by hand with AI help, found it "remarkably elementary", and then had an agent re-formalise *his* version in about 15,000 lines ([Tao, Aug 2026](https://terrytao.wordpress.com/2026/08/12/a-digestion-of-the-proof-of-sendovs-conjecture/)). The Erdős #728 write-up shows the anchored form at lemma granularity. Much of the text was drafted by ChatGPT, "manually checked", and a table maps each of 14 paper lemmas to the Lean declaration that proves it ([arXiv 2601.07421](https://arxiv.org/abs/2601.07421)). In the terms of DeDeo and Duede, the formal proof justifies the prose only if the prose *tracks* the formal steps ([arXiv 2603.13680](https://arxiv.org/abs/2603.13680)). That is the owner's first requirement stated as a property.

Two concrete lessons on presentation come from the only blind reader experiment found. Ganesalingam and Gowers's readers wanted the goal restated after each definition was unfolded, the subfield's idiomatic definitions (open balls), and witnesses declared ("Let δ = min{η, θ}") rather than the search narrated ([arXiv 1309.4501](https://arxiv.org/pdf/1309.4501)). Lamport's hierarchical proofs add the expansion discipline. The reader sees a few named steps, opens lower levels only until satisfied, and every fact used is cited by name ([Lamport 2012](https://lamport.azurewebsites.net/pubs/proof.pdf)). No controlled study tests Lamport-style or blueprint pages on research mathematicians. The case for expandable, hierarchical presentation rests on argument and practice, not experiment.

## OPN's rules leave three legal homes, and the site's own renderer is the first gap

The network's constraints decide where a translation layer can live. D-36 makes the site "a static site regenerated on every merge to graph, reading nothing but graph". D-35 requires everything outside the graph to be rebuildable from the graph plus the pinned gate ([architecture_decisions](../architecture_decisions.html)). F04-R10 enforces a Content-Security-Policy of `default-src 'none'` with same-origin scripts, which is why KaTeX is vendored under a sha256 manifest ([F04 spec](../../engineering/specs/features/F04.html); [math.js](../../site/opn_site/static/math.js)). D-3 already admits model-drafted explainers ("human author plus drafting model if any"). They are content-hashed, immutable and labelled unverified, and since v3.17 they count toward a target's digestion only when a steward or curator signs: "I can explain this proof without the tool that produced it." The project's research refuted AI proof sketches as a digestion rung with the rule "A model may draft; only a human signature counts" ([research_math_and_ai_2026-09 §8](../research_math_and_ai_2026-09.html)).

Against those rules each candidate lands in one of three places **(inference)**. A pure function of the graph (blueprint rendering, statement and dependency views, the correspondence of nodes to declarations) fits D-35 and D-36 cleanly and needs no decision. A deterministic Lean extraction (have-tree outlines, goal states) can be rebuilt from the pinned gate. But the site generator does not elaborate Lean, so the extraction has to run in the sandboxed gate or post-merge job and be committed as a product. Like `CONTEXT.json`, it then needs a decision that it is a product. An LLM rendering is not byte-reproducible. It can only be rebuildable if its output is committed, and the one existing home for committed model prose is the D-3 explainer. A generator that wrote model prose straight into the site, or a new graph actor that wrote it automatically, would contradict D-36's "the site cannot show what the repository does not contain" or require a new mode.

The site's present state shows how far there is to go. It prints the attested `Proof.lean` verbatim in a `<pre class="lean">`, and withholds it if the bytes do not match the attestation's hash. It shows an informal statement only at target level. Its contributor-prose renderer escapes every character and supports paragraphs and fences only, so an explainer containing TeX would display raw `$…$` ([prose.py](../../site/opn_site/prose.py); [render.py](../../site/opn_site/render.py)). The live graph holds **zero explainers and zero write-up records** across 114 nodes **(measured)**, and the site's own Leiden table admits "Nothing renders the graph as a blueprint yet". The informal content that does exist sits in three unconnected places: the curated `informal:` field of each target, 59 annexes (untrusted, written before a skeleton), and author comments inside attested Lean files. The erdos-69 variant's docstring is an example. Hole nodes, which carry much of the real mathematics, have gate-generated statements and no informal referent at all. Their ids are the only trace of the decomposition.

The sandbox bounds anything done at gate time. Step 3 runs with 2 CPUs, 4 GiB and 600 seconds, without network access. Memory kills on Mathlib targets were a real failure as recently as 2026-09-20 ([engineering log](../../engineering/CLAUDE.md)). Nothing in `gate/lean/` touches info trees today. The cost of extracting goal states from an 800-line Mathlib proof is **unmeasured**. The pretty-printing lesson also carries over. Default `ppExpr` once turned real-valued obligations into natural-number ones, so any extracted goal text must be printed with the round-trip-safe options the hole extractor already uses (`pp.coercions.types`, `pp.numericTypes`, `pp.funBinderTypes`).

## A three-stage plan: structure now, outlines next, signed prose last

**Stage 1: render each target as a blueprint, from the graph alone (build; no decision needed).** The graph is already a blueprint in all but format. A node is a declaration, declared deps are `\uses`, status is a colour, and annexes and explainers are the prose. The project's research called rendering it "the largest single digestion gain available and … a generator change" ([research_math_and_ai_2026-09 §7.2](../research_math_and_ai_2026-09.html)). Concretely, Stage 1 has five parts. Each target page gains an ordered lemma view down the closing proof's dependency closure. Each node shows its Lean statement, which Scholze found readable, beside whatever informal account exists, labelled by provenance, and links the attested proof by commit, hash and line span. Hole nodes show which parent `have` they came from. The page carries a correspondence table in the Erdős #728 style. And the KaTeX pass extends from the target's informal statement to explainer and annex prose, which still needs a small, escaped TeX path in `prose.render`. This meets requirement (1) at lemma granularity immediately and is fully rebuildable. It does not meet requirement (2), and should not claim to. Adopt: the site's vendored KaTeX, and leanblueprint's established status-colour conventions as a reading aid ([Tao's PFR tour](https://terrytao.wordpress.com/2023/11/18/formalizing-the-proof-of-pfr-in-lean4-using-blueprint-a-short-tour/)). A leanblueprint *export* is cheap and gives outside mathematicians a format they know, but its templates must be run with a vendored MathJax URL. Do not adopt Verso Blueprint wholesale yet. It has no licence file, its graph runtime defaults to jsdelivr, its toolchain line (4.34) is ahead of the graph's 4.33.1, and its model is a human-authored document, whereas OPN's DAG grows from contributions.

**Stage 2: a gate-extracted proof outline, committed as a product (build, with a measurement first and an owner's decision).** For each merged proof, a small Lean metaprogram would emit the `have`-tree: names, types printed with the round-trip options, the goal before and after each top-level step, the constants each step uses (reusing `opn-used-constants`), and which steps automation closes. The site would render this as a Lamport/Massot outline. Named claims come first. Each step expands to its goal state and then to its Lean lines. Steps closed by `omega`, `simp` or `positivity` are marked "routine computation" and collapsed by default, which keeps Tao's friction legible rather than smoothed away. Massot and Miller's `Explanation`/`GoalInfo` tree is the display model worth copying. Their code is not available, so this is a schema to emulate, not a dependency. SubVerso (Apache-2.0, maintained, JSON proof states) is the candidate to adopt for extraction, if it runs on the pinned 4.33.1 toolchain within the step budget. Whether it works on arbitrary files without anchors was not confirmed, so building the extraction on the gate's own `Frontend.lean` is the fallback. The measurement to make first is the extraction's time and memory on the erdos-1050 hole chain, inside the sandbox. The output still shows Lean, in better order. It moves requirement (2) closer for a reader willing to read Lean statements, and it is the scaffold Stage 3 needs.

**Stage 3: model-drafted explainers through D-3, signed by a human (adopt the existing path; tooling optional).** Where a steward wants a draft, it should be generated from the Stage 2 records, not from source text. The evidence-backed recipe is goal-state conditioning, per-tactic templates, a premise library, and recursive summarisation along the dependency tree ([arXiv 2509.09726](https://arxiv.org/pdf/2509.09726)). Each paragraph stays keyed to the step ids it describes. A cheap mechanical check exists that no paper reports: every lemma or hypothesis name a paragraph cites must appear in the Lean steps it is keyed to. That catches the "reasoning not in the original proof" failure without a model judge **(inference; untested)**. The draft enters the graph as an ordinary explainer PR, with the drafting model recorded under D-23, and counts for digestion only when signed. Nothing here needs a protocol change. The draft tool can live in the network repo as a contributor aid, the way D-9's review brief does, and be labelled the way D-9 labels model text: "a judgement, not evidence."

**What remains the owner's decision.** There are five calls, each of which changes the protocol surface. (a) Whether the Stage 2 outline becomes a graph product, extending what the post-merge job commits and possibly the step budget, or stays a site-build artifact produced by a separate pinned job. D-35 is satisfied either way only if the output is deterministic. (b) Whether *any* machine-generated prose may appear on a node page outside the explainer slot. D-36 and the §8 refutation say no as currently written, and changing that is a decision, not a feature. (c) Whether hole nodes should carry an informal statement at all, given that D-9 exempts interior nodes from fidelity and nobody currently writes one. (d) Whether the explainer path needs a schema, for example a field naming which step ids each paragraph tracks, to make anchoring checkable. Today the gate checks only the content-hash file name. (e) Whether the Massot–Miller line is worth pursuing directly with its authors, since it is the only design that targets both requirements at once.

## Conclusion

The owner's two requirements pull apart. Traceability is cheapest when the page shows Lean, and followability is best when a person rewrites the argument, as Tao's Sendov digestion did, ending up with a different and shorter proof. No tool in October 2026 closes that gap automatically for research-level agent proofs, and the only measurement of the attempt is 38 calculus proofs graded by one person. So the network should not try to manufacture followability. It should make followability *checkable and cheap*: a blueprint that already holds the correspondence, an outline that already marks routine steps and states each goal, and a signed explainer whose every paragraph names the Lean it tracks. That reframes the explainer slot. It stops being an empty box waiting for a volunteer and becomes the last, human step of a pipeline whose earlier steps are deterministic and rebuildable.

One finding should change the order of work: with zero explainers on 114 nodes, the binding constraint is not prose generation but the absence of any structure for a writer to hang prose on. Stage 1 is useful even if Stages 2 and 3 never ship. And because the Massot–Miller design is the only one aimed at both requirements, it is worth a direct inquiry to its authors before building Stage 2's display model independently.
